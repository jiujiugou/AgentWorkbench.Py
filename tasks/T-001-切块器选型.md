## 定案（2026-11-02，LlamaIndex 补测后）

补测缺口：README 点名的是 LlamaIndex，探针此前只测了 chonkie。本次补 4 组 + 当前生产自写版 1 组：

| 配置 | 块数 | 接缝率 |
|---|---|---|
| C# 基线（800/120 重叠） | 439 | 7.29% |
| **llama_default（同参数 800/120）** | 532 | **7.52%** |
| llama_zh（中文分句） | 526 | 9.51% |
| llama_zh_ov0 | 524 | 10.88% |
| llama_zh_ov0_s1000 | 484 | 8.26% |
| chonkie 最好一组（无重叠/1000） | 484 | 8.26% |
| **当前自写 chunk_pages** | 523 | **11.66%** |

**决定：llama_default 进生产。** 理由：

1. 全部 11 组配置里唯一追平 C# 基线的 Python 方案（差 0.23%，2 块量级）
2. 自写版（11.66%）接近垫底——它没有重叠；C# 的 120 字重叠让接缝两侧
   共享整行（判据「末行==首行」不报），这一半优势是参数给的，不是算法给的
3. 用户期望与 README 承诺都是「切块由成熟组件负责」，现在它同时是数据上的赢家

**重要修正**：此前说「现状 7.29%」是 C# 的数字，Python 自写版实际是 11.66%——
比基线差 4.4 个百分点，这件事在补测 current 之前是隐着的。

**没过的部分**：门禁 5% 仍然不过（7.52%）。C# 版同样没过（7.29%）。
剩余接缝的主因（29~34 处「块尾不像句尾」）发生在原文没有句末标点的结构
（表格、代码行）上，任何按句子切的组件都救不了——那是 C 选项（解析层回段落结构）的活。

**代价（T-002 的事，本单不动 src/）**：
- llama_default 532 块 ≠ C# 439 块，`seq` 全变 → 40 题评测库 gold（文件名, seq）全部重标
- HitRate / MRR 重跑，与 0.812 / 0.588 对比——可能变好也可能变差，数字说了算
- 组件表 llama-index-core 已标 planned；接进 `chunker.py` 那一刻改 adopted
