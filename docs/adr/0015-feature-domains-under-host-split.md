## 一、为什么需要这一篇

`docs/功能/F1~F7` 描述的是**单进程 Python 版**的功能口径：一个进程里既有身份、又有检索、又有 run 记录、又有 45 个端点。ADR 0013 把它拆成「C# 主服务 + Python 能力进程」之后，**同一件事出现了两种说法**：

- F4 说「每一次作答都在库里留下一行可核对的事实」——实施后，这行事实在 C# 的库里，不在 Python 的库里；
- F1 说「检索与答案生成必须遵守知识库可见性」——实施后，判定在 C#、过滤在 Python，一句话跨两个进程；
- F2 说「删除要三处清干净」——实施后，索引在 Python、记录在 C#，三处分布在两个库。

这**不是**措辞问题。U-19（成员能否删文档）就是「两种说法并存」的产物：需求写一种、实现做另一种，谁都没错，但没人能判定。现在 7 篇文档 + 3 篇 ADR 同时在讲同一批能力，如果不动，同一种病会以七倍的规模复发。

所以本篇的定位是：**把「域」与「运行位置」这两件事拆开，逐条标归属，并明确哪几篇从此冻结。**

---

## 二、判据：域不按「跑在哪里」切

功能域是「**一组必须一起成立的能力**」，它的划分依据是**不变量**，不是部署拓扑。所以：

- **F1~F7 的域划分本身不用推翻。** 身份、资料、问答、执行、记录、服务端、通用对话，这七组不变量在拆分后依然成立，只是每条能力多了一个「谁承担」的标注。
- **真正缺的是两件事**：① 域内每条能力没有归属；② **ERP 动作根本没有域**。

第二件事是本篇的重点。F1~F7 全篇以「作答」为对象——检索、判定、引用、拒答、记录一次问答。ERP agent 的对象是「**动作**」：查一张采购单、建一张草稿单、改一个交期。它有 F1~F7 里完全没有的四样东西——参数校验、幂等、审批、对账。硬塞进 F4 会让 F4 变成杂物间（F4 是「记录必须真实」，不是「动作必须安全」）。

**因此新增两个域**（F8 / F9，见 §五），F1~F7 冻结为 v1 口径。

### 3.2 要放弃的（连同放弃的理由）

| 放弃 | 为什么 | 怎么处理 |
|---|---|---|
| `CalculatorTool`、`GetCurrentTimeTool` | **不是「没用」，是风险源。** 它们给模型留了「自己算」的入口；ERP 调研里最典型的事故就是「合法推理出错误汇率」。数字必须来自 ERP 表 | 删除 |
| 本地知识实现：切块、解析、索引、`Chunker.cs`（用 SK 文本切块） | ADR 0013 定「RAG 不重写，归 Python」。这套实现 Python 侧更完整（61 文档 / 437 片段 / 评测集） | 删除实现，只留调用 |
| `SearchKnowledgeTool` / `ListDocumentsTool` 的**本地调用** | 同上。**放弃的是本地实现，不是能力** | 改为调 Python `/retrieve` |
| `RecallTool`、`RememberTool`、`SqliteLongTermMemoryStore`、`MemoryRetentionService` | 长期记忆第一版不做（ADR 0014 §二·附）。ERP 里记错的代价是**持续犯错**：记住一次错误的供应商偏好，后面每单都跟着错 | **停用不删**，保留代码与表 |
| `ToolApprovalPolicy` 的**执行方式**（同步确认） | 同步确认做不到「挂起 → 人等 → 恢复」，跨天审批必须靠 checkpoint | 保留业务规则，换执行方式（MAF `request_info`） |
| 自研 `Workflow` 的图构建与调度 | 与 MAF workflows 重复，两套调度器会争同一个调度权 | 保留表结构，调度交给 MAF |
| `DocumentsController` 里的上传/解析/重解析 | 解析归 Python；C# 只管归属、权限、记录 | 改为转发 |
| F7 通用对话路径（`Conversation/ChatService` 的非检索分支） | 与本产品主线无关（见 §六） | 停用不删 |

### 3.3 要加强的（按「不补就跑不通」排序）

| # | 加强什么 | 现在什么样 | 为什么必须 |
|---|---|---|---|
| 1 | **身份模型**：`AccountLevel`、团队元数据、凭据变更时间戳、`must_change_password` | `UserRecord` 只有 `Id/TenantId/UserName/DisplayName/PasswordHash/Role/IsActive` | REQ-AUTH-08（停用后会话失效）、REQ-AUTH-09（改密后失效）、REQ-25（账号等级）在 C# 侧**没有承载字段** |
| 2 | **知识库归属与可见性** | `KnowledgeBase` / `Visibility` **零命中**；`DocumentRecord` 无知识库字段 | 这是 Python 侧独有、必须整体迁过来的东西（Python 有 `knowledge_bases` 表 + 可见性判定） |
| 3 | **引用快照**（`message_citations`） | 只有 `CitationParser` 正则，**DbSet 里没有这张表** | 原文删除后历史答案必须仍可复核（ADR 0013 §二） |
| 4 | **参数校验层** | `ToolExecution` 里 `Validate` **零命中** | 金额上限、必填、枚举、跨字段一致性——现在一条都没有 |
| 5 | **幂等键 + 去重表** | `Idempot` **零命中** | 跨系统超时后状态未知，重试会重复建单 |
| 6 | **审计事件表** | `AuditEvent` **零命中**；`ExecutionTrace` 是运行轨迹，不是业务审计 | 「谁批的、批的哪张单、金额多少」必须能查 |
| 7 | **五字段错误信封 + `request_id` + `retryable`** | 匿名对象 `new { code, message }` | 跨进程后 `request_id` 是唯一贯穿线索 |
| 8 | **权限维度扩展** | 团队 × 角色 | → 业务对象 × 操作 × 数据范围 × 金额阈值（PDP 仍只一处） |
| 9 | **判定与编号迁入** | 在 Python：`sufficiency.py`、`document.py` 的 `[n]` 分配、`citation.py` | ADR 0013：判定与编号必须与持有 `run` 的一侧同处 |
| 10 | **Step 加三列**：`IdempotencyKey`、`ApprovalId`、`ExternalRef` | 只有 Tool/Arguments/Result/Error | 「这次调用对应哪张 ERP 单据」是追责的起点 |
| 11 | **HITL / Checkpoint** | `request_info`、`Checkpoint` 均**零命中** | ADR 0014 §六 的 ② |

> **顺序有讲究**：1~3 是「不补就没法谈权限与证据」，4~6 是「不补就会下错单」，7~11 是「不补就查不回来」。第 9 项依赖 Python 侧先稳定 `/retrieve` 契约，放在最后一批。

## 四、Python 侧

### 4.1 要放弃的

按 ADR 0013 §四 P1 执行，不重复列 16 张表清单。要点三条：

1. **整域退役**：F1（16 条 REQ）、F4、F5、F7、settings/供应商配置、45 个端点里除 4 个内部端点外的全部。
2. **前端退役**：`web/`（7,047 行 TS+Vue，5 页面）。新产品不写前端，先 API + 内部页面。
3. **判定逻辑移交**：充分性判定、`[n]` 编号分配、引用校验的**结论生成**归 C#；Python 只返回原始 hits 与距离。

**一条容易忽略的**：`packing.py` 的 D-03「编号、字符数、判定必须出自同一份检索结果」。跨进程后这条更容易坏——判定用 A 批、模型拿 B 批，两端都留不下证据。所以 Python 侧**放弃装填，只返回带稳定 id 的原始 hits**；装填在 C# 做。

### 4.2 要加强的

| # | 加强什么 | 现状 | 目标 |
|---|---|---|---|
| 1 | **`/retrieve` 契约化** | 现在返回已打包的证据（编号 + 字符预算 + 判定同源） | 返回 `hits[]`：`chunk_id / doc_id / content / page / distance / stable_seq`；**不带身份、不带阈值、不带编号** |
| 2 | **`/execute`（新写）** | 不存在 | ERP 适配器：拿到**已校验**的参数 → 翻译成 ERP 调用 → 原样返回 `result / external_ref / elapsed_ms` |
| 3 | **`/ingest`、`/embed` 保留并稳定** | 已实现 | 补上「调用方不传身份」的边界；删除补偿（L1/L2/L3）保留 |
| 4 | **主数据索引（新）** | 只有文档片段索引 | ERP 调研结论：**主数据进向量库**（供应商/物料/成本中心/科目），**交易数据实时查**。两套索引，不是一套 |
| 5 | **评测改造** | 40 题端到端 + 阈值 0.05/0.45 | 拆成两份：检索契约评测（HitRate/MRR 仍有效）、动作正确性评测（新，判据在 F8/F9） |

**保留不动的**：`rag/`（retriever / indexer / tokenizer）、`ingest/`（parsing / pipeline / deletion）、`llm/embeddings.py`、`evals/`、61 份文档 437 片段。这是全项目最好读、最像工具、最少编号跳转的一块。

### F8 的第一批需求（只写 4 条，不铺开）

| 编号 | 需求 | 判据（能写出反例才算） |
|---|---|---|
| **REQ-ERP-01** | 每个动作必须有机器可校验的契约（JSON Schema）：字段、类型、必填、枚举、取值范围 | 传非法枚举 / 缺必填 / 金额超上限 → **在调用前**拒绝，且不产生外部调用 |
| **REQ-ERP-02** | **数字不得由模型计算**：金额、汇率、税额、库存量一律来自工具返回或 ERP 表 | 提问中给出与 ERP 不符的金额 → 系统以 ERP 值为准，并显式指出差异 |
| **REQ-ERP-03** | 只读与写动作必须可区分，写动作默认不可自动执行 | 未带审批的写请求 → 拒绝执行；只读动作 → 无审批也执行 |
| **REQ-ERP-04** | 单据状态必须来自 ERP 查询，不得由模型叙述推断 | 「这张单到哪一步」→ 必须带 ERP 返回的状态码与时间戳；查不到 → 明确说查不到 |

### F9 的第一批需求（4 条）

| 编号 | 需求 | 判据 |
|---|---|---|
| **REQ-SAFE-01** | 写动作必须有幂等键，键与 `request_id` 同源；重复提交只执行一次 | 同一 `request_id` 连打两次 → ERP 侧只有一张单，第二次返回首次结果 |
| **REQ-SAFE-02** | 写动作必须先挂起、经人确认、再执行；审批记录落本库 | 未审批 → 无外部调用；超时未审 → 过期作废不执行；拒绝 → 记录理由且不执行 |
| **REQ-SAFE-03** | 超时不得重试，只能查证：记「执行中」→ 查 ERP 实际状态 → 再定 | 模拟超时 → 系统不重放调用，而是发起状态查询；查不到则转人工 |
| **REQ-SAFE-04** | 每个动作的意图、参数、审批人、结果、外部单号必须可追 | 任取一笔执行 → 五个字段齐全，能回答「谁在什么时候让系统做了什么」 |

**只有 8 条判据**——这是刻意的。Python 版最贵的教训不是「验证做得不好」，是「验证做得太早、太多、对象还没确定」（23 篇文档 / 113 条判据 vs 2 条会话 / 6 条消息）。这 8 条全部关于动作正确性，且每条都能写出反例。

## 六、F1~F7 七篇怎么处理

### 6.1 结论：**只加口径声明，不改正文**

| 文档 | 处置 | 说明 |
|---|---|---|
| **F1 身份与访问** | 冻结 + 加声明 | 16 条 REQ 全部归 C#。**唯一要动的是标注 REQ-24/25 在 C# 侧无承载字段**——这不是口径变，是实现缺口 |
| **F2 知识资料** | 冻结 + 加声明 | 执行体归 Python、归属与可见性归 C#。对象在 ERP 场景扩「主数据」，属 F8 的输入，不改 F2 |
| **F3 知识问答** | 冻结 + 加声明 | 范围缩小：从「产品唯一主线」降为「F8 的一个只读工具」。判据（三条不变量）仍成立，只是服务对象变了 |
| **F4 执行与审计** | 冻结 + 加声明 | **不改。** F4 管「作答的记录」，F9 管「动作的保障」，两者对象不同，混写会毁掉 F4 的清晰度 |
| **F5 会话与记录** | 冻结 + 加声明 | 全归 C#，语义不变。补一张 `message_citations` 表属实现动作，不改文档 |
| **F6 服务端能力** | 冻结 + 加声明 | 现有 5 条归 C#；**新增一条内部契约需求**（4 个内部端点、不对外暴露、不判身份），写在 ADR 0013 而不回填 F6——避免正文与 ADR 各存一份 |
| **F7 通用对话** | 冻结 + **停用** | 见 6.3 |

### 6.2 为什么不是修订七篇

每篇正文都有大量 `pyproject.toml` 的验证编号引用（`I-V1`~`I-V19`、`C-V1`~`C-H2`、`S-V*`、`D-V*`、`V-13`~`V-19`）。ADR 0013 §七已定「113 条验证项逐条重立」——**重立之后，这七篇里的编号引用全部失效**。

那么「修订七篇」的真实工作量不是改章节，是**重写 113 条判据 + 重接所有编号引用**，而且是在一个连一次真实 ERP 动作都还没跑过的时间点上做。这正是要避免的那件事。

所以：**正文冻结，顶部加 4 行声明，新增能力进 F8/F9**。声明写清「本文描述单进程 Python 版，判据引用已冻结，不得作为新产品判据」——这样既不留两种说法，也不用重写。

### 6.3 F7 为什么停用而不是删

- 它**已实现**（`conversations.kind`、`D-V1`~`D-V5`）。删掉要连带删表与迁移，成本高于收益。
- 它与主线无关：本产品的不变量是「动作可追责」，通用对话既不检索也无动作。
- **停用 = 代码保留、入口关闭、判据不再维护**。重开条件：出现「不查资料、纯对话」的真实需求（例如客户内部助手的闲聊入口），且有人愿意为它维护一套答案合同。

## 七、实施顺序（六步，第一步不写业务代码）

1. **改 `UserRecord` + 补 `KnowledgeBase` / `message_citations` 三张表**（3.3 的 1~3）。没有这三样，后面每一步都在流沙上。
2. **写 `ErpAction` / `ActionSpec` / `ActionResult`，用假工具跑通动作层**（ADR 0014 第一步）。此时不接 MAF、不接 ERP。
3. **补参数校验 + 幂等键 + 去重表**（3.3 的 4~5）。此时仍不接真实 ERP——用假工具验证「重复提交只执行一次」。
4. **接 ERPNext，打通 1 读 + 1 写（写挂审批）**。第一个可证伪点在这里。
5. **补错误信封 + 审计表 + Step 三列**（3.3 的 6~7、10）。有了真实动作，才知道要记什么。
6. **判定与编号从 Python 迁入**（3.3 的 9）+ 瘦 Python。

**为什么表结构在前、ERP 在后**：§6.3 的教训是「对象没确定时堆判据」。反过来，表结构是**对象**，先定它不会白做；而判据是**结论**，要等第一次真实动作之后再定。

## 八、后果

- **七篇功能文档不再是现行口径**，只是 v1 的历史记录。任何人拿 F4 的判据去验 ERP 动作，都会验错对象。
- **两个仓库的能力不再对称**：C# 有运行时缺业务语义，Python 有知识层缺运行时。这种不对称是设计意图，不是待修的缺陷。
- **`docs/验收/` 四篇（含 v2.4 验收计划、现状、未解决问题 U-01~U-25）全部标「历史口径」**。它们是单进程 Python 版的验收记录，对新产品不构成结论。
- **F8/F9 的第一批只有 8 条判据**，比 F1 一个域（16 条 REQ）的一半还少。这是刻意的克制，不是遗漏。
- **长期记忆、通用对话、多 agent 三样明确不做**，且都写了重开条件，不是「以后再说」。

## 九、重开条件

| 决定 | 什么时候重开 |
|---|---|
| F1~F7 正文冻结 | 当 F8/F9 的 8 条判据全部通过、且第一次真实 ERP 写动作被成功执行与追回之后，再决定是否把 F1~F7 重写成生产版口径 |
| F7 停用 | 出现「不查资料、纯对话」的真实需求，且有人维护它的答案合同 |
| 长期记忆不做 | 有真实使用数据，能定义「什么算记错」时 |
| 只读一个 + 写一个 | 两类动作都跑通并经真实数据验证后，再扩第三个动作 |
| C# 侧主数据不进向量库 | 若 ERP 主数据量极小（< 1 万条），可直接实时查，不必建第二套索引 |
