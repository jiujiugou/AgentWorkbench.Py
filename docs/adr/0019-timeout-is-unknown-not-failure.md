# ADR 0019 · 外部动作超时归「不知道」而非「失败」，且不人工造故障验它

- **状态**：Accepted
- **日期**：2026-11-22
- **来源**：结果层第 4 句「超时只查证不重放」的真跑验证过程；用户 2026-11-22 指令「不需要模拟，我们知道有这种情况然后做了方案」定调
- **与既有 ADR 的关系**：不动 0013–0018 的任何归属。本篇只裁定**动作执行体的失败归类语义**与**该类机制的验收方式**；不新增架构组件、不改进程边界。

---

## 背景

外部副作用动作（提交、取消）发出后，写可能已经落到对方，但响应在回来之前断了。此时系统**不知道成没成**。

旧行为把它和「对方明确拒绝」一起归成 `Failed`，审计写「失败」，外部单号空。后果有两层：

1. **查证机制永不可达**。`ActionRunService` 只在结果是 `Unknown/Timeout` 时走「只查证不重放」；全归 `Failed` 后，这条分支在真连链路上没有任何生产路径能到达，只活在单测里。
2. **把人诱去重试**。显示「失败」但对方可能已经成功，操作者重试一次就成了重复副作用——正是这套系统要防的东西。

11-22 真跑暴露了三层缺口：错误归类把所有失败拍成一类 → 执行体没有 `Unknown` 路径 → 工具调用根本没有超时（会无限等，超时场景不会发生）。三层都已修，判据全绿。

但接着卡在验收上：为了拿到「真超时后对方只留一条写」的外部证据，两次尝试人工造故障——在 MCP server 侧注入 sleep、计划在 C# 侧假装超时。前者把同步 server 的事件循环堵死、连查证一起饿死；后者是纯演戏。两者都不是真实发生的超时。

---

## 决定

**一、归类语义**：外部副作用动作在「不知道成没成」时，一律归 `Unknown`，绝不归 `Failed`。

- `Failed` 只留给**对方明确拒绝**（4xx、校验错、权限错）——那种情况副作用确定没发生。
- `Unknown` 触发**只读查证**，绝不重放写动作。
- 区分依据只看一件事：**副作用到底有没有发生，我们知不知道**。

**二、验收方式**：这类"防止重复副作用"的机制，**不靠人工造故障来验收**。

- 知道有这个情况、做了方案、有判据覆盖行为，就够了。
- 外部证据等真实使用里自然出现一次超时时，看轨迹怎么收口；不造、不演、不把造出来的故障当证据。

**三、机制指针**：具体归类、超时配置、查证分支的实现见 C# 仓 `src/Core/Tools/AgentWorkbench.Tools.Mcp/` 与 `src/Core/Runtime/AgentWorkbench.ActionGateway/ActionRunService.cs`；判据见对应测试文件。ADR 不复制规则。

---

## 后果

**好处**：
- 「不重放」从单测摆设变成真连可达的语义；超时不再被误报成失败，掐断「显示失败却已成功→人去重试→重复副作用」这条链。
- 验收不再被"造不出真故障"卡住，也不再用假故障制造假绿。

**代价**：
- `Unknown` 与 `Failed` 必须逐类分清，判据落在文本关键字与异常类型上，对方换错误文案可能漏判（保守方向：漏判成 `Failed`，即回到不查证——不会误把拒绝当超时）。
- 第 4 句的**外部证据明确拿不到**，状态长期停在「机制已验、外部未验」。这是诚实代价，不用绿灯填补。
- 引入调用超时后，真慢的外部 API 可能被误判超时（可配置缓解）。

---

## 什么情况下该重开

- 出现一种可观测、且**不是人工注入**的判定信号，能可靠区分「对方拒绝了」和「对方收到但响应丢了」——则重审归类判据是否该从文本匹配换成结构化信号。
- 真实使用里自然发生一次超时，轨迹收口行为与本篇决定不符——则本篇的归类语义被证伪，重写。
- 有人要用人工造故障的结果来宣称第 4 句「已验」——按本篇驳回，证据不算。
