# ADR 0017 · 底座业务无关：端口与适配器

- **状态**：Accepted（架构原则，未实施）｜**日期**：2026-11-07
- **触发**：对照「一个完整 Agent 系统的技术结构」七层图时确认——`Agent Runtime / Harness`、`编排层`、`知识层`、`记忆与状态层`、`工程保障层` 五层**不应认识任何外部系统的具体概念**；对接只能由 `企业应用层` 与 `工具层` 承担。
- **与 ADR 0013 正交**：0013 管「进程与状态」（谁持有、跨不跨进程），本篇管「业务语义」（谁认识采购单）。两者互不取代，冲突时各管各的。
- **本文不推翻 v2 范围**：第一版仍只做 ERP 一个动作域。本篇定的是**边界**，不是把产品改成通用平台。

---

## 一、决定

一句判据：

> **把 ERP 整个换成另一个动作域（MES / WMS / PLC 控制），底座五层一行代码不改，只换企业应用层的策略与工具层的适配器。做不到，就是底座被业务污染了。**

| 侧 | 组成 | 认识外部系统吗 |
|---|---|---|
| **底座** | Runtime / Harness、编排层、知识层、记忆与状态层、工程保障层，**以及工具层的「管辖」半边** | **不认识**。只认识自己的抽象词汇 |
| **业务侧** | 企业应用层、**工具层的「适配器」半边**（动作定义 + 执行体） | 认识。所有业务语义集中在这里 |

这是依赖倒置（端口与适配器）：**底座定义端口，业务侧实现并注入**。底座不 import 业务侧，业务侧可以 import 底座的契约。

---

## 二、逐层词汇边界

「不认识」不是「什么都不写」，是**只认识自己的抽象词汇，不认识任何外部系统的概念**。

| 层 | 允许出现（抽象） | 禁止出现（业务语义） |
|---|---|---|
| **Runtime / Harness** | `ToolName`、`Arguments`（不透明 JSON）、`Guard`、`Veto`、`Status`、`RunCode`、`SessionId`、迭代轮次、终态 | 采购单、供应商、金额阈值、审批人角色、任何 ERP 名 |
| **编排层** | 步骤、节点、状态机、挂起 / 恢复、`CheckpointBlob`、超时（时长可注入） | 审批层级、「谁审」、金额档位、单据状态码、月结期间 |
| **知识层** | 文档、片段、向量、距离、`hits[]`、`tenant_id` / `kb_ids`（**作为下传条件**）、`EvidenceRef` | 物料编码、税码、成本口径、交易分录语义、SKU 主数据的字段含义 |
| **记忆与状态层** | 会话历史、`run` / `step`、逐字节 checkpoint、引用快照字节 | 业务单据状态（如「采购单待审批」）——那是 ERP 的状态，不是任务状态 |
| **工程保障层** | `TraceEvent`、`request_id`、审计事件**结构**、评测执行框架、五字段错误信封 | 「这张单有没有下错」的判据、题库内容、通过线、重试的业务策略 |
| **工具层 · 管辖**（属底座） | 白名单、JSON Schema、参数校验规则、幂等键生成与去重、审计落库 | 具体字段名、ERP 端点、协议细节 |
| **企业应用层**（业务侧） | 身份、唯一 PDP、权限策略（业务对象 × 操作 × 数据范围 × **金额阈值**）、审批层级、字段映射、业务 API、管理后台 | — |
| **工具层 · 适配器**（业务侧） | `ActionSpec` 声明、ERP / PLC / MCP 具体调用、单据状态翻译、题库与判据 | — |

**最容易被忽略的一格**：工具层在图里是一整块，实际**只有适配器半边认识业务**。白名单、Schema 校验、幂等键、审计落库这些「管辖」动作是通用的，属于底座；把 `PurchaseOrder` 写进管辖层，等于把业务概念塞进底座。

## 三、三个注入口（端口）

底座不是不能拦、不能判、不能测——它**问**，但不**理解**。

1. **权限**：底座发 `PermissionQuery(subject, action_key, scope)`，PDP 返回 `allow / deny + reason`。
   底座认识「调用前必须问一次」，**不认识「金额上限 5 万」**。PEP 在底座（middleware），PDP 在企业应用层（ADR 0013 唯一判定点）。策略与阈值属于业务侧。
2. **评测与轨迹**：底座提供 `TraceEvent` 结构、审计事件表、评测执行框架；**判据、题库、通过线由动作集自带并注入**。附录 C 写的「评测执行可交 Python、判据定义不交」，本篇把「不交」的对象明确为业务语义。
3. **动作定义**：`ActionSpec` 由适配器声明，底座按 Schema 校验、按名绑定、原样透传 `Arguments`。**参数值对底座是不透明 JSON**；字段含义只有适配器知道。

## 四、最容易破界的三处

| 处 | 破界形状 | 正解 |
|---|---|---|
| **幂等键** | 运行时自己去生成带业务含义的键 | 底座只**透传 / 记录**，不生成、不理解（ADR 0016 §七已写，本篇扩到五层） |
| **Checkpoint** | 把「采购单待审批」当执行进度存进去 | checkpoint 存的是**执行进度字节**；业务状态在业务库。「框架说继续、业务说已完成」的分裂就来自混写（ADR 0014 §二·附） |
| **审批** | 把「谁审 / 几级 / 超时多久」写死进 workflow 定义 | 底座只提供挂起 → 人批 → 恢复的**机制**；层级与时长是**注入的策略** |

## 五、与现有 ADR / 文档的关系

- **ADR 0016 §七** 已对 `AgentHarness` / `AgentLoop` / `ToolExecution` 三工程立禁词（含「携带不等于理解」）。2026-11-07 实测 C# `src/` 中 `PurchaseOrder` / `Supplier` / `AmountLimit` / `TaxCode` / `ERP` / `SAP` / `Modbus` **全部零命中**——**运行时那一层已经成立**。本篇把它扩到编排、知识、记忆与状态、工程保障四层，并明确工具层两半。
- **ADR 0014 §三** 的 `ErpAction` 是**适配器侧的动作定义**，不是底座类型；底座侧统一用 `ActionSpec`。原表述把二者并列叫「自己的领域层」，容易读成底座类型，在此澄清。**不改名**——改名会牵动 §3 示例与 §6 改动清单。
- **ADR 0013**：Python 的 `/execute` 是适配器执行体，它认识 ERP；`/retrieve` 不认识。进程边界与业务语义边界正交，不冲突。
- **ADR 0015 的 F8 / F9** 是**第一个动作集**（8 条判据带金额、单据状态等业务语义），不是底座的一部分。
- **v2 产品目标与范围**：§1.1 的「ERP 动作 Agent」描述的是**第一版产品**，不是底座；底座业务无关由本篇约束。

## 六、可验证判据（只 2 条）

| 编号 | 判据 | 反例 / 通过条件 |
|---|---|---|
| **AC-01 换域不改动底座** | 用一个**假的第二动作集**（不同字段、不同权限策略、不同题库）跑通同一套运行时，底座五层 diff 为空 | 若为了跑通它，需要往 Runtime / 编排 / 知识 / 记忆 / 保障任一层加一个业务字段 → 失败 |
| **AC-02 禁词扫描** | CI 扫描底座模块的**类型名、字段名、方法名**，命中业务词即失败 | 词表由业务侧维护：`PurchaseOrder` / `Supplier` / `AmountLimit` / `TaxCode` / `SAP` / `用友` / `金蝶` / `Modbus` / 具体单据状态码。注释与说明文字里提到不算违规 |

**AC-01 第一版只做一次轻量演练**（假动作集、假题库），**不实现第二个真实域**——证明边界用，不是平台化。两条件都不改 §4 成功目标里的「1 只读 + 1 写」。

这两条比堆判据更有力：**它验的是「业务能不能换掉」，而不是「这次跑通了没有」**。

## 七、代价与重开条件

- **代价**：每条业务语义都要走一次注入，比直接写在底座麻烦；端口定得过窄会让适配器反复绕路，定得过宽又会把业务概念漏进来。第一版只定三个端口（权限 / 评测 / 动作定义），不预先抽象第四、第五个。
- **不重开**：出现第二个真实 ERP、第二类动作，只**新增适配器与策略**，不动本篇。
- **重开条件**：若出现「所有动作域都共享同一条业务规则、且必须由运行时强制执行」，才考虑把它上移为**新端口**——仍然不是把业务概念写进底座。
