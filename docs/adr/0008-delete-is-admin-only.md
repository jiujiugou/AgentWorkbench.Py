# ADR 0008 · 删除文档只对团队管理员开放

- **状态**：Accepted
- **日期**：2026-11-05
- **机制**：见 [`docs/功能/F2-知识资料.md`](../功能/F2-知识资料.md) §1.2 / §1.5

## 背景

REQ-10 的 actor 表写的是「管理员；合规审阅者」，而实现只判了「是不是这个团队」。
两者不是同一条规则，D9 的红队 B 组实测把它变成了一个可复现的事故：

```
管理员上传一份资料 → 最低权限成员的一条 DELETE → 204
（没有软删除，没有"谁删的"的入口，历史回答里的引用还在）
```

一个离职账号或一次误点就能清空团队知识库。这不是权限写错，是**需求与实现两处
都有"谁来决定"的权力**，而两处说法不同、又都各自成立。

三个候选，各自否决的理由：

| 候选 | 否决理由 |
|---|---|
| 谁都能删（现状） | REQ-10 的 actor 表成了假话；删除是唯一「让别人失去依据」的破坏性动作，而它没有审计入口 |
| 只能删自己上传的 | `documents` 表没有上传者列，加列要迁移；更根本的是语义错——文档是**团队资产**，不是个人文件，按上传者判会把共享知识库变成一堆私有文件 |
| 只有管理员能删 | 放弃的是「成员传错了能自己撤」 |

## 决定

**`DELETE /api/documents/{id}` 只对团队管理员开放。成员得到 403，且判定在查行之前。**

- 判定复用 `identity_context.require_admin`，与管理接口同一条规则、同一份实现。
- 顺序：先判「你有没有资格调这个动作」（403，不需要目标），再查行（404）。
  反过来，成员拿一串 id 就能用 403 与 404 的差别数出团队里有多少份资料。
- 前端在 `DocumentsView` 按 `role` 隐藏删除按钮。**它只是礼貌**：边界在后端。

「合规审阅者」在 v1 不存在——`identity/models.py` 里的角色只有 `admin` 与 `member`，
这是 F1 §2.1 刻意的二维取舍。等真的出现「只能审阅、不能管理成员」的岗位需求时，
再讨论它是第三种角色还是管理员的一个子集；在那之前把它写进 actor 表，
只会让每个实现者自己猜它等于谁。

## 后果

**好处**

- 「删除」的授权与「成员管理」的授权收敛到同一处判定，改角色模型时只有一个地方要改。
- 成员误传的代价从「知识库被清空」降为「找管理员删一次」。
- 审计口径统一：能删的人和管理员是同一批人，出事时不需要先回答「谁有这个权限」。

**代价**

- 成员传错文件后不能自己撤销，要等管理员。**这是这次交换里真实付出去的东西**，
  不是可以忽略的边角——上线后如果成员上传量远大于管理员在线时长，会变成一条体验投诉。
- 「删除」从此不是团队协作能力，与 F1「团队内部不做文档级授权」并不矛盾：
  它仍然只按角色分，没有引入文档级 ACL。

## 什么情况下该重开

- 成员上传量成为主要来源、且管理员无法在可接受时间内响应删除请求 → 讨论
  「软删除 + 成员可撤回自己上传的」。（前提是 `documents` 补上传者列。）
- 出现真实的「合规审阅者」岗位，且它的删除权与管理员不同 → 那时它才需要成为角色，
  而不是坐在 actor 表的括号里。
