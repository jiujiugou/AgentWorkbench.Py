# ADR 0010 · 通用对话与知识库问答分成两个能力

- **状态**：Accepted
- **日期**：2026-11-05
- **机制**：见 F7 §1–§4；会话类型见 F5 §1.10；运行记录见 F4 §1.6

## 背景

当前前端在同一个对话页上有一个“对话 / 知识库问答”开关，但 Python 后端只有
`/api/knowledge/ask` 一条作答链路：两个按钮最终都调用同一个接口。用户点“对话”
时，系统仍然检索企业文档、仍然可能因“资料不足”拒答。这是一个**假选择**：界面
承诺了两种能力，后端只提供了一种。

产品原定位明确写着“不是通用聊天助手”（`docs/需求/产品目标与范围.md` §1.3），
但实际需求又需要“不查资料、直接和模型说话”的入口。继续用一个开关模拟两种能力，
会让引用、拒答、审计三套合同互相污染：通用回答可能被当成企业文档答案，知识库
拒答后可能被通用回答兜底。

## 决定

把通用对话做成独立功能域 **F7**，与知识库问答（F3）并列：

1. **入口分开**：知识库继续走 `/api/knowledge/ask`；通用对话走独立入口（建议
   `POST /api/chat`，具体传输形状归 F6/接口契约）。
2. **会话类型不可变**：`conversations.kind` 取 `knowledge` / `general`，创建时固定；
   切换模式 = 新建会话，不允许同一条会话混流。
3. **通用对话不检索、不引用、不兜底**：不读企业文档，不生成来源/角标；知识库拒答
   后不得自动转通用回答。
4. **仍走统一 run 与归属**：每次通用回答必须写 run；run 没有检索/证据步骤，也不
   得伪造；`user_id` / `tenant_id` 与会话归属沿用 F1/F5。
5. **共用 F6 的平台级模型配置**：不为通用对话另建供应商或模型配置。
6. **明确标识**：接口与界面都标出“通用对话 / 未使用企业资料”，不得长得像知识库
   答案。

## 后果

好处：

- 两种答案的合同各自成立：知识库可核、可拒答；通用对话不冒充企业资料。
- 引用、拒答、审计不再依赖 UI 的局部开关，服务端有类型可判、可测。
- 历史可以同时保存两类会话，且用户能分辨哪条有企业依据。

代价：

- 增加一个功能域、一条 REQ、一个 `kind` 列与迁移，以及两套入口的验收。
- 前端要拆入口/列表筛选，不能继续用当前同一个 `ChatView` 的局部 toggle。
- 通用对话也要写 run，增加一次写入与审计链；但它不能伪造检索步骤。
- 产品文档必须从“不是通用聊天助手”调整为“知识库问答为主、通用对话是明确标识的
  辅助入口”，否则文档与界面自相矛盾。

## 什么情况下该重开

- 产品决定通用对话成为主产品，而不是辅助入口：重写产品定位、差异化与 MVP 目标。
- 客户要求知识库拒答后自动用通用模型补答：重开 F7 的“不兜”不变量，并同时改
  F3、F7、验收与 UI 告知。
- 审计要求允许通用对话不留 run：重开 F4 的“每个作答入口都留痕”。
- 通用对话要接工具调用、联网、文件上传或跨会话记忆：新增独立功能域/REQ，不能直接
  塞进 F7。
