**一句话**：C# 强在运行时与编排，Python 强在身份、知识与评测。ADR 0013 的分工正好取两边所长——C# 拿走运行时与状态（但要补身份语义），Python 留下知识层与评测（但要瘦成四个端点）。

**最该警惕的**：两侧都没填上的格子是 **ERP / PLC / MCP / Checkpoint / 人工审批**。也就是说，把两个仓库拼起来，仍然得不到一个「能可靠执行外部动作」的产品——这块得新写，不是迁移。

## 附录 C：按七层的归属裁决（C# 负责什么 / 什么完全交 Python）

- **判据来源**：ADR 0013 §一「状态 vs 无状态计算」、§三 内部契约、§三·附 `/execute` 三条约束。
- **本文不新立决定**，只把已定的判据按七层逐行落到具体能力上；冲突时以 ADR 0013 为准。
- 一句话：**C# 负责「决定」（能不能、做不做、记不记、算不算数），Python 负责「算」（解析、切块、向量、检索、翻译、跑题）。**

| 层 | 归属 | 逐项裁决 |
|---|---|---|
| **企业应用层** | **整层 C#** | 唯一对外入口（登录、身份、管理后台、业务 API）。Python **不判身份、不持有用户表、不暴露公网端口**。注意：Python 版 F1 十六条 REQ、九个 `judge_*`、账号等级、知识库可见性做得最完整，但按规划是**整体迁到 C#**，不是「共用」或「各留一份」——留着就是两个权限源，PDP 当场裂开 |
| **Agent Runtime / Harness** | **整层 C#** | 模型循环、工具调用、上下文、会话、任务执行，Python 一项都不留。**上下文要特别说明**：Python 只给原始 `hits[]`，编号 / 装填 / 判定 / 证据快照全在 C#，所以这一项**不算**交给 Python |
| **编排层** | **整层 C#** | LangGraph → MAF Workflows。工作流图、状态机、人工审批（问谁 / 几级 / 超时 / 记录）、Checkpoint 存储后端全在 C#。Python 不调度、不挂起、不存进度 |
| **工具层** | **劈两半** | **C# 管辖**：注册表与白名单、JSON Schema、参数校验、权限判定、幂等键生成、去重表、审计落库、审批闸门。**可完全交 Python**：执行体——拿已校验参数 → 翻译成 ERP / HTTP / SDK 调用 → 原样返回 `result / external_ref / elapsed_ms`。两边各持各的库，不共享连接、不跨库事务。MCP / PLC 第一版不做 |
| **知识层** | **大部分完全交 Python** | 完全交：文档解析（PDF / DOCX / XLSX）、切块、embedding、FTS + sqlite-vec 索引、检索排序与 RRF、索引侧删除补偿、**主数据索引（新）**、61 份文档 437 片段这些可重建资产、检索契约评测（HitRate / MRR）。**唯一例外**：权限过滤的**判定**不交——`tenant_id / kb_ids` 由 C# 的 PDP 判完作为查询条件下传，Python 只执行过滤，不判「这个人能不能看」；`/ingest` 的删除决策同理归 C# |
| **记忆与状态层** | **整层 C#** | 会话历史、任务状态、长期记忆（第一版停用）、Checkpoint，一项都不交——这层名字里全带「状态」。注意两层 Checkpoint 别混：MAF 恢复的是框架内部执行进度，业务状态仍在自己的库 |
| **工程保障层** | **劈两半 + 横切** | **C#**：审计事件表、权限拦截（PEP 挂 middleware）、`request_id` 生成与贯穿、重试策略决策、错误恢复的状态判定（查证不重放）、跨进程轨迹收口。**可完全交 Python**：评测的**执行与数据集**（40+28 题改造成对 `/retrieve` 的契约评测、阈值网格扫描）、解析/索引侧指标与自检、单侧进程的日志与耗时。**不能交**：判据定义与「什么算通过」的结论台账——Python 可以跑题、出数，不能自己定通过线 |

### 「完全交给 Python」的四条充要条件

四条**同时**满足，Python 才能独立闭环（可单独重启 / 部署 / 压测，不用回 C# 问）：

1. **不读身份、不判权限** —— PDP 只能有一处；
2. **不写业务状态** —— 不产生「发生过、以后要查、要回滚」的东西；
3. **给定输入必然同一输出** —— 可重放，不依赖上一次调用留下的东西；
4. **不自行记住幂等结果** —— 写动作带 C# 下传的 `idempotency_key`，去重表在 C#，`/execute` 只是转发，不是幂等通道。

任一条不满足 → 归 C#。

### 两个必须说清的后果

- **按这张图，Python 能「整层完全负责」的只有知识层的一部分**；其余六层要么全归 C#，要么只分到「执行体」「跑题」这类无状态片段。所以 Python 从主服务降成能力进程是**实质性**的，不是换个端口。
- Python 侧现在最强的三块里：**身份与前端要退役，评测只留执行**；留下的恰好是 `rag/` / `ingest/` / `embeddings.py` / `evals/`——全项目最好读、最少编号跳转的那一块。

### D.1 为什么不是「一篇对应一层」

- **F 域按「谁承担不变量」划分**：一条不变量的实现会**竖着穿过**多个技术层。

  工程保障层（引用校验与拒答判定）**四层**。

## 结论

这张图**可以填，但只能当体检表**：它能查出「哪些能力没有」，查不出「这些能力归谁、状态在哪、边界在哪」。

- 用来定范围 → 够用；
- 用来写代码 → 用 ADR 0016 的五条不变量 + 上一轮那张 17 工程装配图；
- 用来判「能不能上线」 → 都不够，要先跑通 F8/F9 的 1 读 + 1 写。

**填完最值得记的一句**：运行时那一层几乎全绿，空的全在「动作能不能被追责」这一侧。这与 Python 版的失衡正好互补——那边是验证体系最厚、运行时是空壳；这边是运行时最厚、动作保障全空。
