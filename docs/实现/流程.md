# 实现流程

流程本身一年不会变一次，所以这里只有一张图、两张表、三条判据。

```
新增契约？───否───→ 直接改，一行提交信息
    │是
跨模块 / 决策未定？───是───→ 先写 ADR（取舍与代价），再往下
    │否
    ↓
① 定契约 ──→ ② 写断言 ──→ ③ 实现 ──→ ④ 改坏，再恢复
```

## 分档：唯一判据是"有没有新增契约"

| 档 | 走法 |
|---|---|
| 小（无新契约，一天内） | 直接改 + 提交信息 |
| 中（新增枚举 / 状态机 / 接口 / 配置项） | 四步循环 |
| 大（跨模块，或"这么做还是那么做"没定） | 先写 ADR，再走四步 |
| 选型未定 | 不写代码，开一张 `tasks/` 决策单，产出是一个数字和一个选择 |

**判据是"有没有新增契约"，不是"我觉得重不重要"。** 给两行 bug 套完整流程，是这套东西被弃用的头号原因。

## 四步的完成标志

| 步 | 做完的标志 |
|---|---|
| ① 定契约 | 断言能 import 到它们——失败从 `ImportError` 变成 `AssertionError` |
| ② 写断言 | 跑一次，**贴出红在哪一行**。红在 `ImportError` 或 `NotImplementedError` 才算合格 |
| ③ 实现 | 全绿 + CI 六段全过 |
| ④ 改坏 | 三类各一次：顺序错、判据缺、兜底错。能说出"改这处 → 红哪几条" |

## 三条判据

1. **什么时候不能先写断言**：红是因为"函数不存在"→ 写；红是因为"我还不知道该测什么"→ 不写，先跑对照实验定接口（比如切块器四选一）。
2. **文档什么时候删段落**：问"这段话删掉，代码会不会写错"。会 → 它该是断言，搬进 `tests/invariants/`；不会 → 删掉或进注释。必删的是"描述文档自己状态的表"（进度表、已下沉表）。
3. **铁律**：能被 ruff / mypy / import-linter 判的，一个字都不写进文档。本文只写人做判断的部分。

## 哪些真有牙齿

| 规则 | 谁执行 |
|---|---|
| ③ 全绿 + CI 六段全过 | **机器**：`scripts/ci.py check` 退出码 |
| 每条不变量写明「被改坏时用户会看到什么」 | **机器**：`test_gates.py::test_every_invariant_states_what_breaks` |
| ① ② ④、三条判据、分档 | **人**：看 diff 判断，机器判不了 |

不假装最后一行有闸。流程约束的是「人怎么干活」，机器只能验「系统是什么状态」——
所以本文的其余部分是**给你 review 用的标准**，不是给 CI 用的规则。

## 不适用

探针与 spike（`evals/spikes/`）、一次性脚本、选型未定时的实现、纯文档改动。
