## 1. 产品定义

### 1.1 一句话

> **面向企业私有化部署的受控动作执行底座：把「模型想做什么」变成「系统真的做了什么」，保证不越权、不重复执行、办错了能追回。对外交付的是「底座 + 一个动作域」的完整系统；ERP 是第一版装进去的那个动作域，不是产品本身。**

两层必须同时说清，缺一半都会读错：

- 只说「底座」→ 会读成卖框架、没有可交付的东西；
- 只说「ERP 动作 Agent」→ 会读成一套工单逻辑，把底座降成配角（v2.0 的毛病）。

**底座不单独交付。** 客户拿到的是装好第一个动作域、能跑通完整动作的系统；「业务无关」是它的内部结构约束，不是对外售卖的形态。

### 1.2 产品由两层组成

| | 组成 | 认识外部系统吗 |
|---|---|---|
| **底座**（主体，业务无关） | `Agent Runtime / Harness`、`编排层`、`知识层`、`记忆与状态层`、`工程保障层` 五层，**加工具层的「管辖」半边** | **完全不认识**。只认识工具名、不透明参数、步骤、片段、会话、轨迹、终态 |
| **动作域**（可替换，业务相关） | `企业应用层`（身份、唯一 PDP、权限策略、字段映射、业务 API、管理后台）+ `工具层·适配器半边`（`ActionSpec` 声明、ERP / PLC 具体调用、单据状态翻译、题库与判据） | 认识。所有业务语义集中在这里 |

**工具层必须劈两半**：管辖（白名单 / JSON Schema / 参数校验 / 幂等键生成 / 去重表 / 审计落库）属于底座，同样不认识业务；只有适配器半边认识采购单。把业务概念写进管辖层，等于把污染塞回底座。

底座**问，但不理解**，靠三个注入口（ADR 0017 §三）：

- `PermissionQuery(subject, action_key, scope)` → PDP 返回 allow/deny。底座知道「调用前必须问一次」，不知道「金额上限 5 万」；
- `ActionSpec` 由适配器声明，参数值对底座是**不透明 JSON**，只按 Schema 校验、按名绑定、原样透传；
- `TraceEvent` 结构与评测框架在底座，**判据、题库、通过线由动作集注入**。

> **换域判据（ADR 0017 AC-01）**：把 ERP 换成另一个动作域，底座五层一行代码不改，只换企业应用层的策略与工具层的适配器。这是本节「底座是主体」唯一可验证的含义。

三个最容易破界的地方：幂等键只透传不生成；Checkpoint 存执行进度字节、不存业务单据状态；审批的层级与时长是注入的策略，不写进 workflow 定义。

**第一版动作域（ERP）的形状**，属于动作域、不属于底座：

```
自然语言意图 → 结构化参数 → 契约校验 → 权限判定 → （写动作）挂起审批
             → 执行 → 幂等收口 → 轨迹落库 → 结果 / 外部单号
```

- **入口是任务，不是聊天框**：用户要的是「这张单到哪一步」「建一张草稿采购单」，不是一段建议。
- **知识层仍是底座能力，但不是主线**：v1 的知识库问答降为 F8 的一个只读工具（F3 冻结声明）；主数据与文档片段是两套索引，交易数据实时查 ERP，不灌进向量库。
- **两个进程，状态只在一处**：C# 主服务是唯一对外入口、唯一状态持有者、唯一 PDP；Python 侧进程只提供 `/retrieve` `/embed` `/ingest` `/execute` 四个无状态内部端点（ADR 0013）。
- **ERP 衔接器只做协议翻译**：不生成幂等键、不做业务判断、不做重试决策、不记住执行结果。

### 1.3 这个定义排除了什么

边界靠「不是什么」才立得住：

| 排除 | 含义 | 为什么 |
|---|---|---|
| **不是聊天机器人** | 不承诺「答得像人」；查询与写动作必须落到真实数据或真实单据 | 一段看似合理的业务建议在 ERP 里没有价值，还可能诱导人照着做 |
| **不是一套写死的 ERP 逻辑** | 底座五层不得出现采购单、供应商、金额阈值、审批人角色等业务概念 | 写死一次，换域时权限、审计、轨迹全部要重做（ADR 0017） |
| **不是 Agent 平台** | 不做可视化编排、插件市场、多租户 agent 实例、动态人格等**交付形态** | 没有第一个真实动作之前，平台化只会生产「可被自己验收的东西」。**「底座可换域」≠ 平台化**：第一版不实现第二个真实域，只做一次假动作集演练 |
| **不是 ERP 本身** | 不建单据模型、不定义审批层级、不改业务口径 | 单据状态机属于 ERP；本产品只读取状态、按契约发起动作 |
| **不是 RAG 产品** | 检索是底座能力，不是产品；答案质量（HitRate / MRR / 引用角标）不再是成功目标 | v1 的判据对象换了，不能整表继承 |
| **不是对外 SaaS** | 私有化部署、无公开注册、无计费 | 与 v1 相同，这条没变 |
| **不是 BPM 工作流引擎** | 工作流只用于挂起 → 人批 → 恢复与断点续跑，不给用户画流程图 | 编排是运行时机制，不是交付给用户的编排能力 |

### 1.4 差异化在哪

> **通用 Agent 框架能给循环与工具协议，通用 AI 能给一段看似合理的业务建议；但都不替企业回答「这次动作在授权范围内吗、只执行了一次吗、办错了能追回吗」，也不保证换一个业务域时这些保证仍然成立。**

价值 = **能执行 + 管得住 + 查得清**：

- 「能执行」是入场券；
- 「管得住」= 调用前拦截 + fail-closed 审批 + 由动作域注入的权限策略（业务对象 × 操作 × 数据范围 × 金额阈值）；
- 「查得清」= 幂等键、去重表、审计事件、`request_id` 贯穿、外部单号回写。

**业务语义集中在一处**是第四项、对工程的价值：接入第二个系统时不必重做权限与审计——但它不是第一版对客户的卖点，别拿它当扩范围的理由。

模型只负责把自然语言翻成参数，**难点全部在模型之外**——这也决定了下面范围的写法。

### 1.5 关于 v1 §5.2 那条「ERP 连接器不做」

v1 排除的是「把 ERP 当**外部知识来源**同步进来」，理由写得很准：*每接一个来源 = 一套授权 + 增量同步 + 来源侧权限映射*。**本文没有推翻它**。

第一动作域做的是另一件事：**把 ERP 当动作目标实时调用**，不同步数据、不做增量。但 v1 那三条理由一条都没躲掉，反而更重——实时调用还要再加事务、幂等、审批、对账。所以不是「改主意了」，是**换了一个更难的对象**；v1 的排除条款继续对「知识源连接器」有效。

## 2. 目标用户与部署形态

### 2.1 三类用户

| 用户 | 关心什么 | 与 v1 的差别 |
|---|---|---|
| **业务操作员** | 查单据状态、发起一个受控动作 | v1 是「查知识」，这里是「触发动作」 |
| **审批人** | 确认写动作、拒绝并留理由、超时后接管 | **v1 没有这个角色** |
| **系统管理员 / 部署维护** | 工具白名单、**动作域策略与适配器配置**、凭据、审计查询、备份恢复 | v1 的「知识库元数据管理」退居次要 |

同一个人可以兼任多职，但职责边界要分开写——权限与验收标准不同。

### 2.2 部署形态

私有化、服务端、单核同进程：**企业应用层的核（PDP / 票据 / 权限元数据）不与 Agent 运行时分进程**，可独立托管的只有后台 UI 与静态资源（壳）。理由见 ADR 0013 §一「三个唯一」与 `docs/功能/F1-身份与访问.md` 头部声明。

注意：这里的「企业应用层」是**业务侧**的一部分，但它与运行时同进程——**业务语义边界与进程边界正交**，不冲突（ADR 0017 §五）。

### 2.3 第一版面向谁（这里必须诚实）

**第一版没有真实客户，验证对象是开源 ERP（ERPNext / Odoo）默认单据模型 + 一套可替换的适配器。** 它是**第一个动作域**，不是产品的边界。

- 选它的理由不是省事，是**契约由外部设计、不迁就我们**：采购单 → 收货 → 发票 → 付款的状态机、字段校验、权限颗粒度都是别人定的，会暴露自己想破头也想不到的问题。
- 纯 mock 不算验证——契约自己编、验证的是想象，会重演 D5「没有第二台干净机器」那个坑。

### 2.4 不面向谁

个人用户、公众、超大规模组织（无部门树 / 组织树）、多租户 SaaS 运营。

## 3. 核心价值

| # | 价值 | 具体含义 | 对应判据 |
|---|---|---|---|
| 1 | **动作可执行** | 自然语言能变成一次合法的调用并拿到外部单号 | F8 REQ-ERP-01 / 04 |
| 2 | **不越权** | 调用发出前过白名单 + 参数校验 + 权限；非法参数不产生外部调用；数字不由模型计算 | F8 REQ-ERP-01 / 02 / 03 |
| 3 | **不重复** | 幂等键与 `request_id` 同源；超时只查证、不重放 | F9 REQ-SAFE-01 / 03 |
| 4 | **可追责** | 意图、参数、审批人、结果、外部单号五字段齐全 | F9 REQ-SAFE-04 |
| 5 | **可恢复** | 挂起 → 人批 → 恢复；Checkpoint 续跑不重复执行副作用 | F9 REQ-SAFE-02 / 03、ADR 0016 R4 |

第 2、3、4 条是差异化，第 1 条是入场券，第 5 条是长任务前提。

> 另有一条**对工程的约束**，不列入对客户的价值表：**底座不认识业务**（ADR 0017）。它决定上面五条在换域后仍然成立；把它写进价值表，会诱导第一版去实现第二个动作域。

## 4. 第一版成功目标

### 4.1 要证明什么

> **在一个由外部设计的单据模型上，系统能可靠执行 1 个只读动作 + 1 个带人工审批的写动作，且不越权、不重复、能追回；同时证明这些保证没有被写死在底座里。**

拆成六句可检验的话（每条都能写出反例）：

1. 用 ERPNext 的真实 API 查到单据状态，返回带 ERP 状态码与时间戳；查不到时明确说查不到（不是 mock 返回值）。
2. 建一张草稿采购单，**未审批时零外部调用**；拒绝与超时过期都不执行。
3. 同一 `request_id` 连打两次，ERP 侧只有一张单，第二次返回首次结果。
4. 模拟超时，系统记「执行中」并发起状态查询，**不重放调用**；查不到转人工。
5. 任取一笔执行，五个字段齐全，能回答「谁在什么时候让系统做了什么」。
6. 用一个字段、策略、题库都不同的**假第二动作集**跑通同一套运行时，**底座五层 diff 为空**（ADR 0017 AC-01）。这是轻量演练，**不实现第二个真实域**。

**第一批判据只 5 条运行时（RR-1~RR-5）+ 8 条动作（F8/F9）+ 2 条边界（AC-01 / AC-02）**，不铺开。第 6 句不为证明第二域可用，只为证明边界。

### 4.2 不证明什么（这一节比 4.1 更重要）

- **不证明有客户要、不证明业务口径对**：物料编码、税码、单位、成本口径每家不同，必须等真实客户。
- **不证明能对接任意 ERP 或任意动作域**：只证明适配器接口可替换；每家系统仍要一套字段与权限映射。
- **不证明底座能单独作为产品交付**：对外交付的是「底座 + 动作域」的完整系统。
- **不证明模型 tool calling 稳定**：那是前提，不通过就换模型，不算成果。
- **不证明平台化交付形态成立**（可视化编排 / 插件市场 / 多租户实例），也不证明答案质量（那是 v1 的对象）。
- **功能数量、测试覆盖率、绿灯数量、文档篇数一律不是成功标准。**

> **开源 ERP 跑通 ≠ 真实客户可用。** 差异集中在三处：字段与口径、真实权限模型、异常分支。把 demo 跑通当成可以交付，就是自证。

### 4.3 与 v1 最重的差别：反馈源换了吗

v1 的成功标准是「有人真的用起来了」——需要真实用户，而环境里拿不到，于是唯一稳定可得的反馈变成绿灯，闭环退化成**自己写需求、自己实现、自己验收、自己判结论**（v1 最终留下 23 篇文档 / 113 条判据，对应 2 条会话 / 6 条消息）。

v2 把反馈源换成「**外部设计的单据模型不迁就我们**」：它不依赖客户，但也不是自己编的。**这一步能堵住绿灯自证，堵不住「有没有人要」**——后者仍然判不了，必须如实挂着，不能靠再补一轮文档填。

「底座业务无关」**没有拓宽反馈源**：它改变的是内部结构，验证对象仍是同一个外部单据模型。AC-01 的假动作集是**内部边界检查**，不是第二个外部反馈源。

## 5. 第一版范围

### 5.1 必须实现（最小闭合，按两层分列，不铺）

**A. 底座（业务无关，一次建好；换域不改）**

| 范围项 | 归属 | 依据 |
|---|---|---|
| Agent 运行时五条不变量（可停 / 可拦 / 可回放 / 可恢复 / 不自作主张） | C#（MAF 1.23.0） | ADR 0014 / 0016 |
| 编排 / 知识 / 记忆与状态 / 工程保障 四层的底座侧能力 | C# 为主，无状态计算可交 Python | 附录 C |
| 工具层·管辖半边：白名单、JSON Schema、参数校验、权限前移、幂等键、去重表、审计落库 | C# `ToolExecution` | ADR 0017 §二 |
| 三个注入口（端口定义，**不含业务实现**）与五字段错误信封 + `request_id` | C# | ADR 0017 §三、0015 §3.3 |
| 禁词扫描（AC-02）：扫类型名 / 字段名 / 方法名，注释不算 | CI | ADR 0017 §六 |

**B. 第一动作域（ERP，可替换；换域只换这一组）**

| 范围项 | 归属 | 依据 |
|---|---|---|
| 企业应用层策略：唯一 PDP、权限四维、金额阈值、审批层级、字段映射 | C# | 附录 C |
| `ActionSpec` 声明 + **1 个只读动作 + 1 个写动作（强制人工审批）** | C# 管辖 / Python 执行 | F8 / F9 |
| 四个无状态内部端点与 ERP 衔接器（协议翻译） | Python | ADR 0013 §三·附 |
| 文档 / 主数据两套索引、检索契约评测的**执行** | Python | 附录 C |
| 动作正确性评测题库 + 动作回归清单（查询 / 写入 / 重复提交 / 超时 / 审批拒绝 / 审批超时） | 判据归动作域、执行可交 Python | 附录 C |

**审批的人机入口要写清**：第一版不重写 `web/` 前端（ADR 0015 §六），但「人点确认」是写动作的必经环节，不能省。做法是 **API + 一个够点一下的最小内部页面**，不做完整管理后台。这一条不写死，实施时会出现「审批挂起了却没人能批」的断点。

### 5.2 后续版本（带重开条件，不是「以后再说」）

| 范围项 | 重开条件 |
|---|---|
| **第二个真实动作域** → 只新增适配器与策略，**不动底座**，不重开 ADR 0017 | 出现第二个真实集成对象 |
| 真实客户的字段映射、权限模型、异常分支 | 有真实环境与业务专家 |
| 长期记忆 | 有真实使用数据、能定义「什么算记错」（记错会持续犯错） |
| 通用对话、可视化编排、插件市场 | 见 ADR 0016 §五 B/C，各有独立条件 |
| 完整前端 / 管理后台 | 第一个真实使用者出现之后 |

### 5.3 明确不做（每条都有理由，不写「暂不支持」）

| 不做 | 理由 | 出处 |
|---|---|---|
| **把业务概念写进底座五层** | 写死一次，换域时权限、审计、轨迹全要重做 | ADR 0017 §二、AC-02 |
| **第一版实现第二个真实动作域** | 底座可换域 ≠ 平台化；只做一次假动作集演练 | §1.3 / §4.1 |
| 多 agent / 自主规划 / 任务分解 | 两个 agent 争调度权，R1 / R3 立刻破 | ADR 0016 B1 |
| **自动重放带副作用的工具调用** | 超时后状态未知，重试可能建两张单。**模型请求的重试不放弃**（无外部副作用） | B2 / F9-03 |
| 并行工具调用、模型自行计算数字、运行时动态发现工具 | 审批、幂等、轨迹需要确定次序；数字必须来自真实表；工具集须可审计 | B3 / B4 / B5 |
| 自动执行写动作、长期记忆、智能上下文压缩 | 写默认 `Ask` + fail-closed；记错会持续犯错；压缩改写历史，与 R3 冲突 | B6 / B7 / B8 |
| 可视化编排 / 插件市场 / 动态人格 / 通用对话 | 平台化**交付形态**与闲聊入口，第一版无反馈源 | C 组、F7 停用 |
| 公开注册、部门树、逐文档 ACL | 与 v1 相同；权限第一版到业务对象级，不引入组织维度 | v1 §6 依据 3 |
| 把 ERP 当知识源做增量同步 | v1 §5.2 的排除条款继续有效 | §1.5 |

> **放弃 ≠ 容忍缺陷。** 工具重名静默保留第一个是 fail-open，必须改成启动即失败；参数留痕把 `0` 存成 `"0"` 丢了类型，必须存原始 JSON（ADR 0016 §七）。这两条是必修缺陷，不在放弃清单里。

### 5.4 前提（不属于范围，但不满足则整条路不成立）

1. **C# 侧模型 tool calling 实测**（`ModelRuntime` 接 `glm-4-flash`）——第一个可证伪点。
2. **一个能真连的 ERP 实例**——ERPNext / Odoo 自托管，自带 demo 数据与默认流程。
3. **目标 ERP 有没有幂等能力 / 能否按外部单号查状态**——有与没有是两套架构，不能假设。
4. **真实客户业务口径延后**——没有业务专家，先把接口、状态机、幂等、审计做对。

## 6. 范围判定的五条依据

1. **动作正确性 > 功能齐全**：1 只读 + 1 写能跑通，比十个工具都停在 mock 上有信息量。
2. **状态只在一处**：C# 负责「决定」（能不能 / 做不做 / 记不记 / 算不算数），Python 负责「算」（解析 / 切块 / 向量 / 检索 / 翻译 / 跑题）。四条充要条件见附录 C：不读身份、不写业务状态、给定输入同一输出、不自行记住幂等结果。
3. **业务语义只在一处**：底座只定义端口，动作域实现并注入（ADR 0017）。与第 2 条正交——前者管**业务概念落在哪**，后者管**状态落在哪**。
4. **反馈源必须不迁就我们**：外部单据模型 > mock > 绿灯。排序不能倒过来；AC-01 是内部边界检查，不算新的外部反馈源。
5. **判据跟着对象走，不跟着文档走**：v1 最贵的教训不是「验证做得不好」，是「验证做得太早、太多、对象还没确定」。所以第一批只 5 + 8 + 2 条，且每条能写出反例；**表结构（对象）在前，判据（结论）在后**。
