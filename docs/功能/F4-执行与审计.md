# F4 Agent 执行与可审计

> **口径（2026-11-06，已冻结）**：本文描述**单进程 Python 版（v1.x）**的功能口径，不再修订。
> 本域归 **C# 主服务**。**注意对象**：F4 管的是「**一次作答**的记录必须真实」，
> 不是「**一个动作**必须安全」——后者是 ADR 0015 新增的 **F9（审批与执行保障）**。
> 两者刻意分开：把幂等、审批、对账塞进 F4，会让「记录必须真实」这条判据失去清晰边界。
> **现行归属正本**：`docs/架构/能力矩阵-七层填空.md` 附录 C（整层 C#，一项不交）；
> 运行时五条不变量与主动放弃清单见 ADR 0016，其中 **R3 可回放**正是本域「记录必须真实」的运行时表述。
> 本文引用的验证编号随 113 条台账一并冻结，**不得再作为新产品的判据**。

需求出处：`docs/需求/功能需求.md` §5（REQ-11 / 12 / 13 / 16），外加一条它们合起来才成立的隐含要求：**没有绕过记录的路径**。

一句话：**每一次作答都在库里留下一行可核对的事实——存在、完整、不矛盾，且没有任何一条路能绕开它。**

本文只写"这个域应该是什么样"。**Python 侧现状（2026-11-02 核对）**：`core/runs.py` 已实现——`RunStatus` 六值、迁移白名单、九个原因码、`require_transition()`，`tests/invariants/test_run_state.py` 八条测试在跑；但 `trace/recorder.py`、`db/repositories/runs.py` 仍是十行骨架，**`agent_runs` / `agent_steps` 两张表在 `SCHEMA_SQL` 里不存在**。所以第四节里，状态机那部分（V3、V4）是"半通"，其余仍是"未验"——不是"通过"。C# 版的具体事实只当依据用，不当结论抄——它的文档与代码有几处对不上（见 1.6、1.7），照抄会把旧错误一起搬过来。

### 一、这个域要实现什么（标 REQ 编号，写"给谁用/解决什么/不满足会怎样"）

#### 1.1 给谁用

| 谁 | 什么时候会用到 | 不满足时他会怎么样 |
|---|---|---|
| 企业管理员 / 部署维护人员 | 客户问"这个答案凭什么"、"上周三那次为什么错" | 只能再问一遍猜；猜出来的不是当时那次 |
| 提问的成员 | 答案可疑，想知道系统到底查了什么、模型看没看 | 只有"信"和"不信"两个选项。F3 的"可核"核的是原文，本域核的是过程，两件事 |
| 客户 / 合规 | 要求证明"没有人能在不留痕的情况下用这套系统查资料" | 无法证明。**"没有记录"与"没发生过"不可区分** |

#### 1.2 解决什么：四条 REQ，一条隐含

| REQ | 要求 | 判据（库里应能看到什么） | 不满足会怎样 |
|---|---|---|---|
| **REQ-11** | 每次执行一行：唯一标识、执行者、所属团队、输入、状态、最终结果 | 一次提问 → 恰好一行 run；`user_id` / `tenant_id` 与调用者一致 | 记录无法归属。"谁问的、哪个团队的"答不上，越权排查与追责同时失效 |
| **REQ-12** | 关键步骤如实：检索证据、工具调用及输入输出、状态变化、错误 | 步骤与真实调用一一对应；**失败的在，没发生的不在** | 看得到结论、看不到路径。排查退化成"再问一次看看" |
| **REQ-13** | 至少五种状态：运行中 / 成功 / 失败 / 已取消 / 达到限制后终止 | 开始时就有 `running` 行；终态取值可数、可枚举 | 取消、超限、故障全叫"失败"。"要不要重试"判断不了 |
| **REQ-16** | 可停止；**不得把"收到停止请求"当成"已经停止"** | 终态说得出实际停在哪一步 | 界面说"已停止"，后台又跑了两轮，用户按错的结论办事 |
| **隐含** | 每条作答路径都留痕 | 路由表逐条声明，无未声明端点 | 上面四条只对"我们记得的路径"成立 |

隐含那条不是新需求，是四条合并后的必要条件。它没写在 REQ 里，因为写"每条路径"没法验收——只能换成"遍历路由表，逐条表态"，那是一个测试，不是一句需求。

**REQ-12 的证据快照必须带 `kb_id`。** 否则 F5 读取历史时无法判断“这条证据来自哪个知识库、当前账号还能不能看”，只能要么全放、要么全删——前者越权，后者把合法历史也一起抹掉。证据快照记录的是当时的命中，不随等级变化重写；过滤发生在读侧（F5 §1.11）。

#### 1.3 一个功能，四条不变量

判据只有一条：**去掉其中一条，另外三条的判据会不会失效。** 会 → 是不变量，不是四个功能。

| 不变量 | 对应 | 去掉之后 |
|---|---|---|
| **有** | REQ-11 | "全、对、无后门"没有对象 |
| **全** | REQ-12 | "有"只剩一行空壳：能说"跑过"，说不出"跑成什么样" |
| **对** | REQ-13、REQ-16 | 记录会被当成证据，而它自相矛盾——**比没有记录更糟** |
| **无后门** | 隐含 | 前三条只对已知路径成立，审计链在没人走过的那条路上断掉 |

**没有"做完三条"这种算法。** 写成并列的四条，是为了分开验收，不是为了可以分批交付。

#### 1.4 本域只负责"写"

| | 本域（F4） | F5 |
|---|---|---|
| 验什么 | 库里有没有这一行，这一行是不是真的 | 能不能看到，看到的是不是当时那次 |
| 主要模块 | `trace/recorder.py`（唯一写入口） | `trace/reader.py`、会话与消息 |
| 需求 | REQ-11 / 12 / 13 / 16 | REQ-04 / 14 / 15 / 21 |

切开不是为对称，是因为验收对象不同：本域一条 SQL 就能判，F5 要过界面和权限。混在一起时，"写漏了"和"读越权了"会落在同一条验收上，红了说不清是哪边。

**写入口的形状由分层决定。** `pyproject.toml` 的 layers 里 `trace` 与 `rag` 同层、位于 `agent` / `chat` / `api` 之下，所以 `trace` 不能 import 它们。结论：recorder 的入参只能是 `core` 里的纯数据（run 标识、步骤种类、工具名、参数、结果、错误），不能是 `rag` 的命中类型或 `agent` 的运行结果——上层自己翻译，反向依赖自然没有。

同一理由：**`db/repositories/runs.py` 不许给上层直接用。** 只要 api 能直接 INSERT，"唯一写入口"就只是约定，不是事实。

#### 1.5 三条最容易做错的地方

| 判断 | 常见做法（错的） | 后果 |
|---|---|---|
| **"记录"不等于"审计"** | 每条已知路径都调用了 recorder，就算做完了 | 只要有一条路没写，剩下的记录**无法证明"没被记录的操作不存在"**。差的是一个数量级的工作量 |
| **状态机比状态列表重要** | 定义五个常量，谁都能改，没有迁移规则 | `succeeded` 之后再写步骤、`cancelled` 变成 `succeeded`、`failed` 之后追加成功步骤——记录**自相矛盾，却会被当成证据** |
| **"收到停止请求"不等于"已经停止"** | 收到取消就把终态写成 `cancelled` | 已发出的模型调用撤不回来。终态成了"请求的复述"，不是"事实的复述" |

前两条的口径来自 `功能需求.md` §5.4；第三条的依据是 REQ-16 原文，加上 C# 的实证：取消时 harness 的失败事件常常送不进来，终态只能在 hub 里补发（`AgentHub.cs:207-211`）。补发出去的是界面，不是库里那一行。

#### 1.6 无后门是可验证的

判据一句：**遍历路由表，逐条断言"这个端点会不会产出 run"。**

| 结论 | 含义 | 要求 |
|---|---|---|
| 产出 | 会启动一次作答或一次模型调用 | 必须经过唯一写入口 |
| 不产出 | 只读、只改配置、只上传 | 必须在声明表里写明理由（例：只读检索不生成答案） |
| 待定 | 作者说不清 | 不许合并，不许"先这样" |

C# 版的这张表大致长这样（路径相对 `D:/Code/AgentWorkbench`）：

| 端点 | 产出 run？ | 说明 |
|---|---|---|
| `POST /api/harness/run` | 是 | 同步作答入口 |
| `POST /api/knowledge/retrieve` | 否 | 只返回检索命中，不生成答案、不调模型 |
| `POST /api/workflow/runs` | **另一套** | 写 `workflow_runs`（M019），不是 `agent_runs`。两套运行必须各自证明无绕过 |
| 其余 CRUD | 否 | 不产生模型调用 |

**事故：** C# 曾经有 `POST /api/knowledge/ask`，走独立链路——内部检索两次、不写 run、引用格式不同。**记录机制其实是齐的**，缺的是"还有没有别的路"这一问。用户实际在用的那条路没有轨迹，评测一条都覆盖不到。

**现在：** 该端点已从 `KnowledgeController` 删除，AgentHub 的两条入口（`Send` / `Ask`）合并到同一条 harness。

**但：** `功能需求.md` §10 与 `阶段1功能需求.md` 3.5 仍把它记为"现存缺口"——修好了，没人回写。这正是"靠人记得"失效的实证：**"修好了"和"查过了"是两件事。** 删掉一个端点，不证明其他路径都留痕。把这件事交给一条遍历路由表的测试，新增路由时它会自动要求作者表态。

**F7 的通用对话是第二种作答入口。** 实现后必须把它登记为“产出 run”的路由：通用回答同样要有一行 `running` → 终态、一条 assistant 占位/回填行，归属与会话一致。区别只在**步骤内容**：通用 run 没有检索/证据步骤，也不得为了“看起来完整”伪造这些步骤；它的状态机仍是同一条 `run_lifecycle`，不会进入 `refused`。

#### 1.7 起点：C# 版留下的六个事实

| # | 事实 | 依据 | 对 Python 版的约束 |
|---|---|---|---|
| 1 | 只有终态行，**从来没有 `running` 行** | `ExecutionTraceStore` 一次写 run + steps，`CreatedAt = FinishedAt`；仓储只有 Insert，没有 Update | 必须开始时先写 `running`。否则进程被杀的轮次"没有记录"，而"没有记录"与"没发生过"不可区分 |
| 2 | `status` 有库默认值 `'succeeded'` | `M014_CreateAgentRuns.cs:14` | 漏传状态会变成"成功"。默认值必须去掉 |
| 3 | 无执行者、无团队列 | `M014` 只有 `session_id` | REQ-11 要求归属。两列必须非空，不许事后补 |
| 4 | 落库失败只 `LogWarning` | `AgentHarnessService.cs:430-442` | 记录没了，用户仍拿到答案，事后无法证明这次运行存在 |
| 5 | 终态有**两个来源** | harness 写库；hub 在 `OperationCanceledException` 里补发 UI 终态（`AgentHub.cs:207-211`，注释写着"终态要在这里补发一次"） | 终态只能有一个写入者。两个来源必然出现"库里 `running`、界面 `cancelled`" |
| 6 | 同一事实两列都能回答 | `status` 与 `code` 都定义了 `iteration_limit` / `budget_exceeded` / `loop_detected` | 一条事实只许一个落点，否则两列迟早互相打脸 |

#### 1.8 状态只有一种形状

状态取值、迁移白名单、原因码在 `core/runs.py`（`RunStatus` / `ALLOWED_TRANSITIONS` / `RunReasonCode`）。
`tests/invariants/test_run_state.py` 守着三条规则：只有 `running` 能迁移、终态是吸收态、重复 `finish` 抛错。

代码接管了"是什么"，这里只留它表达不了的两条：

- **`refused` 必须独立**，不能并进 `succeeded`：并进去会把拒答统计成"已回答"，同时污染误拒率与无出处句比例。
- **五种是 REQ-13 的下界**，不是上限。加状态必须同时加一条迁移边，否则只是加了一个没人管的常量。

REQ-12 里的"关键状态变化"**不另造一条步骤**：开始时刻、结束时刻、终态、原因码已经在 run 行上。同一事实写两处，两处迟早不一致。

**状态说"以什么结束"，原因码说"为什么"**，同一件事不许两列都写。

**不按链路形状预设步数。** 上游是一条固定链路还是带工具循环，本域都不管：步骤表只记实际发生的调用，不预填空位。预填会让"没有发生的步骤"看起来像发生过（REQ-12 明令禁止），也会在链路一改时静默错位。

#### 1.9 功能流程与子问题对账

| 不变量 | 子问题数 | 明细 | 本文的职责 |
|---|---|---|---|
| 有 | 3 | V5、V8、V11 | 只做"位置 ↔ 子问题"对账 |
| 全 | 4 | V7、V10、H1、H2 | 同上 |
| 对 | 4 | V3、V4、V6、V9 | 同上 |
| 无后门 | 3 | V1、V1b、V2 | 同上 |

共 14 条（含 2 条需人工）；另有 3 条"写不出反例"的不算子问题（见 4.4）。

拆法规则与 F3 §1.7 相同：**列出会出现什么坏结果**。本域有一处必须改写这条规则——**有些坏结果用户当场看不到**。"缺一步"不会让这次回答变差，只在三个月后有人问"那次为什么错"时才痛。所以判据从"用户看到什么"扩成"**谁在什么时候会因此做错判断**"，否则 V2、V7 这类子问题会因为"用户没感觉"被误判成不重要。

#### 功能流程总表（本域流程的权威，1.2 的 REQ 表只分类，顺序全在这）

**这是 run 的生命周期，不是另一条业务链路。** F3 的十个位置是"一次答问经过哪些环节"（纵向），本域六个位置是"一条记录怎么活下来"（横向）——同一时刻的两个视角，不是两张流程图。

| 位置 | 落在哪步 | 输入 → 输出 | 坏了谁做错判断 | 被哪几条覆盖 |
|---|---|---|---|---|
| **入口判定** | 0，业务开始之前 | `app.routes` 全集 → 逐条"产出 run / 不产出 + 理由" | 新增作答路径没表态 → 审计链断在没人走过的那条路上，**而且当时无人察觉** | 无后门（V1、V1b） |
| **run 开始** | 1 | 调用者 + 团队 + 输入 + 模型与 prompt 版本 → 一行 `running` | 进程被杀那轮库里没有行 → "没有记录"与"没发生过"不可区分 | 有（V5、V8、V11）、对（V9） |
| **步骤追加** | 2 | 每一次真实外部调用 → 一行 step（append-only、序号由写入口分配） | 看得到结论、看不到路径 → 排查退化成"再问一次看看" | 全（V7、V10、H1、H2） |
| **终态收口** | 3 | 实际结局 → 一次终态 + 原因码 | 终态之后再写步骤 / `cancelled → succeeded` → 记录自相矛盾**却被当成证据**，比没有记录更糟 | 对（V3、V4、V9） |
| **停止** | 3 的一条边，贯穿生成段 | 停止请求 + 实际停在哪 → `cancelled`，且"已发出未返回"那一步在库里 | 界面说"已停止"、后台又跑了两轮 → 用户按错的结论办事 | 对（V6） |
| **写入口唯一** | 贯穿全部 | 任何模块想写库 → 只能经 `trace/recorder.py` | 写入点散落 → 上面五格的保证逐条失效，且失效时没有任何告警 | 无后门（V2） |

一条 run 的完整形状（以 F3 的预检索形态为例，其他链路形状同构）：

```
t0  请求到达 → 入口声明表说"这条产出 run"
t1  ├─ 写 running 行（归属 / 输入 / 模型 / prompt 版本）   ← 先写，再干活
t2  ├─ ① 检索 → step 1：证据（命中数 / 距离 / 文件 / 页码）
t3  ├─ ② 判定 → 不成步（D-03：判定是证据的一部分）
t4  │   ├─ 判不足 → 终态 REFUSED + knowledge_insufficient   ← ③④ 不执行
t5  │   └─ 放行 → 继续
t6  ├─ ③ 生成 → step 2：assistant（模型 / token / 耗时）
t7  ├─ ④ 校验 → 不成步（落 run 结果字段：越界数 / 无出处句）
t8  └─ 终态收口（一次，只能从 running 迁出）
```

**哪些成步、哪些不成步，是这张表的用处所在**（这条推论直接决定 recorder 的接口形状）：

| 上游动作 | 成步？ | 落点 | 理由 |
|---|---|---|---|
| 检索 | **是** | step：证据 | 外部真实调用，REQ-12 点名要记 |
| 判定 | 否 | 证据步的字段 + 拒答时终态 | 它是检索的产物（D-03）；1.8「关键状态变化不另造步骤」 |
| 否决 | 否 | 终态 `refused` + 原因码 | **没有产生任何调用**——REQ-12 明令不得伪造 |
| 生成 | **是** | step：assistant | 外部真实调用 |
| 引用校验 | 否 | run 结果字段 | 后处理，不是调用 |

推论一句话：**`record_step()` 只接受"真实发生过外部调用"的步骤种类。** 给判定和校验各造一行，V7（步骤数 == 假客户端的实际调用数）就永远红——而它是本域唯一能抓住"伪造步骤"的断言。

#### 开发语义与顺序

每个位置是一个开发单元，**完成的定义 = 挂在上面的子问题升"通"**——"run 开始做完"不是"表建好了"，是 V5 + V8 + V9 + V11 通过。

**顺序不能按 V 编号推。** V1 在业务开始之前，却必须**最后**做：它断言的是"声明表
覆盖路由全集"，而一条真会产 run 的路由都不存在时，`undeclared` 恒为空集——
断言恒真，加什么表都绿。所以顺序反过来推，从最底层往上：

```
表结构 → 写入口（recorder + 仓储） → run 开始与终态 → 步骤追加
      → 建 ask 端点（一建就进声明表）→ V1 才第一次有真对象
```

V1b（注入假路由必红）必须与 V1 **同一次**做完。分开做的话，V1 从第一天起就是装饰——这正是 V1b 存在的理由。

反面教材就在隔壁：C# 的记录机制其实是齐的，`agent_runs` 有、步骤有、状态有。缺的是"还有没有别的路"这一问——`POST /api/knowledge/ask` 走独立链路、不留 run，而**用户实际在用的就是它**。六格做完五格，剩下那一格正好是客户在用的那条。

### 二、选用什么成熟组件（表格；这一节可以很短——本域大概率没有现成组件，那就要写清"为什么买不到"）

#### 2.1 候选与结论

| 候选 | 能当事实源吗 | 判据 | 结论 |
|---|---|---|---|
| `structlog` / 标准 logging | **否** | 可丢、可采样、没有事务、默认落文件。它回答"当时打印了什么"，不回答"发生过什么" | 只做诊断日志，不进审计链。当前 `dependencies = []`，未引入 |
| OTel + Jaeger / Tempo | **否**（第一版） | 采样即丢；SDK 默认批量上报；私有化客户不允许 trace 出内网 | 不作为产品承诺。运维要接是 F6 / 部署侧的事 |
| 框架自带 tracing | 默认否，待验证 | 见 2.3 的钩子测试 | 只有自己写的那份算 |
| 迁移工具 / ORM | 部分 | 管表结构，不管语义 | 用，但它不承担"无绕过" |
| 关系库 + 事务 | **是** | 同库同事务，才可能"要么都有、要么都没有" | 唯一底座 |
| 商业审计产品 | 买不到 | 见 2.2 | — |

#### 2.2 为什么买不到

市面上的产品分两类：**操作日志**（不认识"一次作答"）、**LLM 观测**（默认采样，只覆盖模型调用，不覆盖检索证据与判定）。本域要的是"每条路都留痕 + 迁移合法"，这是**流程约束**，不是采集能力——采集能买，流程约束只能长在自己代码里。它恰好是差异化本身（`产品目标与范围.md` §1.4"查得清"）：买得到的东西不会是差异化。

#### 2.3 一条判据，用来拒绝所有"框架已经帮我们记了"

> **把框架的 tracing 全部关掉，过程还查得到吗？成立，记录才是你的。**

关掉之后查不到，说明那是框架的调试能力，不是产品承诺：它随版本变、随配置关、随采样丢。而客户问的是"三个月前那次为什么错"。

配套一条：**同一份记录不许有两个写入者。** 框架 trace 与自建记录并存时必须指定谁赢，且只有一个人写库（1.7 第 5 条就是没指定赢家的后果）。

### 三、做什么是加分项（按 加分÷成本 排序，写清为什么加分/成本/风险）

| 序 | 做法 | 为什么加分 | 成本 | 风险 | 结论 |
|---|---|---|---|---|---|
| 1 | **路由表遍历断言 + 自检** | 唯一能证明"没有别的路"的机制；新增路由自动要求作者表态，不靠记性 | 半天（遍历 `app.routes` + 一张声明表） | 0 业务路由时恒真 → **必须自带"注入假路由必红"的自检** | **做，先做** |
| 2 | **迁移白名单，代码从表里读** | 防"看起来有状态、实际自相矛盾"；表是唯一真源，测试只是执行它 | 半天（一张 dict + 一个参数化测试） | 表被抄进文档就会漂移 → 只许存一处 | **做** |
| 3 | **prompt 版本 + 模型标识落库** | 改一次 prompt 能对上"哪批答案变了"；换模型也能对上 | 1 小时（两个字段） | 版本号手填必然忘 → 必须从代码常量取 | **做** |
| 4 | **耗时 + token 落库，缺值写 NULL** | "怎么控成本"必被问；也是"这次为什么慢"的第一现场 | 2 小时 | 供应商不回 usage 时写 0 → 0 会被当真实值统计 | **做** |
| 5 | **步骤 append-only + 单调序号 + 失败独立字段** | 回放顺序不能靠 `created_at`（同毫秒会乱）；失败步在库里就分开，展示层（F5）不用猜 | 2 小时 | 序号必须由写入口分配，不能由调用方传 | **做** |
| 6 | 答案行与 run 行同事务 | 不会出现"有答案、没有 run"，这是"可回放"在存储层的下限 | 1 天（要定谁开事务；`chat` 与 `trace` 同层，跨包事务会破坏分层） | 长事务；事务边界跨包，与 importlinter 的层设计冲突 | **缓**，等 F5 的 REQ-21 一起定 |
| 7 | 记录加密 / 哈希链防篡改 | 能证明"记录没被事后改过" | 3 天 + 改表 | 单机私有化部署里，能改库的人也能改代码，对第一版客户不构成真实威胁 | 不做 |

三项必做不在此表（REQ 已要求，不是加分）：唯一标识与归属、开始时写 `running`、终态如实。

**成本是估的**：按一个人写代码 + 跑通对应用例算，不是实测。它只用来排序，不许当排期依据。

> **一条硬规则：记录的写入失败不是"日志没打上"，是这次回答不该被当成成功。**
> C# 的做法是 catch 之后 `LogWarning`——记录没了，用户仍拿到答案。宁可失败，不可静默。

### 四、验证结果（可自动化/需人工；每条有正控与负控，写不出反例的断言不要写）

#### 4.1 读法

- **状态不在这张表里。** 唯一真源是 `pyproject.toml` 的
  `[[tool.agentworkbench.verification]]`，由 `tests/test_gates.py` 守着（标了"通"
  就必须有真实存在的测试撑着）。这里只写**判据**：怎样算通过、怎样算失败。
  两处各存一份"过没过"，最后一定是文档说未验、代码已经跑了三个月。
- 每条必须成对：**正控**（合法路径必须通过）+ **负控**（把功能改坏必须变红）。写不出负控的，不许进表（见 4.4）。
- "通"必须带范围：函数 / 管道 / 接口 / 端到端 / 人工。

#### 4.2 可自动化

| # | 断言 | 正控 | 负控（必须红） |
|---|---|---|---|
| V1 | 每条会作答的路都产出 run | 声明表覆盖路由全集，逐条标"产出 / 不产出 + 理由"；声明产 run 的路由必须在测试里被打过 | 临时加一条 `POST /api/test/answer` 不声明 → 红 |
| V1b | V1 自身不是恒真 | 注入一条假路由，断言必须报出它；扫描结果必须非空且看得见已知路由 | 删掉遍历循环仍全绿 → **V1 作废** |
| V2 | 写入口唯一 | 只有 `trace` 能 import `db.repositories.runs`；扫描器自带非空自检 | 在 `api` 里加一行 import → 红 |
| V3 | 迁移合法 | `running → cancelled` 通过 | `succeeded` 后 append 步骤 / `cancelled → succeeded` / `failed` 后写成功步 → 全部抛错 |
| V4 | 终态不可二次改写 | 第二次 `finish` 抛错，先前的终态留在库里 | 用"覆盖成最后一次"的写法 → 断言红（先前的终态必须留下） |
| V5 | 崩溃留痕 | 子进程里 `kill` 掉后，库里有 `running` 行（归属与输入都在） | 注释掉"先写 running"那一步、或去掉那次提交 → 库里无行 → 红 |
| V6 | 停止如实 | 假模型客户端阻塞中发停止 → 终态 `cancelled`，且"已发出未返回"的那一步在 | 把"收到请求"直接写成终态 → 步骤少一条 → 红 |
| V7 | 不伪造步骤 | 步骤数 == 假客户端的实际调用数；步骤种类只有检索与生成 | 判定不足的 run 里出现 assistant 步（模型没被调用过）→ 红 |
| V8 | 归属正确 | `run.user_id` / `tenant_id` == 调用者 | 换调用者 → 行必须跟着换；写死常量 → 红 |
| V9 | 漏传状态不得变成成功 | 不传 status → 写库报错 | 给 `status` 列加回默认 `'succeeded'` → 断言红 |
| V10 | 缺值不伪装 | 供应商不回 usage → token 为 NULL | 写成 0 → 红（0 会被统计当真） |
| V11 | 写不进去不算成功 | 注入 DB 写失败 → 该次回答返回错误，或显式标为不可审计 | `except` 之后照常返回成功 → 红 |

#### 4.3 需人工

| # | 验什么 | 正控 | 负控（必须红） | 失效条件 |
|---|---|---|---|---|
| H1 | 一次真实 run 的模型名与 token 与供应商账单对得上 | 取一次 run 的数字，去供应商后台核，对得上 | 手动把 token 改大 10% → 核对必须发现不一致；发现不了说明这个人工项没有判据 | 供应商改名、账单粒度变成按天聚合 |
| H2 | 失败步骤在库里能一眼认出（不靠 F5 界面） | 直接查步骤表：错误字段非空的就是失败步 | 把错误写进结果文本、错误字段留空 → 直接查库就分不出成败，人工项判"不成立" | 字段改名，或失败被写进结果文本 |

#### 4.4 写不出反例，所以不写

| 想写的断言 | 为什么写不出反例 |
|---|---|
| "步骤数 ≥ 1 说明记录完整" | 零工具的成功 run 合法，反例不存在 → 恒真式 |
| "每个 service 都调用了 recorder 说明覆盖全" | 漏掉的那条路径本来就没有调用点，覆盖率查不出它 |
| "字段非空说明记录真实" | 空字符串也非空；编造的内容也非空 |

这三条是本域最容易写成"看起来很严谨"的地方。它们全绿时，坏结果照样发生。

#### 4.5 本域自己的验收句

> 拿一条真实作答，**只查库**：有一行 run、有它的步骤、终态与迁移都合法、每一步都对得上一次真实调用；再拿一条被停止的，终态说得出停在哪一步；最后遍历路由表，没有一条能绕开。

### 五、不做与边界（不做什么、为什么、什么条件下重开）

#### 5.1 不做什么

| 不做 | 为什么 | 什么条件下重开 |
|---|---|---|
| **对模型输出的确定性重放** | LLM 输出不确定。承诺重放 = 承诺无法兑现的事。本域承诺的是"记录可回放" | 供应商能给出可复现的 seed + 固定模型版本 + 零温度，且能证明同输入同输出。在此之前不写这句话 |
| **全链路 APM / OTel 全套** | 内部工具能力，不是产品承诺；采样会丢，且私有化客户不允许 trace 出内网 | 客户要求接入自有观测平台，且书面允许 trace 出内网 |
| **成本核算与计费** | 需要用量表与账期规则，属另一个产品面 | 需要按团队出账单时。前置条件：耗时与 token 已经落库（三·4） |
| **执行记录的无限期在线查询 / 归档** | 保留策略尚无定稿；需求文档引用的《待确认决策.md》在仓库里不存在 | 保留期与归档方式定稿，且有真实数据量 |
| **团队级审计视图（管理员看全员）** | 属 F5，且 REQ-AUTH-05 的边界是"自己有权查看的" | 有客户明确要求且能说清"谁能看谁" |
| **记录导出（PDF / 批量下载）** | 导出把数据带出系统，权限随之失效 | 有受控的导出通道与留痕机制时 |
| **把框架 trace 当事实源** | 钩子测试不成立（二·2.3）：关掉框架 tracing，过程就查不到 | 框架提供可关不掉的、带事务的落库钩子——目前没有 |
| **记录"答得好不好"（评分、满意度）** | 那是 F3 的指标与评测，混进来会让"发生过什么"变成"我觉得怎么样" | 不做。这条没有重开条件 |

#### 5.2 与相邻域的接口

| 邻域 | 它要什么 | 本域给什么 | 本域不给什么 |
|---|---|---|---|
| F3 | 判定 / 拒答发生时，证据先落库再终止 | 证据步 + 终态 `refused` + 原因码 | 不判"够不够"，那是 `guard` |
| F5 | 按 run 读步骤、耗时、终态 | `trace/reader.py` | 不做权限过滤，也不做展示裁剪 |
| F1 | 写入时带团队与用户 | 两列 + 非空约束 | 不判"他能不能看"；REQ-16 的"有权管理"由 F1 判，本域只负责"停止这件事被如实记录" |
| F6 | 按 run 标识查状态 | `run_id` + 状态 + 原因码 | 不做对外契约的版本承诺 |

#### 5.3 边界内的三条硬规则（违反即不成立，不是加分项）

1. **记录写不进去，这次回答不算成功。**
2. **没有发生的步骤不写；发生了的步骤不省，包括失败的。**
3. **终态只写一次，且只能从 `running` 迁移。**

#### 5.4 本文怎么改

| 发现的性质 | 改哪份 |
|---|---|
| 用户能看到的坏结果变了（多一条 / 少一条） | 本文加一条不变量或子问题，**同一次提交里验证文档加一行** |
| 坏结果没变，是实现没做到 | 只改验证状态，本文一个字不动 |
| 选的做法被证伪（例如迁移表被证明防不住） | 写决策记录，本文只留结论 |
| 只是数字变了（阈值、条数） | 只改验证文档 |
