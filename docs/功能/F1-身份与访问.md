# F1 身份与访问控制 · 功能域

需求出处：`docs/需求/功能需求.md` §2，REQ-AUTH-01~12 与 REQ-01~03，共 15 条。

一句话：**系统能回答“你是谁、你能不能碰这个”，并且在答“不能”时留下能查的证据。**

本文只写**功能**：为什么要这一域、要成立什么、什么永远不许发生。另外三类各归其位：

- **不变量与验证**（5 条不变量、19 条子问题 + 5 条人工）登记在 `pyproject.toml` 的 `[[tool.agentworkbench.verification]]`（`I-V1` ~ `I-V19` 与 `I-H1` ~ `I-H5`），由 `tests/test_gates.py` 守着。本文不抄判据、不记状态。
- **状态机**（账户状态 / 票据生命周期 / 邀请生命周期）登记在 `[[tool.agentworkbench.state_machine]]`，迁移白名单的真源在 `identity/policy.py`。
- **组件选型**登记在 `[[tool.agentworkbench.component]]`。判定原则一条：**这件事在行业里有没有标准形态**——有就用库（口令哈希 pwdlib、随机数与摘要用标准库 `secrets`/`hashlib`、cookie 与 HTTP 接线用 Starlette/FastAPI），没有就不假装用库（本域 15 条里 11 条是"你的表上的访问控制"，任何框架都碰不到）。每条拒绝都带重开条件，由闸门 ④ 强制。

它只回答“能不能”，不回答“看到什么”。会话列表、续聊、轨迹展开属于 F5；本域只规定“别人的会话你不能动”。

**实现按包看**：身份判定、持久化与流程在 `identity/`，请求侧闸门在 `api/`，引导入口在 `scripts/`；包级分工见 `docs/功能/代码规范.md` §一。本域不维护逐文件清单。

### 一、这个域要实现什么（标 REQ 编号）

#### 1.1 十五条需求、十五句判据

| REQ | 要成立的事 | 一句判据 | 不成立时用户看到什么 |
|---|---|---|---|
| **REQ-AUTH-01** | 全站身份闸：除白名单外，一切业务请求先认人 | 无票据访问任一业务接口 → 401；`/health` 与登录入口例外 | 产品退化成公开聊天框，答案没有归属 |
| **REQ-01** | 注册（凭邀请）、登录、登出 | 登录拿到票据；登出后同一票据立刻 401，且票据行 `revoked_at` 非空 | 无法判断“这次操作是谁做的”；登出只是界面跳走，旧票据还能用 |
| **REQ-02** | 初始团队与管理员 | 空库部署后有人能登录、有团队可用 | 装完系统没人能进，只能手工改库 |
| **REQ-03** | 成员可见与邀请 | 管理员能列出成员、发出一次性邀请；对方凭邀请建号并落在该团队 | 加个人得改数据库；每次部署都要找开发者 |
| **REQ-AUTH-02** | 团队隔离 | 一个团队的成员读不到另一个团队的任何数据（文档、会话、轨迹、检索结果） | 私有化部署里跨团队串数据，等于没有租户 |
| **REQ-AUTH-03** | 会话归属 | 只能读、续、删自己的会话；**越权访问不改原数据** | 别人的会话可读可删，且删了查不出是谁 |
| **REQ-AUTH-04** | 知识访问控制 | 检索与答案只用本团队资料；**落点是查询条件，不是系统提示词** | 模型能答出别的团队才有的内容 |
| **REQ-AUTH-05** | 执行记录访问控制 | 轨迹里的输入、证据、工具参数与结果，与会话消息用同一套归属判定 | 轨迹面板成为绕开文档权限的数据出口 |
| **REQ-AUTH-06** | 默认拒绝 | 判不清身份、归属、权限时不给；没有归属的数据行对所有人 404 | 新接口忘加校验时默认开放 |
| **REQ-AUTH-07** | 登录失败限制 | 连续失败达阈值后该账户在设定时长内拒绝登录；到期自动恢复 | 口令可以被慢慢试到对 |
| **REQ-AUTH-08** | 停用与恢复 | 停用后新登录被拒，**已签发会话在约定窗口内失效**；恢复后可再用 | 人走了旧 cookie 还能用到过期 |
| **REQ-AUTH-09** | 凭据变更后会话失效 | 改密后，改密前签发的其他会话在窗口内失效；**发起改密的那条仍可用** | “改密码”只是换个登录口令，不解决泄露 |
| **REQ-AUTH-10** | 成员管理的权限边界 | 不得造出高于自己的角色；不得停用或删除自己 | 管理员可自封超管，或把自己锁在门外 |
| **REQ-AUTH-11** | 首个管理员的最小路径 | 空库启动能按文档走通，**且只走通一次**；首个管理员首次登录必须先改密 | 只能靠开发者手工插一行；或者初始口令永久有效 |
| **REQ-AUTH-12** | 平台级配置的写入口只归这套部署的所有者 | 团队管理员对 `POST /api/settings/providers` 等四个写入口 → 403，且配置一个字节不变；同一请求由所有者发出 → 成功；读接口对两者都可用 | 任何成员加一条供应商就能把全平台的问答导向自己的服务器，答案与检索片段都经他手 |

两条容易被写成“提示词”的地方，落点必须在数据面：

- **REQ-AUTH-04** 的落点是检索查询里的团队条件。提示词是赌注——模型不遵守时链路照常成功；SQL 条件不是。
- **REQ-AUTH-05** 的落点是“按 id 取 run”这一层的判定，不是在展示层删字段。删字段的做法漏一个字段就泄露一次。

#### 1.2 四条贯穿全域的判断

| 判断 | 依据 | 落地形态 |
|---|---|---|
| **默认拒绝** | AUTH-06 | 判定只有一条 allow 出口，其余全部 deny；身份缺失不许回落到“单人模式”或固定租户 |
| **拒绝可观察** | 跨 F1/F5 约定，不写进 REQ | 用户拿到 404，运维拿到一条记录（见 1.3） |
| **越权不写数据** | AUTH-03 | 判定先于事务；仓储没有“不带 owner”的写方法 |
| **只管能不能** | 功能需求 §2.2 注 | 会话列表、续聊、轨迹展开在 F5；本域不提供任何“看什么”的接口 |

#### 1.3 拒绝记录：一条不写进 REQ 的接口约定

越权返回 404（不泄露资源是否存在），**同时必须留下可查的拒绝记录**。只有 404 时，运维回答不了“他是没权限、还是系统坏了、还是这东西本来就不存在”——三种情况的界面完全一样，排查成本差一个数量级。

字段：

| 字段 | 含义 | 约束 |
|---|---|---|
| `event_id` | 主键 | 与 run 的 id 不同源，避免“拒绝也是一次执行”的误读 |
| `occurred_at` | 判定时刻 | 服务器时钟，不用客户端时间 |
| `actor_user_id` | 已识别则填 | 未登录的拒绝也要记，否则“没登录”和“系统坏了”分不开 |
| `tenant_id` | 已识别则填 | 支持按团队排查 |
| `action` | 方法与路由模板 | 不记原始 URL，查询串里可能带敏感值 |
| `resource_kind` / `resource_id` | 被访问对象的类型与**真实 id** | 只进记录，不进响应 |
| `reason_code` | `unauthenticated` / `not_owner` / `not_in_team` / `role_insufficient` / `account_disabled` / `account_locked_out` / `session_expired` / `bootstrap_closed` | 对外文案与它无关：401、403、404 各一种体，都不随原因码变化 |
| `request_id` | 与访问日志同值 | 让“用户报障时间点”能对上一条记录 |

三条硬约束：

1. **先落记录，再返回 404。** 写失败就返回 500，不返回 404——宁可这次请求明确失败，也不要一条没有证据的“不存在”。
2. **只记元数据。** 不记请求体、不记响应体；轨迹里的证据属 F4，不属这里。
3. **不复用 `trace/recorder`。** 它写的是“一次执行里发生了什么”，拒绝发生时没有 run；为拒绝造一条 run 等于把没发生的执行写进审计链（功能需求 §5.2「没有发生的步骤不得伪造」）。身份事件与执行轨迹是两张表、两个读侧，各自只有一个写入口。

**读侧也归本域**（2026-11-04 定）：F5 文档里没有这一块，把读侧挂过去等于这条约定没人负责。本域提供一个**最小只读接口**——按时间范围与原因码列出本团队的拒绝记录，供运维回答“没权限还是坏了”。**不做聚合、不做趋势、不做跨团队视图**：那是团队级审计，2.1 明确不做。

#### 1.4 账户状态：三个正交维度

| 维度 | 取值 | 谁改 | 拦新登录 | 踢已登录会话 |
|---|---|---|---|---|
| 账户状态 `status` | `active` / `disabled` | 团队管理员 | 是 | **是**（吊销该用户全部票据） |
| 失败锁定 `lockout_until` | 空 / 时刻 | 系统，连续失败达阈值 | 是（到期自动恢复） | **否** |
| 凭据版本 `credential_epoch` | 整数 | 本人改密、管理员重置 | 否 | 是（旧版本票据失效；本人改密时保留当前这条） |

合成一个 `enabled` 布尔，会同时丢掉两件事：**谁改的**（管理员手动还是系统自动），**要不要踢下线**。锁定不能踢会话——否则任何人拿别人的邮箱连错几次密码，就能把对方挤下线，这是一条可预测的 DoS。

票据用 Web 框架的标准 cookie 承载：`HttpOnly`（脚本读不到）、`SameSite=Lax`、`Secure` 取值见 1.8 配置表。**跨站请求的防护靠 `SameSite=Lax` 这个浏览器机制，不自己发 CSRF 令牌**——令牌那套要在每一个写入口上盖一个章，漏一个就漏一个入口，而测试很难证明「全都盖了」；浏览器机制不需要谁记得。代价是它不拦同站子域之间，本产品单进程单域名部署，不在射程内；将来做多子域时要重新评估这一条，而不是继续加令牌。

**还有一列不在这张表里：`is_platform_admin`。** 它回答的不是「这个账户还能不能用」，而是「能不能改这套安装」——所以它不进 `ROLE_RANK`，也不参与 AUTH-10 的「不得高于自己」。两根轴混成一根会立刻出错：判定「目标角色高于自己 → 403」时，它会把一个管供应商的人误当成「更高的团队角色」，而那个人在自己的团队里可能只是个普通成员。

**同样不在这张表里的是 `must_change_password`。** 它回答的不是“账户还能不能用”，而是“这次登录之后必须先改口令”。它不影响登录、`status`、`lockout_until`，也不进 `ROLE_RANK`；引导与管理员重置置 1，本人改密清 0。存量账号迁移默认 0，不误伤；只有新引导出来的管理员会被要求改密。

这一列**只能由引导路径产生**（§1.7 第 t5 步），任何接口都不能把它置 1。一旦存在「授予平台所有者」的接口，团队管理员就能把自己升上去——那就又变回「登录了就能改全平台配置」，也就是 REQ-AUTH-12 要关掉的那个洞。

#### 1.5 失效窗口必须是一个配置值

- 窗口是**会话校验结果的缓存时长**，不是票据寿命。窗口是上界，不是固定值。
- 改密、停用在同一事务里改状态，缓存最迟一个窗口后失效。
- 配置为 0 表示不缓存，吊销立即生效；测试用 0 拿确定性，不靠等待。

没有这个数，AUTH-08 / 09 的“约定窗口”无法验收。

#### 1.6 判定顺序与状态码

四步，前一步不过不进下一步。**顺序不能换**：先判归属再判角色，会把“角色不够”变成“资源存在”的信号。

| 序 | 判什么 | 不过时对外 | 记录里的 `reason_code` |
|---|---|---|---|
| 1 | 有没有有效票据 | 401 | `unauthenticated` / `session_expired` |
| 2 | 账户还能不能用 | 401，文案与第 1 步相同 | `account_disabled` / `account_locked_out` |
| 3 | 这个对象属不属于本团队 | 404 | `not_in_team` |
| 4 | 是不是本人的、角色够不够 | 按 id 取 → 404；按动作调管理接口 → 403 | `not_owner` / `role_insufficient` |

第 2 步与第 1 步对外同为 401 且文案相同：停用与锁定不能通过登录或接口响应被外部识别。两条路径的内部原因码分开，是因为运维要能回答“这是管理员停的，还是系统锁的”。

**第 2 步里的锁定只在登录路径上成立。** 受保护请求只判 `status`，不判 `lockout_until`——否则任何人拿别人的邮箱连错几次密码，就能把在线的对方挤下线，成本比猜中密码低得多（§1.4「锁定踢已登录会话 = 否」）。于是同一个原因码有两处会写：登录时是 `account_locked_out`，访问时永远不会是。这不是遗漏，是两条路径判的东西本来就不同。

**停用同理，但结果反过来。** 停用要吊销该用户全部票据（§1.4），于是下一次请求在**第 1 步**就以 `session_expired` 被拒，走不到第 2 步的 `account_disabled`——两者对外同为 401，记录里写的却是「会话过期」。这个差别在 1.3 的读侧是有意义的：它说明**这次拒绝的第一道闸是票据**；「账户被管理员停用了」这个事实在账户行上（`status`），不在这张表里，也不该靠这张表去查。

#### 1.7 业务流程

一次受保护请求（每一跳都不许跳）：

```
t0  请求到达（cookie 里有票据明文，库里只有它的哈希）
t1  ├─ 判定 ①：哈希比对 → 找不到/过期 → 401 + 记 unauthenticated/session_expired
t2  ├─ 判定 ②：账户 status / lockout_until / 票据版本 → 不过 → 401（文案同 ①）+ 记原因
t3  ├─ 判定 ③：资源所在的团队 = 我的团队？ → 不过 → 404 + 记 not_in_team
t4  ├─ 判定 ④：本人 or 角色够？ → 不过 → 404（按 id）/ 403（管理接口）+ 记原因
t5  └─ 放行：返回 Owner(user_id, tenant_id)，此后所有仓储调用都带它
```

登录（唯一的“先于身份”的写入口）：

```
t0  登录请求（email + password）
t1  ├─ 按 email 找账户；**找不到也跑一次假哈希**（否则响应快慢就是账号枚举器）
t2  ├─ 账户 disabled 或锁定未到期 → 与“口令错”同一句话，同一状态码
t3  ├─ 口令错 → 失败计数 +1，达阈值写 lockout_until → 同一句话
t4  ├─ 口令对 → 计数归零，签发票据（明文进 cookie，SHA-256 进库）
t5  └─ 成功登录只进访问日志，**不写拒绝记录表**
```

步 t5 与 1.3 的「拒绝记录」是同一条约定：`I-V4` 的判据写明「一次正常的 200 不产生任何记录」。一旦成功也写，那张表的语义就从「被拒的人」变成「所有人」，而 1.3 存在的全部理由——运维能回答「他是没权限、还是系统坏了、还是东西本来就不存在」——就失效了：三种情况都在表里，等于都没有证据。

**邮箱是全局唯一的，不是团队内唯一。** 登录请求里只有 email + 口令，没有团队上下文（用户不知道自己是第几个团队）。库里若有两行同 email，取哪一行是任意的——那不是「两个团队各有一个账号」，而是「同一个人可能登进别人的团队」，而两个团队各自看都正常。

改密 / 停用 / 邀请建号，三者的共同点：**改状态与吊销票据必须在同一个事务里**，否则会出现“密码已经改了，旧会话还能用一整个窗口”的缝。

| 动作 | 顺序 | 不许发生 |
|---|---|---|
| 改密 | 校验旧口令 → 新哈希 → `credential_epoch + 1` → 吊销其余票据（保留当前这条） | 改完把发起改密的人自己踢下线 |
| 停用 | 置 `status = disabled` → 吊销该用户全部票据（同一事务） | 只拦新登录，旧会话活到过期 |
| 邀请建号 | 校验邀请未用且未过期 → 建号并绑到邀请者的团队 → 标记邀请已用（同一事务） | 同一邀请能用两次；过期邀请仍可建号 |
| 引导 | 库里已有用户 → **非零退出**；没有 → 建团队 + 建管理员（标记首登改密） | 留着可用，变成永久后门；或者初始口令永久有效 |

**首个管理员的初始口令是一次性的。** 引导把 `must_change_password` 置 1；登录仍然成功，但除 `/api/auth/me`、`/api/auth/logout`、`/api/auth/password` 外，业务请求一律 403 `password_change_required`。本人改密成功后清 0；管理员重置也重新置 1。

平台级配置的写（`settings` 四条写入口）：

```
t0  请求到达，先过全局闸门（§1.6 的四步）——不是所有者也要先是个能登录的人
t1  ├─ 认人不过 → 401，与“这条路由不存在”无关
t2  ├─ 是平台所有者？ → 否 → 403 + 记 role_insufficient（动作级，不需要目标）
t3  └─ 写：供应商、模型、embedding 模型；读接口不在这条路上（它们只要登录）
```

为什么用 403 而不是 404：这几条路由是**公开存在**的动作，本来就不该按 id 藏。判的是「你能不能做这件事」，不是「这个资源在不在」——§1.6 那张表里 403 只出现在「按动作调的接口」这一栏。

**为什么它不属于团队管理员。** `providers` / `provider_models` / `system_state` 三张表没有团队列，它们是全平台一份。资源不是团队的，权限就不能落在团队成员身上；第二个团队出现的那天，「A 队管理员改 B 队供应商」会变成一条合法操作，而 B 队毫无察觉。

#### 1.8 配置项（每项都有消费者）

| 配置键 | 初值 | 谁读 | 对应 |
|---|---|---|---|
| `auth.session_invalidate_seconds` | 60 | 会话校验缓存 | AUTH-08 / 09 的“约定窗口”；**语义是最大陈旧度**：配 0 时吊销的下一个请求即 401，配 N 时最多 N 秒后失效 |
| `auth.login_max_failures` | 5 | 失败计数 | AUTH-07 |
| `auth.lockout_seconds` | 900 | 同上 | AUTH-07 |
| `auth.ticket_ttl_hours` | 12 | 票据过期判定 | AUTH-01 |
| `auth.cookie_secure` | `false` | cookie 属性 | 私有化内网多为 http；对外必须改 true |

初值都是定的，不是测的。验收断言“改配置行为跟着变”，不断言这几个数本身。

#### 1.9 界面上的三件事（多一件都属于 F5）

| 界面必须做到 | 不做会怎样 |
|---|---|
| 未登录访问任一页面 → 跳登录页；登录后回到原来那一页 | 用户停在一个「每个请求都 401」的页面上，那看起来像系统坏了，不像「你该登录」 |
| 任一接口回 401 → 清掉本地登录态并跳登录页，带上原地址 | 界面仍然以为自己登录着，于是每个操作各报一次错，而用户会一直重试 |
| 有登出入口 | 换账号、把共用机器交还别人，都只能靠清浏览器数据 |

**首登强制改密必须由界面接住。** 登录返回 `mustChangePassword=true` 时直接进改密页；任一业务接口返回 403 `password_change_required` 时同样跳改密页，但**不清登录态**。改密页要求旧口令 + 两次新口令，成功后回到原地址。

**界面不许自己造身份。** 拿不到 `/api/auth/me` 时不能伪造一个“本机用户”放行——
那会把一次部署错误（反向代理吃掉 `/api/auth/*`）变成一个安静的“所有人都是管理员”，
而界面上一切正常。说不清就说不清，停在登录页比假装登录着好。

**平台配置的写入口在界面上不隐藏**（REQ-AUTH-12）。非所有者看得到「添加供应商」，
点下去得到 403 与一句「这个操作需要更高的权限」。理由是：隐藏只改变观感，
不改变权限；而「藏起来了」很容易被当成「已经防住了」——真正防住的是那四条路由上的
判定。这条与上一条的区别在于**界面上少一个按钮不构成安全措施，而界面上多一个身份构成**。

### 二、不做与边界

#### 2.1 不做

| 不做 | 为什么 | 依据 |
|---|---|---|
| 公开自助注册、自助建团队 | 注册即得管理员，“管理员”就不再是权限边界，AUTH-10 的“不得高于自己”也失去意义 | 产品目标 §1.3；AUTH-11 |
| 团队内文档级 / 部门级 / 岗位级授权 | 三维矩阵，漏一处就漏数据；二维靠一条条件守住 | 产品目标 §6 依据 3 |
| SSO / LDAP / OAuth / 企业微信 | 无 REQ；接外部 IdP 等于多一套账号映射与一份运行依赖 | 功能需求 §2.3 |
| 两因素认证、邮箱确认、邮件服务 | 无 REQ；开了没人验收，等于扩大攻击面 | 功能需求 §2.5 |
| 自助找回密码 | 第一版由管理员重置 | 功能需求 §2.3 |
| 按 IP 的限流与验证码 | 无 REQ；NAT 下按 IP 锁会连坐整个办公网 | 判断，无 REQ |
| 用 403 作越权主响应 | 泄露资源是否存在；只有“按动作调管理接口”用 403 | AUTH-02 / 03 |
| 把拒绝记录塞进 F4 的 run / step | 拒绝不是一次执行，造一条 run 违反「没有发生的步骤不得伪造」 | 功能需求 §5.2 |
| 团队级审计视图（管理员看全员历史、拒绝趋势聚合） | F5 的边界，且会引出“管理员能否读全员对话”这个新问题 | 功能需求 §6.3 |
| 会话列表、续聊、轨迹展开界面 | 本域只判“这份会话归谁”，“看到什么、怎么接着聊”在 F5 | 功能需求 §2.2 注 |
| 每个团队自带供应商与密钥（BYOK） | 今天没有这个需求，而它会改 F2 的根：`providers` 加团队列、embedding 模型与索引配置也要分团队 | 判断，无 REQ；重开条件见 §四 |
| 一个「授予平台所有者」的接口 | 有它等于让团队管理员自封，REQ-AUTH-12 当场失效 | AUTH-12 |

#### 2.2 一处文档冲突与取法

| 文档 | 说法 |
|---|---|
| 功能需求 §2.2 能力 3（REQ-02） | 新用户注册后获得初始团队与管理员身份 |
| 产品目标 §1.3 | 第一版部署在客户环境，不提供公开注册 |

取法：**注册 = 凭一次性邀请建号**（加入邀请者的团队）；首个管理员只由引导路径产生一次，首个团队由该管理员创建。

理由：如果注册即得管理员，管理员就不是权限边界，团队隔离（AUTH-02）也没有对象可隔离。未取的做法（开放注册 + 每人自建团队）同时绕开 AUTH-02 与 AUTH-11。

### 三、存量数据

阶段 1 的数据全部属于一个种子账号。接入本域时先跑引导建团队，再把这些行一次性绑定过去；绑定前它们没有归属，按 AUTH-06 对所有人 404。

```
python scripts/bootstrap_identity.py --email admin@example.com --tenant "我们团队"
python scripts/bind_tenant.py --to t-xxxxxxxx          # 预演：会改多少行、有没有冲突
python scripts/bind_tenant.py --to t-xxxxxxxx --apply  # 真跑
```

**默认是预演**：搬迁类命令里，「先看一眼会发生什么」必须是最省事的那个动作，否则人会直接加 `--apply`。

三条拒绝都发生在写之前：源与目标相同（什么都不会改，却像成功了）、目标团队不存在（绑过去仍然 404，而退出码是 0）、目标团队里已有同一份文件（`documents` 上的 `unique(tenant_id, sha256)` 会整批回滚，而报错只有一行 `UNIQUE constraint failed`）。**冲突不跳过**：跳过的版本让命令报成功，剩下那几行还在旧租户里，没有任何东西会提醒运维。

不做自动绑定：它需要一个默认值，而默认值意味着任何新建团队都可能继承上一批数据——不报错，只让新团队一登录就看见别人的文件。

宁可“数据看不见”（一查就能发现），也不要“所有人可见”（发现不了）。

### 四、什么条件下重开

| 条件 | 重开什么 | 先补什么 |
|---|---|---|
| 客户要求对接企业 IdP | SSO | 先补 REQ 与 AC，再定账号映射与首登绑定规则 |
| 出现真实的文档级授权需求 | 策略引擎（届时再评估 casbin） | 先有权限矩阵，以及“每个入口都测”的预算 |
| 一套部署要服务多个互不相关的团队 | 自助注册与建团队 | 先补邀请限流、配额与滥用处理 |
| 出现真实爆破 | IP / 设备维度限流 | 先解决可信客户端 IP（反向代理信任链），否则锁的是网关 |
| 出现“账户自助注销 / 数据导出”的合规要求 | 账号生命周期 | 先补 REQ 与 AC，再定与 F5 的删除边界 |
| 一个团队要用自己的供应商与密钥（各付各的账） | 供应商下沉到团队（BYOK） | 先补 REQ，再给 `providers` 加团队列、给 embedding 模型与索引配置定“全局还是每团队一份”，最后才是判定 |
| 部署所有者不止一个，且不想共用账号 | 平台所有者的授予与撤销 | 先补 REQ；授予入口必须需要一个“已有的所有者”作见证，且不能是团队管理员 |
