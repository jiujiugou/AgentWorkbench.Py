# F6 服务端能力 · 功能域

需求出处：`docs/需求/功能需求.md` §7（REQ-17 / 18 / 19 / 20 / 22），缺口见同文件 §9。

一句话：**把前端整个删掉，产品仍要能被另一个程序完整用完；并且全平台只认一个模型来源。**

本文只写**功能**：为什么要这一域、要成立什么、什么永远不许发生。另外两类各归其位：

- **不变量与验证**（5 条不变量、10+2 条自动化子问题 + 2 条人工项）登记在 `pyproject.toml`
  的 `[[tool.agentworkbench.verification]]`（`S-V1` ~ `S-V12` + `S-H1`/`S-H2`；文档旧稿的
  `V-1`~`V-10` 与 F2 撞号，登记处换 `S-` 前缀），由 `tests/test_gates.py` 守着。状态机登记在
  同文件的 `[[tool.agentworkbench.state_machine]]`（本域一台：索引同步位；运行状态机归 F4）。
- **实现**住在代码与注释里：错误码表在 `core/errors.py`、HTTP 翻译在 `api/errors.py` 与
  `api/app.py`、供应商解析在 `llm/providers.py`、凭据加密原语在 `db/crypto.py`、
  平台配置表在 `db/engine.py` 的 `PROVIDERS_SCHEMA_SQL`。组件决定见 toml 的
  `[[tool.agentworkbench.component]]`（fastapi / uvicorn / pydantic-settings / structlog /
  sse-starlette / httpx / cryptography）。

### 一、这个域要实现什么（标 REQ 编号）

#### 1.1 五条需求与一句判据

| REQ | 要成立的事 | 一句判据 | 不成立时用户看到什么 |
|---|---|---|---|
| **REQ-17** | 核心能力可只经 HTTP 完成 | 一个 `curl` 脚本走完：登录 → 上传 → 提问 → 取引用 → 查运行 → 查历史，全程不碰浏览器 | 必须开浏览器点一遍，产品变成"网页" |
| **REQ-18** | 按运行标识查状态与已保存结果 | 给定 run id，能查到状态机当前态与已落库的步骤/结果 | 只能盯着屏幕等，断开就再也找不到这次运行 |
| **REQ-19** | 断连不丢任务 | 发起后立刻断开连接，任务仍跑到终态；重连能查到状态与结果 | 关页面即中断，任务"消失" |
| **REQ-20** | 错误明确、稳定、不泄露 | 同一错误两次调用业务码相同；响应体不含凭据、他人数据、堆栈 | 报"服务器错误"，且不知道能不能重试 |
| **REQ-22** | 平台级模型配置全局唯一 | 改一次配置，**所有团队**的下一次问答都走新配置；任何读接口不回传凭据 | 每个团队各答各的，且没人知道用的是哪个模型 |

#### 1.2 为什么这五条是一个域，而不是五个功能

判据用 `00-功能域怎么写.md` §四：**去掉一条，另外几条的判据会不会失效。**

| 去掉 | 谁失效 | 结论 |
|---|---|---|
| REQ-19 | REQ-18 退化成"当前连接内的进度条"；F4 的"记录真实"没有任何证据——记录可能只写了一半 | 是不变量 |
| REQ-20 | REQ-19 的"查状态"查不出区别：任务失败、任务不存在、你无权看，三者返回同一个 500 | 是不变量 |
| REQ-22 | REQ-17 的 `curl` 全流程跑不完：没有模型，问答那步必错，且错得没有解释 | 是不变量 |
| REQ-17 | 其余四条只能靠浏览器验证，"服务端为主"这句退化成口号 | 是不变量 |

**所以本域是"一个功能、五条不变量"，不能做成一条放四条。** 任何一条不成立，产品就退化成"只能在浏览器里用的网站"（`功能需求.md` §7.4）。

#### 1.3 域里有两类不同性质的东西

| 类型 | 包含 | 判据形态 | 失败半径 |
|---|---|---|---|
| **接口属性** | REQ-17、18、19、20 | 调接口、看响应、查库 | 某功能不可用 |
| **平台配置** | REQ-22 | 查配置、比对所有团队是否一致 | **所有人拿到错答案，且不报错** |

两类必须分开验收。混在一起写，会让"断连容忍"和"模型配错"共用一个通过/不通过，最后谁也说不清红的是哪一类。

#### 1.5 REQ-22 的四个缺口与处置

四个缺口来自 `功能需求.md` §7.2 现状栏，其中前三项已在 C# 迁移与仓储里逐条核对过。

| # | 缺口（代码事实） | 后果 | 处置 |
|---|---|---|---|
| ① | `api_key` 库内明文（`M006` 注释原话"P2 再加密"） | 备份文件、`data/*.db` 被拷走即凭据外泄 | 库内加密：密钥只来自环境变量，**缺密钥时启动失败**（明确失败，不静默用明文）。读接口用白名单 DTO，不做"取全字段再删" |
| ② | `is_active = 1` 无库层唯一约束，靠"先全清 0 再置 1"+事务 | 并发或直接 SQL 可造出两行激活；`GetActiveProviderAsync` 取 `Id` 最小的那条，**另一个静默失效** | 加**部分唯一索引**：`UNIQUE (is_active) WHERE is_active = 1`（全表级，没有 tenant 列——平台配置）。事务保留（保证切换原子），索引保证终态 |
| ③ | `provider_models` 缺 `UNIQUE(provider_id, model)` | 同一模型可加两次，设置页出现两行，`is_default` 落在哪行不可预期 | 加唯一索引；**同款缺口还有一处**：`is_default = 1` 也没有唯一约束，同样加部分唯一索引 |
| ④ | 判据④未验证：配置失效时是报错还是静默走默认值 | 配置坏了没人知道，所有人继续拿到错答案 | 先立判据（S-V9），再改代码：删除"无声兜底"，把"未配置/配置不可用"变成显式错误码 |

关于 ④，C# 代码里已经能看到静默路径，不是假设：`ChatClientFactory.ResolveAsync` 在激活供应商**没有模型**时，第 120 行 `model = _fallback.Model`——直接落到配置节的默认值。同理，`ApiKey` 为空仍会构造出 `ChatEndpoint`。Python 版目前同款违规在 `llm/providers.py`：空 `api_key` 被兜底成 `"not-required"` 继续答。这两处正是"配置错了所有答案都错、而且不报错"的具体形状。

#### 1.6 一处容易被忽略的张力：embedding 配置 ≠ chat 配置

| | chat 模型 | embedding 模型 |
|---|---|---|
| 换掉的代价 | 下一次问答即生效 | **索引全部作废**，必须全量重建 |
| 换错的症状 | 答案质量变化，肉眼可见 | 检索返回空，但"可检索"标记照旧——症状与"检索不准"完全一样 |
| 允许的变更方式 | 随时换 | 只允许"换 = 重建"，不提供热切换 |

**处置（写死，不是建议）：**

1. 两组配置**永不合并**为一个"模型配置"对象。落点：chat 是 `providers` / `provider_models` 两张表（解析在 `db/repositories/providers.py`，客户端在 `llm/providers.py`），embedding 是 `system_state` 的两个键；`llm/providers.py` 与 `llm/embeddings.py` 也一直是两个文件，不要为了"统一"合并。
2. 设置接口分成两组命名，**响应体不合并**：chat 走 `/api/settings/providers`（按资源命名），embedding 走 `/api/settings/embedding`；embedding 的 DTO 字段集硬断言为 `{model, indexedModel, stale}`，混入 chat 字段即红（S-V10 负控）。
3. 改 embedding 配置必须把索引标记为"待重建"；在重建完成前，检索接口返回明确错误（`index_stale`），不得返回空列表冒充"资料里没有"。依据同 F2 的 REQ-06：失败不能伪装成"查不到"。
4. 这条要有负控（S-V10）：把 embedding 配置改名而不重建，断言检索报错而不是返回空。

#### 1.7 判据的可执行形状

**REQ-19 的四步（这条是本域的支柱，不能写"要支持断连"）：**

| 步 | 动作 | 断言 | 红了算什么 |
|---|---|---|---|
| 1 | `POST /api/runs`，带问题（202） | 响应立即返回（只有 conversationId），此刻**问题已落库**（会话 + 用户消息）；run 行由后台线程创建，客户端经消息列表的占位行发现 runId（C-V11 的占位 = 发现路径，不发明第四条） | 说明"提交"与"执行"没分开，客户端一断就什么都没有 |
| 2 | 拿到 `run_id` 后**立刻放弃连接** | — | — |
| 3 | 轮询 `GET /api/runs/{id}`（条件等待，不 sleep） | 状态从 `running` 走到 `succeeded`（**不是** `cancelled`） | 任务随连接消失——状态其实在前端，F4 的可审计承诺不成立 |
| 4 | 重连后查状态与结果端点 | 结果正文、用量、终态齐全，answer 与会话历史里那行一致，且与不断连的那次同构 | 断连时记录只写了一半，"记录真实"被破坏 |

配套的代码约束：执行体**不持有** `Request` / 连接对象 / 取消令牌；后台任务必须被一个集合强引用并在退出时移除（裸 `create_task` 会被 GC 静默回收）。反例就在 C# 现状里：`AgentHub.RunAsync` 用 `CreateLinkedTokenSource(Context.ConnectionAborted)`，客户端断开即取消整条 run——把它移植过来，S-V3 必须红。

**REQ-20 的响应结构约定：**

| 字段 | 约束 | 违反后用户看到什么 |
|---|---|---|
| `code` | 稳定枚举，**不随文案变**；一个 code 只对应一个 http_status | 客户端按文案判断，改一次文案全部失效 |
| `http_status` | 与 code 一对一映射，状态行与 body 里都在 | 分不清是"没权限"还是"系统坏了" |
| `retryable` | 布尔，调用方据此决定重试或放弃 | 无限重试打爆上游，或该重试的直接放弃 |
| `message` | 中文、可读、**不含内部细节**；不出现异常原文、SQL、堆栈、文件路径、主机名 | 内网地址与表结构进了浏览器 |
| `request_id` | 可拿去日志里定位同一次请求；响应头 `X-Request-Id` 同值 | 用户报错时运维无从查起 |

**铁律：内部细节只进日志，不进响应。** 判据可执行：异常对象里塞入的哨兵串，必须出现在日志、必须不出现在响应体。三类泄露各一条（S-V5）：①凭据（`api_key` 值）；②其他团队数据（别人的文档名）；③敏感配置（`base_url` 里的内网主机名）。

**REQ-22④ 的三种故障注入**（判据 S-V9）：

| 注入 | 期望 | 禁止 |
|---|---|---|
| 清空激活供应商的 `api_key` | 问答返回 `model_not_configured`，不产生助手消息 | 落到占位串继续答、继续请求上游、返回 401 原文 |
| 删掉该供应商的默认模型、列表也空 | 明确报"未配置模型" | 静默用配置节默认值（C# 现状第 120 行） |
| 供应商 `base_url` 指向不可达地址 | `model_unavailable`，`retryable=true` | 静默用缓存客户端继续答 |

三种注入的共同断言：**假供应商收到 0 个请求**。只断言"返回了 503"不够——一个先发请求再报错的实现也能过；"没发出去"才是"不静默"。

#### 1.8 需人工的两条（S-H1 / S-H2）

| 项 | 判据 | 为什么自动化替代不了 |
|---|---|---|
| 无前端完成首次配置 | 空库 → 按文档用 `curl` 配出供应商与模型 → 完成第一次问答 | 这条路径必须真的走一遍并写进部署文档，否则"删掉前端"只是口号 |
| 日志可查性 | 拿 `request_id` 在日志里还原一次失败：能看到 code、模型、耗时、上游状态；**看不到**凭据 | 日志侧的完整性只能人工核；哨兵测试守的是响应侧 |

#### 1.9 功能流程

```
t0  程序提交（POST /api/runs）→ 202 + run_id（此刻 run 行已落、running）
t1  ├─ 后台执行体拿 run_id 起线程：自己开连接（不持有任何请求对象）
t2  ├─ F3/F4 作答：检索 → 判定 → 生成 → 校验 → 终态
t3  ├─ 客户端任何时候都在：轮询 GET /api/runs/{id}，或（将来）订阅 SSE
t4  └─ 错误路径：任何异常 → { code, http_status, retryable, message, request_id }
       原文只进日志（request_id 可对上同一次请求）
```

**完成的定义**：某个位置做完，是挂在它上面的子问题在 `pyproject.toml` 里从 `partial` 变 `pass`——不是"代码写了"。

#### 1.10 本域的两台"状态机"登记

- **run_lifecycle**（归 F4）：running → 五种终态，真源 `core/runs.py` 的迁移白名单。本域只消费——REQ-19 的"提交与执行分离"是这条状态机的**入口**，不是新状态机。
- **index_sync**（本域）：ready / stale 两位。**位，不是机**：`system_state` 里 `embedding.model`（想要的）与 `embedding.synced`（索引实际用的）两值不同 = stale。stale → ready 只能由"索引重建完成"触发；检索层只读不写——stale 时报错而不是顺手重建，重建是 F2 的重活，不能藏在一次检索里。

#### 1.11 启动与静态托管

一条命令从零到能访问界面：

```
python -m agentworkbench serve [--host H] [--port P] [--dist DIR]
```

**服务进程托管前端构建产物（`web/dist`），前后端同源**——CORS 在这个形态下不生效，那是给 vite dev server（5173 另一个源）用的。

- **SPA 回落**：`/chat`、`/login` 这些前端路由在磁盘上没有对应文件，统一回落到 `index.html`，由前端路由接手。但 `/api/*` 下的未知路径**不回落**——接口的 404 就是 404，回一页 HTML 会把"路径写错"伪装成"请求成功"
- **静态资产不要求登录**：登录页本身需要 js/css 才能加载，"资产先于身份"是刻意的。边界在 API 层（全局闸门），不在资产层
- **`web/dist` 不存在时服务照常启动**（API 可用），日志警告界面不可用——开发态经常没有 dist，托管缺失不该挡住后端调试
- 首次部署顺序：装依赖 → 设 `AWB_SECRET_KEY`（缺了启动即失败）→ `bootstrap_identity.py` 建管理员（只能跑一次）→ `npm run build` → `serve`。建表在装配时幂等完成，新库零手工；**老库**结构变更走 `alembic upgrade head`

#### 1.12 备份与恢复（NFR-08）

MVP 第 4 句的后两件事（「装起来」见 §1.11）。出处 `产品目标与范围.md` §四：

```
python -m agentworkbench backup  --to DIR [--data-dir DIR]   # 热备，服务运行中可做
python -m agentworkbench restore --from DIR [--data-dir DIR] # 停服后执行
```

- **备份目录是自足的**：`agentworkbench.db`（`VACUUM INTO` 一致紧凑副本，单文件无 `-wal` 伴生）+ `files/`（上传原件）。只备库不备文件，恢复出来的是「目录说有、盘上没有」的半套系统
- **热备的语义**：另一连接持有未提交写事务时照常执行——备份看到的是已提交快照，未提交的行不进备份（两条方向都有测试）
- **备份不许覆盖**：`--to` 指向已存在且非空的目录直接拒绝——覆盖写毁掉的是用户最后一份好版本，没有确认兜底
- **恢复先验后动**：quick_check + 关键表存在（`documents`/`users`，能挡住「随便一个 sqlite 文件」）→ 拷到目标目录内的临时文件再验一次 → 原子替换 + 清掉旧库 `-wal`/`-shm` 残留（旧 WAL 对不上新库，留着即损坏）。校验不过时目标一字不动——恢复失败的正确形态是「什么都没发生」
- **换机器恢复必须带同一个 `AWB_SECRET_KEY`**：库里的供应商凭据是 Fernet 密文（S-V6），密钥丢了库完好也等于丢一半。提示印在 CLI 与 README，代码校验不了——密钥对不对只有解密那一刻才知道
- 已知边界：`files/` 恢复是合并拷贝，备份之后删掉的文件恢复不回来（多删不可逆，刻意不删目标多余文件）；定时备份与保留策略归运维 cron，不进产品

### 二、不做与边界

#### 2.1 产品边界（本域永远不做）

| 不做 | 理由 |
|---|---|
| **每团队自带模型供应商（BYOK）** | 会把"一套部署一个模型来源"变成"每个团队各自一份凭据"：运维与排障成本翻倍，凭据分散后无法统一审计。**这是刻意选的全局共享，不是没做**（`功能需求.md` §7.3）——所以 `providers` 表没有 tenant 列 |
| 模型路由 / 多供应商负载均衡 / 故障自动切换 | 第一版只认"当前激活的那一个"。自动切换会让"这次用的是哪个模型"无法回答，直接毁掉 F4 的可审计 |
| 按团队或按用户的用量统计与配额 | 需要用量表（当前没有）。用量表本身不难，难的是"超限后拒答"要和 REQ-09 的拒答区分开，否则两种"不答"混成一团 |
| 公开 SDK（各语言客户端） | 有稳定 HTTP 契约后 SDK 只是包装。先有契约，再谈包装 |
| GraphQL / gRPC | REST 够用。多一套协议 = 多一套要维护的契约，且与"第一版客户就是自己人"矛盾 |
| 第三方应用市场 / 插件体系 | 后续版本，需先有稳定契约 |
| 前端 | 本域的前提就是"删掉前端"。恢复任何前端专属通道（SignalR、前端缓存）都会让 REQ-19 的证明失效 |

#### 2.2 有条件不做（条件到了立刻做）

| 不做 | 触发条件 | 为什么 |
|---|---|---|
| 对外 API 版本化承诺（`/v1` 冻结） | **一旦出现外部调用方** | 第一版契约可以动；有外部调用方还动，等于让对方半夜挂掉 |
| 供应商凭据加密的密钥轮换 | 第一次真实备份/迁移演练 | 加密先做（S-V6），轮换是第二步；没有轮换方案的加密只解决"文件被拷走" |
| OpenAPI 契约快照纳入 CI diff | 有第二个客户端时 | 单客户端时 diff 只是噪音 |

#### 2.3 本域不负责（别在这里找）

| 事 | 归谁 |
|---|---|
| 任务的执行、步骤写入、状态机合法迁移 | F4（REQ-11 ~ 13、16）；运行状态机真源在 `core/runs.py` |
| 会话历史、引用落库、回答与运行的关联 | F5（REQ-04、14、15、21） |
| 登录、会话票据、团队隔离判定 | F1（REQ-AUTH-01 ~ 11）——**S-V1 的登录步卡在这里** |
| 备份恢复 | **已归本域**：`backup` / `restore` 命令见 §1.12（S-V12，2026-11-04）。定时调度与保留策略仍归运维；监控阈值归 `非功能需求.md`（NFR-09，尚未成文） |
| 任务在**服务端进程崩溃**后的恢复 | 不做。REQ-19 承诺的是"客户端断开"，不是"进程重启" |

#### 2.4 两处容易被越界的判断

1. **"有 HTTP 接口"不等于"REQ-17 成立"。** C# 版每个功能都有 REST 入口，但流式只有 SignalR——意味着"看答案生成过程"这件事只能经浏览器。判据永远是那个 smoke 脚本，不是路由表。
2. **"错误返回了"不等于"错误稳定"。** 用 `{ message }` 拼字符串的实现，文案一改调用方全挂，而且没有任何测试会红。稳定性只能由 `code` 枚举保证。
