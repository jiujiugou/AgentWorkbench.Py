# F2 知识资料管理 · 功能域

需求出处：`docs/需求/功能需求.md` §3（REQ-05 / 06 / 10），缺口见同文件 §9（"文档**无团队归属**；删除的索引清理未验证"）。

一句话：**把一份纸变成可检索、可引用的证据；变不成的，必须当场说出来。**

本域的决策已预登记在 `docs/adr/README.md`（0001~0007 全部属 F2：`parsed` 的含义是全文就绪、索引写入是一个事务、删除分三层、去重靠唯一约束、先落盘后写记录）。本文不重述理由；判据落在哪里见第四节。

### 一、这个域要实现什么（每条标 REQ 编号，写"给谁用/解决什么/不满足会怎样"）

#### 1.0 链路总图：两条路，一条进一条出

**摄取**（REQ-05 → 06）：

```
POST /documents
   │
   ├─▶ ① 四码判定 ──拒绝──▶ 400 + code   （库 / 盘 / 队列 三者都不变）
   │        空 → 格式 → 大小
   │        顺序即契约，8 条断言盯着
   ▼
② sha256 —— 在内存字节上算，不落盘
   │
   ├─▶ ③ 去重 ──命中──▶ 返回已有 id（不新建行，也不写第二份文件）
   ▼
④ 落盘（相对存储根）
   │      失败 → 500，不留行（记录还没建，没有状态可标）
   ▼
⑤ 建 documents(pending) ── 先提交，再入队
   ▼
⑥ 入队（huey 自己的任务表：同一个库、不同的表）
   │  入队失败不回滚记录 —— 真正的兜底是启动时扫 pending / parsing，
   │  队列只负责"尽快开始"，不负责"保证开始"
   ▼
⑦ 解析（按后缀分派）─── 失败 → failed + no_text_layer / encrypted / corrupt / unsupported
   ▼
⑧ 切块 ────────────── 失败 → failed + chunk_empty
   ▼
⑨ 写索引三处 ───────── 失败 → failed + index_transient / index_permanent
   │  （正文块 + FTS + 向量，同一事务）
   ▼
parsed ← 只有"三个计数对齐"才配叫这个名字
```

**删除**（REQ-10）：

```
DELETE /documents/{id}
   ▼
① 标 delete_pending ── 吸收态；重入放行（重试按钮按第二次不许报"非法迁移"）
   ▼
② 清索引（FTS → 向量）+ 核对残留 ──有残留──▶ RETRY_LATER，停在原地等重试
   ▼
③ 删三张表（一个事务；显式删，不靠 ON DELETE CASCADE）
   ▼
④ 删文件 ── 失败 → 只留垃圾，不回退状态
   ▼
（行消失，检索 0 命中）
```

**哪些会变、哪些不会**——这决定图能活多久：

| 图里画的 | 变化率 | 变了意味着 |
|---|---|---|
| 步骤与顺序 | **极低** | 变了就是架构改，ADR 要重写 |
| 失败落在哪个码 | 低 | 枚举只加不改语义 |
| 组件名 | 中 | `chonkie` 还没定 |
| **参数**（块大小 / T 超时 / 重试次数） | 高 | **所以图里一个数都没写** |

**画图时浮出来的一处**：如果先落盘再去重，命中的那次会在盘上多留一份孤儿文件，而 V-1 的负控要求"磁盘恰好 1 份"。所以哈希在内存字节上算、去重排在落盘之前；并发撞唯一约束时，输的一方删掉自己那份文件。ADR 0006 的"先落盘后写记录"仍然成立——它约束的是**文件与库行的先后**，不是**哈希与文件的先后**。

#### 1.1 两条前提

1. **19 个 C# 迁移文件不能逐个搬**（编号有空洞、M027 的内容与注释互相矛盾）——已由 ADR 0002 承接：从现状 schema 反推**一条** initial，之后逐条追加。
2. **状态列不可信，只有计数可信。** "可检索"的判定看块数与向量数，不看 `status`——判据已落成 `db/consistency.py` 的断言，不再靠人记。

#### 1.2 三条需求、三个使用者、三句判据

| REQ | 给谁用 | 解决什么 | 一句判据 | 不满足会怎样 |
|---|---|---|---|---|
| **REQ-05** | 团队管理员（上传）；企业成员（间接受益） | 纸变成"能被引用的证据"的唯一入口 | 传 PDF / DOCX / XLSX → 列表出现一行并开始处理；传 XLS（旧二进制）/ 图片 / 空文件 / 超限 → 明确拒绝并**说清支持哪三类**，库里没记录、盘上没文件、队列里没任务 | 没有资料可问，产品退化成通用聊天框（`产品目标与范围.md` §1.3） |
| **REQ-06** | 上传者；被问"为什么搜不到"的运维 | 让"处理中 / 失败 / 可检索"在用户侧是**三件长得不一样**的事 | 三态都看得见；失败带可读原因；**未成功的一律不进检索结果** | 失败被读成"资料里没有"，用户去怀疑 AI 和阈值（§1.3） |
| **REQ-10** | 管理员；合规审阅者 | 删除 = 以后不再作为依据 | 用只在该文档出现的词检索 → 删除 → 同一问题 0 命中；正文、索引、文件三处都清 | "撤回"是假的（§1.5） |

三条是一条链上的三段：**进得来（05）→ 进得对（06）→ 出得去（10）**。缺 05 没东西可查；缺 06 不知道查到的是不是全部；缺 10 删掉的还在答。

按 `00-功能域怎么写.md` §四的判据（去掉一条，另外几条的判据会不会失效），它们**是一个功能的三条不变量，不是三个可以分别交付的功能**：去掉 06，"上传成功"无法证明；去掉 10，"可检索"没有撤销路径，这个标记只增不减；去掉 05 与 10，06 的三态没有对象可标记。

#### 1.3 REQ-06 存在的唯一理由：失败不能被伪装成"资料里没有"

**四种"查不到"，在用户侧完全同构。**

| 真实原因 | 库里能看到的差别 | 用户看到 | 用户会归因为 |
|---|---|---|---|
| 文档没传 / 传了被拒 | `documents` 无行 | 查不到 | AI 不行 |
| 传了，处理失败 | `status=failed` + `error` | 查不到 | AI 不行 |
| 传了，还在处理（或永远在处理） | `status=pending / parsing` | 查不到，或一句"再等等" | 系统卡了 |
| 资料里真的没有 | 文档可检索，检索 0 命中 | 查不到 | **正确行为** |

前三行是缺陷，第四行是功能。**它们的输出一模一样（都是 0 命中），差别只在库里的一个字段——而用户看不到库。**

这就是这条需求存在的唯一理由：它要求把"库里的差别"搬到用户眼前，而不是"界面上多一个状态列"这种装饰。**排查成本极高**，因为症状与"检索不准"完全重合：查的人会先调召回、再调阈值、再怀疑模型，而没有一个数字会指向"这份文档根本没进来"。

**三处现状反例（读代码得出，不是推测）：**

| # | 形状 | 后果 |
|---|---|---|
| ① | 解析成功、索引**永久**失败（鉴权 / 模型不存在 / 维度不符）→ `status=failed`，但 `chunks_fts` 行**已经写进去了**（`DocumentParseWorker` 先 `ReplaceChunks` 再 `IndexDocument`） | 列表说"失败"，全文检索却能命中 → 一份"失败"的文档进了答案和引用。**反向伪装**：不是失败像成功，是失败的东西仍在提供依据 |
| ② | 队列是内存无界 `Channel`，启动时不重扫 `pending` | 进程重启后那些行永远 `pending`："处理中"变成永久态，用户等到放弃 |
| ③ | 解析中途进程崩溃 → 停在 `parsing`，没有任何东西把它推向终态 | 同上，且更隐蔽：状态看起来像"正在干活" |

三条共同点：**都在"库里有差别"这一侧，而用户侧看起来都一样。** 修法也因此不在界面，在状态机与索引的先后关系。

**所以写法只有一条：`可检索` 的判据来自数据，不来自状态列**——三处计数对齐即可检索，`status` 写什么都不算数。这条已落成 `db/consistency.py` 的七类断言（a / b1 / b2 / c1 / c2 / e / f）。

仍待实现的一条：**`failed` 必须意味着"检索不到它"**。要么在失败分支回滚已写入的全文行，要么在检索侧按 `status` 过滤——**选一，不能都不做**（现在是都不做）。

**顺带一条隐含要求**：失败要能重试（C# 有 `POST /{id}/reparse`，状态回 `pending`、清旧 `error`）。它没有独立 REQ 编号，但它是 ②③ 的现实出口——没有重试，"永久处理中"就只能靠人工改库。

#### 1.4 切块器决定块边界，块边界决定 40 题标准答案

题库的 gold 写成 `(文件名, 片段序号)`，不写 `chunk_id`。理由已经写在 `evals/self/questions.json` 的 `note` 里：`chunks.id` 自增，重解析会重建，id 全变，**且不报错**。

但 `seq` 同样是切块器的产物：换切块器 → 块边界变 → 同一份文件的第 3 块不再是原来那段话 → **gold 指向错误的块**。这件事同样不抛异常，只会让命中率从 0.812 悄悄掉下去，而所有人先怀疑检索、再怀疑分词、最后才怀疑切块。

所以顺序固定，反过来做等于白做：

| 序 | 动作 | 做完才有资格做什么 |
|---|---|---|
| 1 | **定切块器**：唯一一份实现，且接缝率 ≤ 5% | — |
| 2 | **重标题库**：40 题 gold 按新块边界重标 | 任何检索指标 |
| 3 | **量阈值**：第一名距离、间隔、拒答线 | 任何"够不够"的判断 |

理由：阈值是在"块"这个单位上量出来的。块边界一变，距离分布跟着变，第 3 步的结论全部作废——而它作废时也不报错。

**现有数字在 `evals/baseline.json`**（被测对象是 C# 切块器产出的库副本，与 Python 无关）：439 块 / 接缝 376 条 / 疑似切断 32 块 / **7.29%**（阈值 5%）；类别分布为块尾不像句尾 24、标题或表格行被切断 6、块首不像句首 3、相邻块拼接成词 1。

7.29% 的意思是：**大约每 14 块就有 1 块从半句开始或半句结束**。这类错误的特殊处在于**不会触发任何其它告警**——引用照样能对上（那句话确实在这一块里），判定照样说"已回答"，而答案是从没有主语的半句推出来的（`F3-功能验证` §4.2 有三条实例）。

**一条落地要求**：`chunks` 行要能回答"这批块是哪个切块器切的"。做法是加一列 `chunker_version`（常量字符串），写入时落盘。没有它，改完切块器之后**无法判断库里哪些文档是旧边界**——只能全量重解析或靠记忆。（待验证：若重解析永远全量，这一列可降级为"文档级一次记录"。）

#### 1.5 删除是跨库的，而且没有事务

| 层 | 在哪 | 能不能回滚 | 删不掉的后果 |
|---|---|---|---|
| L1 业务记录 | `documents` / `document_pages` / `chunks`，同库 | 能（同一事务） | 无 |
| L2 索引 | `chunks_fts` / `vec_chunks_vec`（vec0），**无外键** | **不能**（跨表、跨扩展） | 静默失效，不抛异常 |
| L3 磁盘文件 | 存储目录 | 不能 | 只留垃圾，不影响一致性 |

（分层沿用 `docs/adr/README.md` 索引里的 ADR 0005：只对 L1 保证原子。）

**两个方向，哪个更糟：**

| 顺序 | 失败后留下什么 | 用户有没有入口补救 |
|---|---|---|
| 先删记录 → 再删索引 | 列表看不见、检索能命中（**幽灵**） | **没有**。文档已不在列表，用户无法再点一次删除 |
| 先删索引 → 再删记录 | 列表还在、检索不到（**残废记录**） | 有。再点一次删除即可 |

所以 C# 选的顺序（先索引、后记录、再文件）是对的，`DocumentsController.Delete` 还会在索引不干净时回 409 而不是硬删。**缺的不是顺序，是中间态没有名字**：索引已清、记录未删那一段，`status` 仍是 `parsed`，列表照旧显示"可检索"——正是 §1.3 那条"失败伪装成可用"的删除版本，只不过伪装的方向反过来（**可检索**伪装成没事）。

**四步补偿已落成 `ingest/deletion.py`**：标状态 → 清索引并**核对残留** → 删三张表 → 删文件。索引有残留就返回 `RETRY_LATER`，记录和 `delete_pending` 都留着等重试。9 条断言盯着它：顺序（先索引后记录）、重入（吸收态必须放行）、残留（不清干净不许删记录）、文件失败（留垃圾不回退）。

`delete_pending` 必须对**管理员可见**，否则"清完索引、删记录失败"那一步又变成看不见的中间态。它与普通"失败"的区别：失败是"这份资料不能用"，`delete_pending` 是"这份资料正在被撤销、还没撤干净"——**两者都不能出现在检索结果里，但只有后者需要重试按钮**。

### 二、选用什么成熟组件

本域不自造轮子。每个能力落一个组件，只写"落在哪 / 换掉成本 / 许可"。

**组件的权威清单在 `pyproject.toml` 的 `[[tool.agentworkbench.component]]`，不在本文。** 本文只写取舍（为什么换掉很贵、许可限制），**不写状态**——状态是机器可读的那一份，由 `tests/test_gates.py::test_component_table_matches_dependencies` 盯着：定了不用、用了没定、偷用已否的，三条都会红。本文再抄一遍就是第二份会漂的清单。

| 能力 | 组件 | 落在哪 | 换掉成本 | 许可 |
|---|---|---|---|---|
| 收文件 | FastAPI + `python-multipart` | `api/routes/documents.py` | 低 | MIT / Apache-2.0 |
| PDF 抽取（含页码） | `pypdf` | `ingest/parsing/pdf.py` | **中**：换解析器文本序与页序都变 → 块边界变 → 40 题 gold 作废 | BSD-3-Clause |
| Word 抽取 | `python-docx` | `ingest/parsing/office.py` | 低：只读段落与表格，无版面分析 | MIT |
| Excel 抽取 | `openpyxl` | `ingest/parsing/office.py` | 低：`read_only` 流式读，合并区域靠 `merged_cells` 精确填 | MIT |
| 切块 | `chonkie`（版本 pin 死，不用范围）；中文能力实测不达标则自写 | `ingest/parsing/chunker.py` | **高**：块边界是题库与基线的共同锚点 | MIT（待回源核对） |
| 去重 | `hashlib` + 唯一约束 | `ingest/upload.py`、迁移 | **低**：退回应用层"先查再插"，并发下会插两条并共享同一磁盘文件 | 标准库 |
| 持久化 + 全文索引 | SQLite + FTS5 | `db/engine.py`、`rag/indexer.py` | **高**：换 Postgres = 换分词方案 + 重建索引 + 重跑基线 | Public Domain |
| 向量存储 | `sqlite-vec`（`vec0` 虚表） | `rag/indexer.py` | 低 | Apache-2.0 / MIT |
| 后台队列 | `huey` 的 `SqliteHuey`，**指向同一个库** | `ingest/queue.py` | **低**：退回内存队列会静默丢任务 | MIT |
| 迁移 | `alembic`（一条 initial + 逐条追加，不搬 C# 那 19 个） | `db/migrations/` | 低 | MIT |

**不引**：`procrastinate` / Celery / Redis（要的只是同一个库里的任务表）；`docling` / `unstructured`（换解析器等于换块边界，条件见 §5.3）；OCR（§5.2 的产品假设）；S3 / MinIO / fsspec（单机私有化，一个 `stored_path` 够用）。

embedding 模型不在本域选型：它在 `llm/embeddings.py`，由 F3 定（`bge-m3`），本域只消费它的输出。

队列有一条必须写死的约束：**队列可以丢任务，状态不能丢。** `documents.status` 才是真源——进程启动时扫一遍 `status IN (pending, parsing)` 把它补回来。`huey` 没有 visibility timeout，worker 崩溃后任务不会自己回来。

### 三、做什么是加分项（按 加分÷成本 排序，写清为什么加分/成本/风险，要具体到动作）

口径：**加分** = 少了它某条 REQ 无法验收，或排障会明显变慢；**成本** 用低 / 中 / 高粗档，不估工期。

四项已经不在这里：**拒收四码 + 判定顺序** → `test_upload_codes.py`；**一致性检查第六类（`failed` 却可命中）** → `db/consistency.py` 的 `[f]` 类；**失败原因分类 + 状态机** → `core/documents.py`；**删除四步补偿 + 重试** → `ingest/deletion.py`。

| 序 | 加分项（具体动作） | 加分 | 成本 | 为什么加分 | 风险 |
|---|---|---|---|---|---|
| 1 | **把接缝率从"备注"升级为"门禁"** | 高 | 低 | `python -m evals run` **已经在跑** `sample_chunks.py`，但超阈值只记一行 `quality_notes`，退出码仍是 0（`evals/__main__.py`）。先修到 ≤5%，再把质量条改成退出码——否则"7.29% 高于目标 5%"永远只是一行谁都不看的字 | **顺序不能反**：今天就设门禁会让 `evals run` 永远红，红久了就没人看。先修切块（1.4），再上闸 |
| 2 | **块长分布**：p50 / p95 / max + 过短块（< 80 字）占比，进 `evals run` 的统计输出 | 中 | 低 | 接缝率只判边界，不判"块太碎 / 太长"。太碎 → 引用片段没有上下文；太长 → 挤占上下文预算（`F3` 可用五实测 2265 / 4089 字 / 5 块，块再长就顶窗口） | 不要设通过线。现在没有"多长算对"的依据，只记录（同 F3 对"覆盖率阈值只记不判"的处理） |
| 3 | **页码可追溯实测**：抽 10 条引用，人工翻到 PDF 对应页，核对片段首 20 字 | 中 | 低 | REQ-08 说"相关位置"，REQ-10 的删除判据也依赖"能定位"。而 `ingest/parsing/pdf.py` 的注释写着"页码精度只到第 1 页，撑不起页面跳转"，与按页切块的实现**互相矛盾**——这条冲突必须先实测掉 | 矛盾没解决前不许在文档里写"能跳转到页"。实测结论写进第四节 |
| 4 | **`chunker_version` 列** | 中 | 低 | 改完切块器后，能一句话回答"库里哪些文档是旧边界"（§1.4） | 若重解析永远全量，这一列就是没人读的配置（`代码规范` §5.2：没有消费者的配置比没有更糟） |
| 5 | **磁盘孤儿对账**：`documents.stored_path` 与磁盘文件双向差集 | 低 | 低 | 删除第 4 步失败、上传"先落盘后写记录"中途失败，都会留孤儿。一条脚本能数出两侧差额 | 只对账不自动删。自动删会把"记录写失败但文件还在"的正常重试路径也删掉 |

前五项都是"一列 / 一个码表 / 一条断言 / 一次改顺序"量级——**这就是它们排在前面的原因**：本域的难点不在写多少代码，在让"失败"这件事无法藏起来。

**① V-5 · 失败不参与检索**

|---|---|---|---|
| 1 | 造一份 `failed` 且 `chunks_fts` 有行的文档（真实路径：索引永久失败） | 前置成立，不是手改库编出来的 | 造不出来说明失败分支根本没留全文行，①已不存在，本条降级为"防回归" |

#### 4.4 落地前必须解决的两处矛盾

1. **页码**：`ingest/parsing/pdf.py` 注释说"精度只到第 1 页"，但 C# 切块器是**按页**切、`ChunkDraft` 带 `PageFrom / PageTo`。以实测为准（V-12）。
2. **`chunks_fts` 的内容**：注释与脚本都指出它存的是 **bigram 化后的 token 串**，不是原文。任何"删除后查一下 `content` 里还有没有这个词"的验证都会得出错误结论。

另：REQ-05 / 06 / 10 的 AC 尚未成型，本节是**判据草案，不是 AC**；按 `功能需求.md` §10 维护约定第 3 条，AC 补齐前不计入完成度。

### 五、不做与边界（不做什么、为什么、什么条件下重开）

#### 5.1 产品边界（本域永远不做）

| 不做 | 理由 |
|---|---|
| 图片、网页、旧版 Office（`.doc` / `.xls`） | 图片与网页要的是 OCR / 渲染，不是文本抽取；`.doc` / `.xls` 是二进制复合格式，`python-docx` 与 `openpyxl` 都不读，硬接要引入 antiword / LibreOffice，链条比"让用户另存为"长得多。**注意 C# 实际还能收 txt/md/json**——那是超出承诺，不是承诺 |
| 文档版本管理（v1 / v2 / 回滚） | 属文档管理系统范畴（`产品目标与范围.md` §1.3）。做了它，"哪一版是现行版"就变成一个要用户维护的字段，而第一版没有维护界面 |
| 在线预览与编辑 | 只提供"可核查原文"的只读访问。做编辑器就要处理并发与保存冲突，与"查资料"无关 |
| 文档级 / 部门级权限 | 三维矩阵，量级高一个数量级（`产品目标与范围.md` §6 依据 3）。本域只负责让每行带上 `tenant_id`（**现在没有，要加**），判不判由 F1 定 |
| 外部知识来源连接器（飞书 / Confluence / 网盘 / ERP） | 每个连接器 = 授权 + 增量同步 + 来源侧权限映射，与 AI 能力无关 |

#### 5.2 目标客户的文档假设——这一条必须如实写

> **支持 PDF / DOCX / XLSX 三类，但三类都只取"有文本层"的那一部分。这句话是刻意的边界，也仍然是一个可能不成立的产品假设。**

**三种格式归一化成同一个东西：段。** 解析层的输出永远是 `list[str]`，第 i 个元素（1-based）就是引用里的"第 i 页"。切块、索引、检索、引用四处一行都不用改——它们只认识"段"。

| 格式 | 段怎么分 | 引用显示的第 N 页实际是 |
|---|---|---|
| PDF | 每页一段 | 真实页码 |
| Word | **整篇一段** | 第 1 段（`python-docx` 不提供页码；假装按页切会给出用户翻不到的数字） |
| Excel | **每个工作表一段** | 第 N 个工作表（按 sheet 顺序） |

代价写在明处：Word / Excel 的引用无法定位到具体页或行。要定位到行，得先把"段"换成带行列号的"表格单元"，那会改切块与引用的契约——归入 §5.3 的条件不做。

| 假设 | 制造业现场的现实 | 假设不成立时用户看到什么 |
|---|---|---|
| 客户的核心资料是电子版文件 | 图纸、盖章工艺卡、检验记录、老设备手册**大量是扫描件或照片**；Word / Excel 里也常夹着扫描图 | 传进来 → `no_text_layer` 失败。用户读到的是"不支持"，而不是"系统认出这是扫描件、需要 OCR" |
| 一份 PDF 是一份独立资料 | 合订本手册 800 页，正文与附录、不同型号混排 | 块数暴涨，引用指向"合订本第 300 页"，回原文仍要人翻 |
| 文字横排、单栏、版面规整 | 图纸标题栏竖排、双栏排版、表格式参数页 | 抽取顺序乱 → 接缝率上升 → 块从半句开始（§1.4 的 7.29% 只是当前这批电子版的数字，扫描/图文混排只会更差） |
| 客户能说清哪份是现行版本 | 车间文件夹里 v1 / v2 / 带"作废"章的同时存在 | 两版都入库，答案引旧版，而系统没有任何字段能区分 |

**结论要写在这里，不许含糊**：这条假设不成立时，产品价值**要打折**，而且打折的恰是最痛的那一块——现场资料。能问的只剩"电子版手册"这一小部分，而用户最先想问的往往是那张盖章的工艺卡。这不是"以后加 OCR 就好"能带过的：OCR 进来会同时改变块边界、题库 gold 和引用可信度（识别错的字会被当成原文引用）。

#### 5.3 有条件不做（条件到了立刻做，条件不到做了就是浪费）

| 不做 | 触发条件 | 先补什么 |
|---|---|---|
| OCR（tesseract / paddleocr） | 客户前 20 份真实文档里扫描件占比 > 30% | **现在没有客户样本，这个数待验证**。先补 REQ 与 AC；OCR 必须引入独立状态（"已识别，可能有错字"不是"可检索"），否则识别错误会静默进入引用 |
| docling / 版面分析 | 接缝率修完仍 > 5%，且人工复核确认根因是版面而非切块算法 | **先重标题库**（gold 全部重标），再换解析器。顺序见 §1.4，反过来做等于白做 |
| 文档版本管理 | 出现"同一份文件两个版本都被引用"的真实投诉 | 先补 REQ。版本会改文档主键或加一个 version 维，牵连 F5 的引用落库与 F4 的记录关联 |
| 增量重解析（只重跑变更页） | 单份文档解析超过 N 分钟 | 现在没有大文件样本，N 定不出来 |
| 跨团队去重（同内容只存一份） | 出现存储压力 | 现在按团队去重就够。跨团队共享文件会让"删一条毁另一条"从一个团队内的 bug 变成一个跨团队的数据事故 |

#### 5.4 本域不负责（别在这里找）

| 事 | 归谁 |
|---|---|
| 检索、排序、拒答、引用校验 | F3（REQ-07 / 08 / 09） |
| 团队归属判定、谁能上传 / 谁能删 | F1（REQ-AUTH-02 / 04） |
| 处理失败的**运维告警**与重试策略编排 | `非功能需求.md`。本域只保证"状态真实、可重试" |
| 错误响应体格式、业务码的传输层约定 | F6（REQ-20）。本域只定义**文档侧**的码（`NO_FILE` 等四个 + `error_code` 枚举） |
| 引用如何落库、回答与运行的关联 | F5（REQ-21） |

#### 5.5 三条最容易越界的判断

1. **"传上去了"不等于"能搜到"。** 索引要写三处（正文块、全文、向量），任一缺失都会让列表显示"可检索"而检索全空。所以"可检索"的判据永远是三个计数，不是 `status` 字段（`db/repositories/documents.py` 的注释已经写死这条）。
2. **"删掉了"不等于"搜不到"。** 删除的判据是**检索**（用只在该文档出现的词问一次），不是列表里少了一行。列表消失是最容易做到、也最容易骗过自己的一半。
3. **"有错误信息"不等于"能排查"。** 一句 `error` 自由文本能让用户看到"失败了"，但不能回答"这个月失败里多少是扫描件"——而后者才是要不要做 OCR 的依据。所以 `error_code` 是枚举，`error` 只是文案。
