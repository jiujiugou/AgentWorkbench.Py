### 一、这个域要实现什么（标 REQ 编号）

#### 1.1 四条需求、四句判据

| REQ | 要成立的事 | 一句判据 | 不成立时用户看到什么 |
|---|---|---|---|
| **REQ-04** | 看得到自己的历史会话，能接着聊 | 换个浏览器登录，会话列表、标题、最近更新顺序与上次相同；选一条追问，消息落在同一条会话里，不新开 | 刷新就没了；或者每次追问都变成一个新会话，历史碎成一地问一答 |
| **REQ-14** | 每条回答可展开其运行记录 | 展开任意一条历史回答，能看到迭代轮次、工具调用及参数与返回、耗时、结束状态与原因 | 只有一个答案，说不清它是查出来的还是猜的 |
| **REQ-15** | 过程审查的边界是"自己有权查看的"，含其中的输入、证据、工具参数与结果 | 换一个账号，拿这条会话的 id 取轨迹，返回 404 而不是内容；**原数据不被修改**；轨迹里的参数与结果与会话消息用同一套归属判定 | 不知情的越权读；或者"消息看不到，轨迹却能看"——隔离只做了一半 |
| **REQ-21** | 回答在保存时，正文、引用、运行三块一起保存 | 关浏览器重开：答案原文、引用列表（含当时的校验标记）、对应的唯一一次运行，三样都在且与当时一致 | 回复还在，出处没了，过程没了——而"没保存"和"没显示"在界面上长得完全一样 |

**REQ-21 是本域唯一一条"新写"的需求**，另外三条是从 F1 与 F4 移过来的（编号不变，`功能需求.md` §1）。移过来的理由写在需求文档里，与本域的实现无关；这里只承接判据。

#### 1.2 为什么它必须是独立域

C# 版里，"会话"分散在三处，三处都只保管一部分：

| 位置 | 保管了什么 | 都不回答的问题 |
|---|---|---|
| `Webapi/Controllers/ConversationsController.cs`（4 个动作：列表 / 新建 / 取消息 / 删除） | 会话与消息的对外形状 | 一条回答由哪些部分组成 |
| `Persistence/ConversationRepository.cs`（8 个方法） | 会话行、消息行的读写与事务 | 同上。**签名里就能看出来**：`AddMessageAsync(conversationId, role, content)` 只有三个参数，没有引用、没有 run 的位置 |
| `Memory.Persistence`（`M023` + `SqliteSessionStore`） | 整段会话序列化进 `state_json`，给模型续聊用 | 这是给模型的历史，不是给人的历史；它和 `messages` 互不知情 |

**没有一个模块对"历史"负责。** REQ-21 的两个缺口不是谁写错了代码，是这两件事从来没有归属——所以它可以一直缺着，而且每一处看起来都正常。C# 文档里那句"只有「引用」没有落点"（`docs/数据库/表与域.md` 第 21 行）就是这个洞的原文。

两处缺口的具体形状：

- **引用从未落库。** 保存回答只写正文一个字段；重开时前端加载完**主动把 `sources` / `citations` / `toolSteps` 全置空**（`agent.ts:90-95`）。所以"引用丢失"在代码里是一次赋值，不是一个缺失的功能——这正是它容易被当成"前端小问题"放过去的原因。
- **消息与运行之间没有边。** 三个 id 彼此不相指：会话 id 永久、`messageId` 只活在当次连接的内存里、`messages.id` 是自增整数。后果有两层：重开后 3 条回答对 5 次运行，说不清谁是谁；而且同一轮对话在"当时"和"重开之后"连标识都不是同一个，想记也接不上。

它定义的不是两个字段，是**一条回答由哪些部分组成**：

| 组成 | C# 保存在哪 | 重开之后 |
|---|---|---|
| 正文 | `messages.content` | 在 |
| 引用（含当时的校验标记） | 只在当次推送里 | **不在** |
| 那次运行 | `agent_runs`，但不知道是哪一条回答的 | 在，但接不上 |

三块只存了一块。"可回放"这个承诺在用户侧就不成立——用户看不到的地方等于没有保存。只把它当成"顺手加两列"，会漏掉三件必须现在就定的事：写入时机（三块同事务，1.6）、失败轮次挂在哪（正文为空也要有一行，1.6）、删会话时跟不跟着删（1.7）。

#### 1.3 引用必须存原文快照，不能只存 `chunk_id`

| 只存 `chunk_id` 会怎样 | 说明 |
|---|---|
| 重建索引 / 重解析之后 | `chunks` 全表换 id，旧 id 要么查不到（空卡片），要么指向**别的内容** |
| 后者更糟 | 指向别的内容时**不报错**：卡片照样弹出来，文件名也许还一样，只有原文对不上——而用户正是来看原文的 |
| 存 `document_id + chunk_id` 也不行 | `documents` 行还在，旧 id 与新内容之间没有任何校验能发现不匹配 |
| 校验与被校验分叉 | 当时的校验用的是当次证据，历史回看用的是库；两边一分叉，谁都不会红 |

**快照必须包含的字段（这是判据，不是表结构）：**

| 字段 | 为什么必须有 | 出处 |
|---|---|---|
| **文件名** | 人得先知道是哪份文件 | REQ-08 三要素之一 |
| **片段序号** | 文件内的位置。页码退出判据后，它是唯一还能定位的东西 | REQ-08"相关位置"；D-06 已把页码降级 |
| **原文片段（前 120 字）** | 重开后**不查库**也能读出"当时引的是哪一段" | 前端 `citations.ts:74` 取 `content.slice(0, 120)`；F3 可核五的卡片字段 |
| **当时的校验结论** | 否则"当时标红的误挂"重开后变成一条干净引用——比没有引用更危险，它带着担保 | REQ-21 判据②"与当时一致"；F3 可核三 |
| 可选的页码 / 小标题 / 覆盖率 | 有则更好，缺了不影响判据 | `RetrievalHit` 已有字段 |

关于 120 字这个数字，写清出处，免得被当成 D-06 定的：**D-06 只把"回原文"从页面跳转降级为片段卡片，并把页码退出判据**；120 字来自前端卡片现有的截断长度。选定 120 是因为它和界面一致——库里存的和界面显示的必须是同一个数，否则"与当时一致"要按哪一份算就说不清了。

**这条判据的可执行形状（C-V3）：** 重建索引（或把 `chunks` 里的内容换成一个哨兵串）之后，换一台机器登录同一账号打开同一会话：引用卡片上的文件名、片段序号、原文片段、校验标记，与提问当时**逐字相同**；哨兵串不得出现在任何历史引用里。

它成立的前提是"读引用时不查询 `chunks` 表"——快照必须自包含。一条需要回表查的快照，等于把 `chunk_id` 方案换了个写法。

**存储形态（JSON 列还是子表）属于实现，本文不规定。** 唯一不允许的是：快照里的任何字段是外键或指针，而不是复制下来的值。

#### 1.4 判据只有一句，观察点有四个

> **换一台电脑、换一个浏览器、登录同一账号：历史会话、当时的答案、当时的引用、当时的轨迹，必须一模一样。**

四个观察点，少一个这句就不成立：**会话**（列表内容、标题、顺序、条数）、**答案**（正文逐字相同）、**依据**（引用条数、每条的字段、当时的校验标记）、**过程**（迭代、工具、参数、返回、耗时、终态与原因）。

**为什么不能放宽成"刷新后还在"：** 只存在于当次推送里的东西，刷新就消失。用户会认为"系统没保存"，而事实是**从未保存过**。这两个问题在界面上长得完全一样，排查成本差得远——一个是找 bug，一个是补功能。

**标题属于判据，不是装饰。** 标题若只活在前端内存（取首条用户消息前 18 字），换设备后列表里所有会话都叫"新会话"——四个观察点里"会话"这一项当场不成立，而消息本身是对的，用户会以为"历史乱了"，实际只是名字丢了。所以标题必须随会话落库、写一次、之后不再变。

**顺序也属于"一模一样"。** 列表与消息都必须有确定的次序（同一秒创建的两条不许换位），否则这条判据落到测试里会变成随机红。用哪个键排是实现的自由，**"确定"是功能要求**。

#### 1.5 会话列表不得泄露"存在性"

不是"列表里不出现别人的会话"，是**连"存在一条你看不到的会话"都不能推断**——计数、排序、时间都不行。

| 约束 | 为什么 |
|---|---|
| 每个读写操作的第一个参数是 owner，且**强制**而非可选 | "可选参数、为空则不过滤"会让漏传一次就跨租户泄漏，而测试里都传同一个值，看不出来 |
| 越权返回 404，不是 403 | 403 等于承认"这条 id 存在" |
| 别人的会话 id 续聊 → 当作"不存在"新建，不报错不复用 | 同上：不能通过报错探出存在性 |
| 过滤在查询里，不是"查全部再过滤" | 分页的总数也只能是过滤后的数，否则总数泄漏 |
| 排序要有确定次序 | 见 1.4 |
| 拒绝必须留痕 | 404 不泄露，但运维要能回答"是没权限还是坏了" |

**一处必须写死的边界**：读消息这个动作不能独立于归属存在。C# 是"先校验会话、再按 id 取消息"的两步式，顺序反了就是跨租户读取，而写成测试时很容易变成"先读后校验"，测试还是绿的。本域要求：**读取必须自带归属**，让"漏校验"在类型上不成立。

#### 1.6 每一次作答都要落行，且三块同事务

"本域不产生任何新数据"这句话有一个例外，不写清会被当成自相矛盾：REQ-21 要求把当次的引用抄一份存下来，这是写。

区别在于写的是什么：**写的是已经发生过的事实的副本**，不是新结论——不重新检索、不重新打分、不重新判定。三条硬规则跟着出来：

| 规则 | 违反后用户看到什么 |
|---|---|
| 快照只从当次证据与当次校验结果复制，落库时**不许重算** | 重开后引用"看起来一样"，但校验标记是事后算的；一次模型/阈值变更就让历史自相矛盾 |
| 正文、引用快照、`run_id` **同一次事务写入** | 半条回答（有正文没引用）在界面上与"引用从未落库"完全一样 |
| **每一轮都要有一条 assistant 行**（正文可为空），`run_id` 必填且唯一 | 失败/取消那一轮没有挂点，轨迹永远看不到——而失败原因恰好是最需要回看的（REQ-14 要求失败步骤必须标出） |

**这一行要早写，不能等作答结束。** 只在跑完之后才写行，留了一个说不出口的空档：进程在写回答之前被杀，那次运行在库里的状态是"跑着"，而消息里**一行都没有**。后果不是"少一条记录"，是这条运行落不到任何会话——它不属于任何一段历史，删会话也带不走它，就那么一直躺在库里。

所以写回答分两段：**运行一起来就先占一行**（正文空），作答结束后把正文与引用补到同一行上。代价是界面必须分得清三种"没有字"：

| 界面看到的 | 意思 | 用户该做什么 |
|---|---|---|
| 正文空 + 运行仍在进行 | 这一轮还没结束（可能真在跑，也可能进程早就不在了） | 等一下；长时间不动就是中断了 |
| 正文空 + 运行已失败 | 跑完了，没答上来 | 展开轨迹看失败在哪一步 |
| 正文有内容 + 运行已拒答 | 它明确说了"资料里没有" | 换问法，或者补资料 |

三种都显示成"一条空回答"，等于把三个排查方向压成一个。**"进行中"与"跑完了但空"必须在界面上可区分**——这是两段写带来的必然后果，不是可选的优化。

**拒答在历史里必须还是拒答。** 拒答的正文是一句固定文案。如果历史只存正文，重开之后这条会变成一个普通回答气泡——字一样，但它当时的意思是"我没答"，现在成了"我答了这么一句"。差别不在内容，在**这是不是一次回答**。

判据：重开历史，当时拒答的那条仍然以拒答的样子出现，理由与当时相同，正文一字不变。两条禁止：

- **不许用"正文等于那句文案"来判定。** 文案会改，改文案那天所有历史拒答会一起变成正常回答，而且没有任何东西会红。
- **不许在展示层重新判一遍。** 判定发生在当时；事后按当前阈值再反推，等于让"当时"随参数一起改口。

它挂在**同**（重开之后与当时一致）而不是**存**：要成立的不是"拒答被存下来了"，而是"重开之后它还是拒答"。

#### 1.7 删除的级联范围（写死，不留给人猜）

用户能执行的最强删除动作就是"删整个会话"（单条消息不许删，见 §二）。所以这个动作必须真的删干净——**库里留一份用户看不见、也不会再被读到的历史，与"没删"没有区别**，却会让"删除"这个承诺变成假的。

| 表 | 删会话时 | 理由 |
|---|---|---|
| `conversations` | **删** | 动作的对象 |
| `messages` | **删** | 会话内容本身 |
| 引用快照 | **删**（随 `messages`） | 它存的是原文片段。留下来等于"界面删了，原文还在库里"，是这个动作最不该有的样子 |
| `agent_runs` / `agent_steps` | **删**（同事务） | 它们含输入、证据、工具参数与返回。**这是刻意选的**：团队级审计视图不做（§二），这些行删掉之后没有任何人能读，留存只增加一份看不见的副本。代价是"这次对话的审计证据随会话一起消失"——接受这个代价，写在这里 |
| 模型侧的历史副本（C# 的 `agent_sessions.state_json`） | **删**（同事务） | 它是整段对话的**第二个副本**，含用户原文；而且它只按过期时间清、不会自己走。不删它，"删会话"就只是删了给人看的那一份。Python 版不建这张表，等于从源头去掉了第二副本 |

三条约束跟着这张表：

1. **同一事务**。删一半（消息删了、历史副本还在）时，用户看到的是"删成功"，实际是"删了一半"，而且没有任何地方会报错。
2. **不做软删**。软删需要一个"谁看得到已删行"的规则，而那个规则只在团队级审计视图里有意义——本域不做那个视图。
3. **删除必须在日志里留一行**（**不含内容**：会话 id、操作者、时间、删了几条消息）。这是 1.5"拒绝要留痕"的同一条原则：删干净了，运维还得能回答"这条会话是被删了，还是从来没创建过"。

**级联写对，不等于用户能删。** 仓储里五处一起删、测试全绿，而对外接口上没有这个动作时，界面上的删除按钮每一次都失败——用户看到的是"删不掉"，排查的人看到的是"删除逻辑明明测过了"。**一条只活在仓储层的删除，等于没有删除。**

判据：删除之后，列表少一条、消息与轨迹都取不到；对同一个 id 再删一次得到 404，且这次响应与"一个从来没存在过的 id"**逐字段相同**（§1.5：删除也不能当探针用。比较时剥掉 `request_id`——它是每请求随机值，与存在性无关；2026-11-03 随 S-V4 精确化）。删别人的会话同样只是 404，B 的任何计数都不变——**别人的会话不能被"删"这个动作证实在过**。

#### 1.8 功能流程

**四条不变量**（子问题与验证在 toml）：**存**（三块一起落库，缺一块等于没存）、**同**（换设备逐字段相同）、**隔**（别人的会话连"存在"都不可推断）、**清**（删会话删干净）。

| 位置 | 落在哪步 | 输入 → 输出 | 坏了谁做错判断 |
|---|---|---|---|
| **入口与会话归属** | 0，业务开始之前 | question +（可选 `conversationId`）+ owner → 会话 id（新建 / 复用 / 他人 id 当作不存在而新建） | 传别人的 id 就直接复用了别人的会话：内容写进他人历史，两边都看不出来 |
| **用户消息落行** | 写 1 | 用户原话 + 会话 → 一条用户消息 | 只在内存里 → 刷新即失，与"没保存"长得一模一样 |
| **作答** | 写 1 的下游（F3 / F4） | 会话 + 问题 → 正文 + 当次证据 + 校验报告 + `run_id` | —（本域不重做，只消费它的产物） |
| **三块同事务落行** | 写 2 | 正文 + 引用快照 + `run_id` → 一条回答 | 半条回答（有正文没引用）在界面上和"引用从没落库"完全一样 |
| **先占一行** | 写 2 的前半，run 一起来就写 | 会话 + `run_id` → 一行空正文的 assistant | 只在结束时写 → 崩溃那次运行落不到任何会话，删会话也带不走它 |
| **引用快照复制** | 写 2 的一部分 | 当次证据 + 校验结论 → 快照（文件名 / 片段序号 / 原文 120 字 / 当时标记） | 只存 `chunk_id` → 重建索引后要么空卡片，要么指向**别的内容**，后者不报错 |
| **历史投影** | 读 | 会话 + owner → 消息三块 | 界面拿 id 回表再查一遍 → 证据与当时分叉，且没人会发现 |
| **轨迹读取** | 读（F4 的表） | `run_id` → 步骤全文 + 终态 + 原因 | 把当次推送的 600 字预览存起来当历史 → 失败步骤永远看不到 |
| **列表与排序** | 读 | owner → 会话列表（标题 / 更新时间 / 条数，确定次序） | 计数或首末时间泄漏"存在一条你看不到的会话"；同一秒创建的两条换位 → "一模一样"变成随机红 |
| **删除** | 写 3 | 会话 id + owner → 五处一起消失（1.7） | 删一半（消息删了、run 还在）→ 界面说"已删除"，库里还有一份 |
| **删除的对外入口** | 写 3 的入口 | 会话 id + owner → 成功；不存在 / 别人的 / 已删过 → **同一句** 404 | 端点没接 → 界面按钮每次必失败，而删除逻辑"明明测过了" |
| **归属过滤** | 贯穿全部读写 | 调用者 + 查询条件 → 只含该 owner 的行 | 某一处漏了 owner → 跨租户读写，而测试全绿：因为所有用例都传同一个 owner，漏与不漏结果一样 |
| **入口声明** | 全局 | 路由全集 → 逐条表态 | 新增一条作答路由没登记 → 本域断在没人走过的那条路上 |

一条回答的完整形状：

```
t0  请求（question，可能带 conversationId）
t1  ├─ 会话：新建（title = 首条问题前 18 字，只写这一次）/ 复用 / 他人 id → 新建
t2  ├─ 用户消息一行
t3  ├─ run 开始 → **立刻占一行空 assistant**（此刻起，这次运行有历史了）
t3.5├─ F3/F4 作答：检索步 → 生成步 → 终态              ← 已有，不归本域
t4  ├─ 读当次证据与校验结论（内存里那份，不回表）
t5  └─ 一个事务：把正文 + 引用快照补到 t3 那一行上（`run_id` 不变）
```

**完成的定义**：某个位置做完，是挂在它上面的子问题在 `pyproject.toml` 里从 `partial` 变 `pass`——不是"代码写了"。

#### 1.9 本域没有状态机

会话与消息都没有状态列。"失败那一轮也要有一行"是**行存在性**，不是状态迁移——那次运行的状态在 F4 的 `agent_runs.status` 上，本域只引用它。占位行带来的"进行中"也一样：那不是消息的状态，是它指向的那次运行还没结束。消息这一侧只有两件事可问——**行在不在**、**正文有没有**。原子性靠事务边界表达（三块同事务写、五处同事务删），不做软删，也就不需要状态机。

给它造一个"存在 / 已删除"两态的状态机，只会诱使实现去做软删——而软删需要一个"谁看得到已删行"的规则，只有团队级审计视图才用得上（§二）。

#### 1.10 会话类型：F7 接入后的结构约束

F7 的通用对话与 F3 的知识库问答是两种答案合同。本域不改变“存/同/隔/清”四条不变量，但会话多了一个**创建时固定**的类型：

| 列 / 行为 | 规则 |
|---|---|
| `conversations.kind` | 只能是 `knowledge` 或 `general`；新库建表时写入，老库迁移默认 `knowledge`（存量会话全部是知识库会话） |
| 类型可变性 | **不可变**。通用切知识库、知识库切通用，都必须新建会话；禁止 UPDATE `kind` |
| 列表与计数 | 可以混合展示，也可以按 `kind` 筛选；无论哪种，计数、排序、筛选都不能泄漏“另一类里有没有会话” |
| 消息与引用 | 两类都保留 `messages` 与 `run_id`；`knowledge` 回答还要有引用快照，`general` 回答的引用快照必须为空 |
| 续聊 | 请求的 `conversationId` 必须与入口期望的 `kind` 相同；不同 kind 按“不存在/不可续聊”处理，不得把通用回答写进知识库会话 |
| 删除 | 两类都按 §1.7 的五处同事务硬删；不因 kind 不同而保留 run 或引用 |
| 标题与排序 | 两类规则相同：标题写一次、排序确定；类型不改变归属与历史判据 |

**这不是第五条不变量**：`kind` 是结构约束，不是“存/同/隔/清”之外的新承诺。它防止的是 F7 的“不混”被实现成一次 UPDATE；类型一旦可变，引用快照、拒答历史与列表计数会同时失去解释。

#### 1.11 历史引用与轨迹证据：按当前等级过滤，正文保留（REQ-24）

**引用快照不因等级变化重写，但读取时按当前等级重新判断来源可见性。** 一次回答发生时，用户可能有权看某个私人库；之后等级被降低，历史答案仍在，引用快照也还在。系统不能假装那次回答没发生，但也不能继续把私人库的原文片段递给已经无权查看的人。

| 对象 | 读侧规则 | 不允许 |
|---|---|---|
| 引用快照 | 快照必须带 `kb_id`；按当前等级判断该知识库是否可见。可见 → 正常显示；不可见 → 只显示“来源已不可访问”，**不显示文件名、片段、页码** | 因为快照是历史数据就跳过权限；或把不可访问的引用整条删除，让用户以为当时没有引用 |
| 轨迹证据 | 检索步骤里的文件名、片段、命中文本同样按当前可访问集合过滤；不可见时显示“证据不可访问” | 只过滤引用面板，轨迹仍能展开原文 |
| 答案正文 | **保留，不改写、不追溯删除** | 承诺“降级后连历史答案里的旧内容也完全看不到” |

**残余风险要写在明处**：答案正文可能已经包含高等级资料的内容，降级后正文仍然可见；引用过滤只能挡住“来源侧”的再次读取，不能把模型已经写下的句子收回去。这是 ADR 0011 明确接受的取舍，不能在验收里写成“完全不可见”。占位文案只说明“这里曾有一条来源”，不显示知识库名称、文件名、片段或页码；它是历史读取的明确例外，不是检索侧可以泄漏的接口。

**迁移与查询条件**

- 旧引用/证据快照回填默认公共知识库；默认公共库对全团队可见，因此存量历史行为不变。
- 查询历史时，`knowledge` 会话按当前等级过滤 `message_citations` 与证据；`general` 会话本来没有引用，不受影响。
- 管理员没有内容后门：低等级管理员读历史时同样看不到高等级私人库的引用与证据。
- 等级恢复后，同一批历史引用应重新可见；过滤是读时判定，不写回快照。

**验收至少覆盖**：高等级账号产生引用 → 降级 → 引用只剩“来源已不可访问”且无文件名/片段 → 恢复等级 → 引用重新可见；答案正文前后不变；低等级管理员看不到高等级私人库证据；公共库历史不受影响；跨团队仍 404。

### 二、不做与边界

#### 2.1 产品边界（本域永远不做）

| 不做 | 理由 |
|---|---|
| **团队级审计视图**（管理员浏览全员历史） | REQ-AUTH-05 的边界是"自己有权查看的"。全员历史是另一个产品面——它回答的是"谁在什么时候问了什么"，涉及员工行为，需要单独的授权与告知设计，不能靠"管理员本来就能看"顺推 |
| **会话导出**（PDF / Markdown / 批量下载） | 导出把数据带出系统，权限随之失效（转发不受控）。而且导出物里必然带引用快照——那是原文片段，等于把知识库内容整段带走。这不是"以后再说"，是**导出的那一刻 REQ-AUTH-04 就不成立了** |
| **历史会话的全文搜索** | 需要独立索引，与知识检索是两套东西。第一版不混进知识库索引——两套索引共用一套编号空间，"检索命中"与"历史命中"会互相污染 |
| **自动归档 / 保留期清理** | 第一版不做清理，**但也不得对外承诺"永久保留"**。不做清理 ≠ 承诺永久：保留期是待定项，对外只能承诺"当前不自动删除" |
| **编辑或删除单条消息** | 两个理由，任一个都够：①破坏"回答 ↔ 运行"的对应，审计链断；②**删不干净**——模型记忆在会话状态里，删消息那一行，模型那份还在。允许删单条，等于制造一份自相矛盾的历史。只允许删整个会话 |
| **跨会话的上下文记忆**（"还记得我上次说的吗"） | 长期记忆是后续版本；第一版只在同一条会话内续聊。这不是能力不足：记忆一旦跨会话，就出现了"它凭什么记得"的权限问题（A 的会话内容进入 B 的回答），而现有权限模型只到会话归属这一层 |

#### 2.2 有条件不做（条件到了立刻做）

| 不做 | 触发条件 | 为什么 |
|---|---|---|
| 保留期清理（按时间自动删） | 第一个真实部署提出合规要求，或库体积成为问题 | 它需要先回答"删掉的会话，其 run 与引用快照跟不跟着删"——那正是 1.7 与 C-V8 定下的事。顺序反了，清理会先删出悬空 run |
| 历史全文搜索 | 会话数量超过人工翻找的规模，且愿意为第二套索引付维护成本 | 见 2.1。先有量，再谈索引 |
| 历史消息分页 | 单会话消息数超过一次渲染能承受的量（具体数值待压测） | 现存量 34 条消息，第一版不需要 |

#### 2.3 本域不负责（别在这里找）

| 事 | 归谁 |
|---|---|
| 检索、答案生成、引用校验、拒答判定 | F3（REQ-07 / 08 / 09） |
| `agent_runs` / `agent_steps` 的写入、状态机与合法迁移 | F4（REQ-11 / 12 / 13 / 16） |
| `documents` / `chunks` 的切块与索引重建 | F2（REQ-05 / 06 / 10） |
| 登录、会话票据、团队隔离的判定 | F1（REQ-AUTH-01 ~ 11） |
| 错误响应的结构、错误码表、流式传输契约 | F6（REQ-17 / 18 / 19 / 20） |
| **"这条记录属于谁"** | F4。`agent_runs` 有 `user_id` / `tenant_id` 且写入强制非空，本域读轨迹时用它们过滤，不另外补。**但"他该不该有这个权限"归 F1**——本域按归属与当前等级过滤，不重新定义角色与等级规则 |
| 知识库可见性判定 | F1 §1.10 / F2 §1.6；本域只消费“当前可访问集合”来过滤引用与证据 |
