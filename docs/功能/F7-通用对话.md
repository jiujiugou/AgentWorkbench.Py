# F7 通用对话 · 功能域

需求出处：`docs/需求/功能需求.md` §8（REQ-23）。

一句话：**通用对话是明确标注、不会检索企业资料、也不会伪装成知识库答案的模型对话入口；它和知识库问答是两个入口，不是同一条会话里的两个模式。**

本文只写**功能**：为什么要有这一域、它必须成立什么、什么永远不许发生。另外两类各归其位：

- **不变量与验证**登记在 `pyproject.toml` 的 `[[tool.agentworkbench.verification]]`（`D-V1` ~ `D-V5`），由 `tests/test_gates.py` 守着。本文不抄状态与测试引用，避免两处各存一份“过没过”。
- **实现**住在代码与注释里：会话类型在 `db/engine.py` 与 `db/repositories/conversations.py`，作答入口与 run 写入在 `api/`、`chat/`、`trace/`，前端入口在 `web/src/`。本文规定“必须成立什么”，不规定“怎么写”。

---

### 一、这个域要实现什么

#### 1.1 一条需求、五个判据

| REQ | 要成立的事 | 一句判据 | 不成立时用户看到什么 |
|---|---|---|---|
| **REQ-23** | 通用对话可作为独立入口使用：不检索企业文档、不产生引用、明确标识“未使用企业资料”，且与知识库问答不混流 | 从通用入口提问，回答正常生成；库里没有本次检索证据，响应与界面也没有来源/角标；换到知识库入口问同一句话，仍走原检索、引用与拒答流程 | 通用回答被当成企业文档答案；或知识库拒答后自动转通用回答，用户以为“资料里没有”是“系统不会查” |

**为什么它必须是一条独立需求**：它定义的是“第二种答案的合同”。知识库问答的合同是“有证据才答、无证据拒答、答案可核”；通用对话的合同是“允许模型凭通用知识回答、但不许声称来自企业资料”。两份合同不能靠一个 `mode` 字段在运行时互换，否则引用、拒答、审计三套判据会同时失去边界。

#### 1.2 为什么是独立域，而不是塞进 F3 / F5 / F6

| 现有域 | 为什么不能直接承担 | 结论 |
|---|---|---|
| **F3 知识问答** | F3 的不变量是“可用、可核、不编”。通用对话恰好允许“不检索、无出处、凭通用知识回答”，把它塞进 F3 会让 F3 的拒答与引用判据自相矛盾 | 新增 F7；F3 仍只做有证据的问答 |
| **F5 会话与记录** | F5 负责“历史能被读到、能接着用”，不负责“答案怎么产生”。通用对话需要新的生成路径与新的回答标识，不能靠读侧补齐 | F5 只扩会话类型与历史投影 |
| **F6 服务端能力** | F6 负责 HTTP 可完成、运行状态、错误与平台级模型配置，不定义产品问题“什么答案算企业知识” | F7 复用 F6 的模型配置与传输能力 |

**一句话**：F3 回答“资料说什么”，F7 回答“模型知道什么”；两者都必须存在时，边界必须写在域上，不能只在 UI 上画一条线。

#### 1.3 两个入口的产品边界

| 项目 | 知识库问答（F3） | 通用对话（F7） |
|---|---|---|
| 是否检索文档 | 是，系统预检索 | **否**，不打开 `documents` / `chunks` |
| 是否允许凭常识回答 | 否 | 是 |
| 引用 | 必须有；文件名 + 位置 + 原文片段 | **没有引用**，也不显示来源面板 |
| 资料不足 | 明确拒答 | 不适用；模型可以回答“我不知道” |
| 会话类型 | `knowledge` | `general` |
| 历史 | 答案 + 引用快照 + run | 答案 + run；无引用快照 |
| 审计 | 必须留 run | **必须留 run**，但没有检索/证据步骤 |
| 模型配置 | 平台级配置（F6） | 同一份平台级配置（F6），不另设一套 |

**两个入口可以共用一个侧栏，但会话必须带不可变的类型标识。** 列表可以混合展示，也可以按类型筛选；无论哪种，用户都必须能一眼看出“这条有没有企业资料依据”。

#### 1.4 通用对话必须做到的五件事

1. **不查**：不检索企业文档，不读取 `documents` / `chunks`，不生成引用角标，不显示来源面板。
2. **明示**：接口返回与界面都明确标识 `general` / “未使用企业资料”；不能长得像知识库回答。
3. **不混**：会话类型创建时固定，不能在同一条会话里从通用切到知识库或反向切换；切模式 = 新建会话。
4. **不兜**：知识库问答判定“资料不足”后，不得自动转通用对话回答；用户要通用回答必须自己切入口。
5. **留痕**：每次通用回答仍写一条 run，归属到当前用户/团队；run 里没有检索步骤与证据，也**不得伪造**它们。

#### 1.5 不做什么

| 不做 | 理由 |
|---|---|
| 在通用对话里偷偷检索企业文档 | 一旦检索，它就不再是通用对话，而且会绕过知识库的引用、拒答与权限合同 |
| 把通用回答显示成知识库答案 | 用户会把模型常识当成企业原文，这是本域最危险的失败形态 |
| 知识库拒答后自动转通用回答 | “不编”承诺会被自动兜底绕开；用户无法区分“资料里没有”和“模型自己编了一段” |
| 通用会话与知识库会话互相续聊 | 两种答案的合同不同；同一条会话里混入两种答案，历史无法解释 |
| 给通用对话做文档级权限 | 它不读文档；权限仍只到会话归属与团队边界（F1） |
| 通用对话的工具调用 / 联网 / 文件上传 / 跨会话记忆 | 第一版只做纯文本对话；这些能力会引入新的权限与审计边界 |
| 为通用对话单独配一套供应商/模型 | 平台级模型配置由 F6 统一管理，避免“同一问题两套答案前提” |

### 二、功能流程

#### 2.1 入口

- **通用入口**：独立的通用对话路由 `POST /api/chat`，请求带 `question` 与可选 `conversationId`；响应带 `mode=general`，且 `sources` / `citations` 为空。
- **知识库入口**：继续使用 `POST /api/knowledge/ask`，不得因为通用对话存在而改变其检索、引用、拒答行为。
- **会话类型**：创建时写入 `kind=general`；如果请求带上的 `conversationId` 属于 `knowledge`，按“不存在/不可续聊”处理，**不得把通用回答写进知识库会话**。

#### 2.2 一次通用对话的时序

```
t0  请求（question，可选 conversationId）
     │
t1  ├─ 身份与归属：F1 判定当前用户/团队；未登录 401
     │
t2  ├─ 会话解析：新建 kind=general / 复用同 kind 会话
     │              （kind 不匹配 → 不续聊）
     │
t3  ├─ 模型解析：F6 的平台级激活供应商 + 默认模型
     │              （未配置 → 503 model_not_configured，一行不写）
     │
t4  ├─ 写入用户消息；run 进入 running；
     │  同时占一行空 assistant（正文空，run_id 必填）
     │
t5  ├─ 生成：只把会话内历史交给模型
     │  不检索、不塞证据、不产生引用编号
     │
t6  ├─ 终态：succeeded / failed / cancelled / limited
     │  正文写回 t4 那一行；不写引用快照
     │
t7  └─ 历史：消息正文 + run 可回读；来源面板为空
```

**为什么 t4 要先占一行**：与 F5 相同，进程在生成中途被杀时，这次 run 必须仍然属于一条会话；只在结束时写行会留下一条无法归属的历史。

#### 2.3 失败路径

| 失败点 | 用户看到 | 库里的形状 | 不许发生 |
|---|---|---|---|
| 未登录 / 无权 | 401 / 404 | 不写消息、不写 run | 把身份错误伪装成模型错误 |
| 模型未配置 | 503 `model_not_configured` | 不写会话/消息/run | 使用默认值或占位凭据继续答 |
| 模型不可达 / 超时 | 可重试错误 | run 终态 `failed` / `cancelled`，assistant 行保留 | 只删消息不删 run，或留下悬空 run |
| 进程在生成中退出 | 重新打开后看到“进行中/中断” | run 仍为 `running` 或终态，assistant 占位行在 | 历史里完全没有这次运行 |
| 用户尝试续聊知识库会话 | 404 / 引导新建通用会话 | 不写入原会话 | 把通用回答写进 knowledge 会话 |

#### 2.4 与知识库问答的交互边界

- **不自动兜底**：知识库返回 `refused` 时，前端只显示拒答卡与“补资料/换问法”的引导；不得自动调用通用入口。
- **不共享消息流**：一条会话只有一种 `kind`。通用会话里不出现引用卡、来源面板、引用校验结论；知识库会话里不出现“未使用企业资料”的通用标识。
- **可以共享侧栏**：侧栏可以同时列出两类会话，但每条必须带类型标识；筛选、计数、删除都按归属与类型分别正确。

### 三、状态机

#### 3.1 会话类型不是可迁移状态机

`conversations.kind` 是**创建时固定的枚举**，不是运行时可迁移的状态：

| 值 | 含义 | 允许的后续 |
|---|---|---|
| `knowledge` | 知识库问答会话 | 只能继续知识库问答；删除后行消失 |
| `general` | 通用对话会话 | 只能继续通用对话；删除后行消失 |

**禁止的迁移**（实现与测试都必须拒绝）：

| 起点 | 终点 | 为什么禁止 |
|---|---|---|
| `general` | `knowledge` | 同一条会话会混入两套答案合同；引用快照与拒答语义无法解释 |
| `knowledge` | `general` | 历史里会出现“有引用”和“无引用”两种回答，用户无法判断哪条可核 |
| 任意 `kind` | 删除后复用 | 删除是硬删；同一个 id 不再存在，不复活、不软删（F5 §1.7） |

**切模式 = 新建会话**，不是修改 `kind`。UI 的“切换入口”只改变下一次新建会话的类型；不改变当前会话。

#### 3.2 运行状态机复用 F4

F7 **不新增第二套运行状态机**。通用对话沿用 F4 的 `run_lifecycle`：

```
running ──→ succeeded
        ├─→ failed
        ├─→ cancelled
        └─→ limited
```

| 状态 | 通用对话中的含义 | 界面 |
|---|---|---|
| `running` | 正在生成；assistant 占位行已存在 | 打字动画 / 等待 |
| `succeeded` | 生成完成，正文已写回 | 正常回答 + 通用标识 |
| `failed` | 模型调用或落库失败 | 错误提示；可展开 run |
| `cancelled` | 用户停止或连接取消后按实际终态记录 | 已停止；不显示成成功 |
| `limited` | 达到迭代/预算限制 | 说明限制，不伪造完整答案 |

**通用对话不会进入 `refused`**：拒答是知识库“证据不足”的终态，不是通用对话的答案形态。若通用模型自己说“我不知道”，那是 `succeeded` 的正文，不是 `refused`。

**不新增“检索中 / 引用校验中”状态**：通用对话没有这两段。把它们画进状态机等于伪造步骤，违反 F4 的“没有发生的步骤不得记录”。

#### 3.3 状态机登记

本域向 `pyproject.toml` 登记 **`conversation_kind` 类型状态集**，但**不登记任何迁移边**：

- `states = general, knowledge`；合法迁移为空集。切换模式必须新建会话，不能 UPDATE kind。
- 登记的目的不是把它当迁移机，而是让第三种会话类型出现时必须经过闸门审查，而不是悄悄加一个分支。
- `run_lifecycle` 的真源仍是 `agentworkbench.core.runs`，由 F4 维护；F7 只消费，不重复登记第二套运行状态机。

### 四、不变量

按 `00-功能域怎么写.md` §四的判据（去掉一条，另外几条的判据会不会失效），它们是一个功能的五条不变量，不是五个可以分别交付的功能。

| 不变量 | 对应验证 | 去掉之后 |
|---|---|---|
| **不查** | `D-V1` | 通用对话一旦检索，就会产生“有证据/无证据”的混合语义；引用、拒答、权限三套判据同时失效 |
| **明示** | `D-V2` | 用户会把模型常识当成企业原文；产品最核心的“答案有据”承诺变成假承诺 |
| **不混** | `D-V3` | 同一条会话里出现两种答案合同，历史与引用快照无法解释；列表计数也会泄漏类型 |
| **不兜** | `D-V4` | 知识库“资料不足”被自动通用回答绕过，“不编”承诺失效，且用户无法察觉 |
| **留痕** | `D-V5` | 通用回答成为审计后门：有答案、没有 run，F4 的“每个作答入口都留痕”当场不成立 |

**五条必须一起成立。** 没有“先做三条”的算法：只做“不查”会留下冒充风险；只做“明示”会留下审计后门；只做“留痕”会让错误答案看起来可回放。

| ID | 不变量 | 正控（必须成立） | 负控（出现即红） | 落点 |

| `D-V5` | 留痕 | 通用作答恰好产生一条 run；`user_id` / `tenant_id` 正确；assistant 行有 `run_id`；run 无检索证据且不伪造 | 通用回答没有 run；或 run 里出现伪造的 retrieval/evidence 步骤；或归属为他人/默认团队 | `tests/invariants/test_general_chat_contract.py::test_general_chat_writes_one_run_without_retrieval_steps`；`tests/acceptance/test_p0_audit_entries.py::test_every_producing_route_writes_exactly_one_run` |

#### 5.3 明确不测什么

- 不测“通用对话回答一定正确”——模型能力不在本域承诺内；只测**不查、明示、不混、不兜、留痕**。
- 不测引用质量与拒答阈值——那是 F3 的判据，通用对话不产生引用，也不应该继承 F3 的拒答测试。
- 不测文档级权限——通用对话不读文档；只测会话归属与团队边界（F1/F5）。
- 不把“模型自己说不知道”当成 `refused`；这是 `succeeded` 正文。

#### 5.4 人工检查

| 检查 | 判据 |
|---|---|
| 入口标识 | 通用对话页有明确“未使用企业资料”标识；知识库页没有这个标识 |
| 历史可辨 | 侧栏同时出现两类会话时，用户能一眼分辨；类型不会在刷新后丢失 |
| 切换行为 | 从知识库切到通用，不会继续原会话；旧会话仍按原类型可读 |
| 拒答不兜底 | 知识库拒答后，界面不出现自动生成的通用回答 |

### 六、边界与重开条件

#### 6.1 永远不做

- 通用对话检索企业文档、生成引用、复用知识库的引用校验。
- 知识库拒答后自动转通用对话。
- 在一条会话里切换 `kind`。
- 为通用对话另建一套供应商/模型配置。
- 让通用对话读取或写入文档、chunk、引用快照。

#### 6.2 什么情况下该重开

| 条件 | 重开什么 |
|---|---|
