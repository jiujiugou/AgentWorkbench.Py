# 代码规范

- **本文回答**：代码怎么写、为什么这么写——**只写机器判不了的那部分**
- **本文不回答**：能被工具判的（缩进、引号、行宽、import 顺序、注解完整性、依赖方向），那些的真相在 [`pyproject.toml`](../../pyproject.toml)
- **执行方式**：`python scripts/ci.py check`（六段，约 8 秒）

## 〇 一条总则：本文不重复工具已经做的事

能在 `pyproject.toml` 里写成一行配置的规范，**本文一个字都不写**。

判据：如果你在下面读到一条 ruff 或 mypy 已经能查出来的规则，删掉它——重复的规范一定会和配置打架，然后读者不知道该信哪个。

同理，本文**不写**：目录树（会变）、工具版本（在 `pyproject.toml`）、规则清单（同上）。

| 规范类型 | 谁执行 | 在哪 |
|---|---|---|
| 格式、风格、常见缺陷 | `ruff` | `pyproject.toml` 的 `[tool.ruff]` |
| 类型完整性 | `mypy --strict` | `[tool.mypy]` |
| 包边界与依赖方向 | `lint-imports` | `[tool.importlinter]` |
| **标准本身有没有被削弱** | `tests/test_gates.py` | 13 条断言 |
| 语义、命名、错误处理、异步约定 | **本文 + review** | 这里 |

**最后一格是本文的全部职责。** 它判不了，所以只能写下来靠人守——写下来之后至少争论有依据。

## 一 包边界：每个包只回答一个问题

依赖方向由 `lint-imports` 强制，**方向写错会红**，这部分不需要本文。本文要写的是**为什么这么分**，因为你改目录结构时工具不会拦你。

| 包 | 只回答 | 不许出现 |
|---|---|---|
| `core` | 数据长什么样、状态有哪些 | 任何 IO、任何第三方库、任何对其他包的 import |
| `db` | 数据存在哪、怎么读写 | 业务判断（"够不够"、"能不能"不是 SQL 的事） |
| `identity` | 身份与访问：判定、身份表持久化、登录/邀请流程 | HTTP 路由、DTO 组装、生成答案 |
| `llm` | 怎么和模型说一次话 | 提示词内容（那属于 `agent` / `guard`） |
| `rag` | 去哪儿找、找出什么 | "找到的够不够用"（那是 `guard`） |
| `guard` | 够不够、能不能信 | 检索（自己不查库，只判 `rag` 交来的东西） |
| `ingest` | 文件怎么变成可检索的证据 | 问答逻辑 |
| `agent` | 一次 run 怎么编排 | 任何单项能力的具体实现 |
| `trace` | 发生过什么、怎么回放 | 对业务的判断 |
| `chat` | 会话里有什么、怎么还原 | 生成答案 |
| `api` | 协议怎么转 | **任何业务判断**（api 层出现 if 就是在挪业务） |

三条硬规矩：

1. **`core` 不 import 本项目的任何其他包。** 它是词汇表，词汇表不应该依赖使用它的人。
2. **新代码的 SQL 放 `db`。** 在 `rag` 里写一句 `SELECT` 看似方便，但事务边界就分不清了——C# 版混用 Dapper + EF Core 的代价正在这里。

   现状不是这样：例如 `rag/indexer.py`、`ingest/deletion.py`、`api/routes/settings.py`、`identity/store.py`（身份五张表）里都有直接写 SQL 的地方。这些是既有实现，不是新规矩；新增代码不要照抄，改动时优先往 `db` 收。

3. **`api` 不写 if。** 出现条件分支说明判断漏到了协议层，应该退回 `guard` 或 `agent`。

### 新增一个包之前

只问一句：**它会不会和现有包一起改？** 会 → 并进去，别新建。

Python 没有编译期边界，每个包的收益（自动拦反向依赖）很弱，成本（导出面、循环导入）很实。C# 那边 17 个项目里 6 个只为了让框架跑起来，别重复这个路径。

## 二 命名：让名字承担类型系统做不到的事

Python 的类型是注解，不是契约。所以**名字必须额外告诉你两件事：有没有副作用、失败怎么表达**。

### 2.1 动词前缀约定

| 前缀 | 含义 | 有没有 IO |
|---|---|---|
| `build_` / `make_` | 纯构造，同样输入必得同样输出 | 无 |
| `parse_` / `normalize_` | 纯转换 | 无 |
| `judge_` / `check_` | 纯判定，返回判定结果 | 无 |
| `load_` / `save_` / `fetch_` | 读或写外部 | **有** |
| `run_` / `execute_` | 跑一整条链路，可能有副作用 | **有** |

看到 `build_answer()` 就知道它不该访问网络；看到 `build_` 里有 `await session.get(...)`，那是命名撒谎，review 直接退。

### 2.2 反例与正例

| 别写 | 写成 | 理由 |
|---|---|---|
| `process_document()` | `parse_pdf()` + `index_chunks()` | "处理"什么都没说，一个函数干两件事 |
| `handle_error()` | `classify_failure()` | "handle"是万能动词，等于没名字 |
| `get_data()` | `load_chunks()` | "data"不是名词，是占位符 |
| `check()` | `judge_sufficiency()` | 判定什么？名字里必须有宾语 |
| `flag` / `tmp` / `obj` / `info` | 具体名词 | 同上 |

### 2.3 禁用文件与目录名

`utils.py`、`helpers.py`、`common.py`、`manager.py`、`misc.py`。

理由不是洁癖：**这类文件没有主人**。放进去的东西不会有人 review，三个月后里面有一半是死代码，而且没人敢删。真需要共享，它会自然地属于某个已有包（`core` 放类型，`db` 放查询）。

### 2.4 语言

- 标识符、文件名、包名：**英文**
- 注释、文档字符串、提交信息：**中文**，用全角标点（`RUF001/002/003` 已为此全局豁免）

包名用职责名，不用复数：`rag` 不是 `rags`，`guard` 不是 `guards`。

## 三 错误与状态：本项目的核心，单独讲

这个产品的差异化就是"答错了能查清"。所以错误的表达方式不是风格问题，是产品问题。

### 3.1 业务分支不用异常

判定结果（已回答 / 依据较弱 / 资料不足 / 未判定）是**正常返回值**，不是异常。抛异常表达"资料不足"会让调用方被迫用 try 表达正常流程，也拿不到判定依据。

异常只用于"本不该发生"：磁盘满了、配置缺了、模型端返回了 500。

### 3.2 错误必须带码

```python
raise ModelNotConfiguredError(code="model_unavailable")
```

C# 版 `AgentRunCode` 那套（`cancelled` / `run_timeout` / `model_timeout` / `tool_error` / `model_unavailable`）照搬，因为**"超时"至少有两种，归成一类就查不出问题**：整条 run 跑满预算，和单次模型调用超时，处理方式完全不同。

### 3.3 禁止的三种写法

| 禁 | 为什么 |
|---|---|
| `except Exception: pass` | 吞掉的是证据。审计链就是这么断的 |
| `except:` 裸捕获 | 连 `KeyboardInterrupt` 都吃 |
| 终态用 `else` 兜底 | 状态机的终态必须显式列出，兜底等于隐藏新状态 |

补一条：**状态迁移必须合法**。`cancelled` 之后不许再写步骤，`succeeded` 不许回退。写不出迁移表，说明状态设计还没想清楚。

### 3.4 顺序：先落记录，后判结论

拒答、否决、终止这些动作发生时，**证据必须先写进 record**，再执行停止。否则事后查"它看到了什么才拒的"——查不到。C# 版的注释写得很清楚："先落轨迹、再判"，这句要继承。

## 四 异步：全项目 async，失误代价最高

`ruff` 的 `ASYNC` 规则集能抓一部分（漏 `await`、在 async 里用同步锁），抓不到下面三条。

### 4.1 阻塞调用不许出现在 async 函数里

`time.sleep`、`requests`、同步文件 IO、同步数据库驱动——都必须包进 `asyncio.to_thread()`。

一个阻塞调用会卡住整个事件循环，症状是"别的请求无响应"，而堆栈指向完全无关的地方。

### 4.2 不裸 `create_task`

`asyncio.create_task()` 的返回值没有强引用会被 GC 回收，任务静默消失。要后台跑就建一个集合持有它，并在退出时 `await`。

### 4.3 超时必须说清是哪一层

| 层 | 含义 | 错误码 |
|---|---|---|
| 单次模型调用 | 这一次请求没回来 | `model_timeout` |
| 整条 run | 预算用完，还在循环 | `run_timeout` |
| 工具调用 | 工具自己卡住 | `tool_error` |

三者不能共用一个超时值，也不能共用一个错误码。C# 版踩过一次：合成一个之后，"是模型慢还是循环没收敛"查不出来。

## 五 注释与文档字符串

只写**为什么**，不写**是什么**——是什么代码里已经写着。

```python
# 好：解释一个看不出来的取舍
# 判定必须在工具返回之后做：此时证据已经落库，拒答也有据可查。

# 坏：重复代码
# 调用 judge 方法
result = judge_sufficiency(hits)
```

三条禁令：

- **不写时间戳、作者名、"临时"**——"临时"是最永久的三个字
- **不留被注释掉的代码**——git 记得，文件不记得
- **不写"下一步要做"**——那是任务，不是代码

### 5.1 实现某个决策时，注释标决策编号

移植过来的设计决策（`D-01`~`D-12`、`A-01`~`A-07`）在代码里要留指针：

```python
# D-01：用间隔而不是融合分——融合分第一名恒为 1/61，不表达相关程度
margin = second_to_fifth_mean - first_distance
```

这样从代码能查到决策，从决策能查到代码。半年后想问"为什么不用余弦相似度"，两边都找得到答案。

### 5.2 配置项必须有消费者

新增一个配置项，必须同时有读它的代码。**没有消费者的配置比没有这个配置更糟**——下一个人（或下一个 agent）会以为对应机制还在。

## 六 测试的写法

工具管不了"这条测试有没有用"，只能靠写法约定。

**什么时候该先写、写几条、怎么算完成，见 `docs/实现/流程.md`。本节只管写出来之后长什么样。**

### 6.1 一个文件一条不变量

`tests/invariants/` 下每个文件对应一条不变量，文件头写清三件事：

```python
"""不变量：资料不足时不给答案。

改坏时用户看到什么：一段很像手册内容的排查建议，末尾附一句"资料不足以回答"。
——比空答案更危险，因为编造被包装过了。
"""
```

### 6.2 测试名说"什么坏了"，不说"测什么函数"

| 别写 | 写成 |
|---|---|
| `test_judge()` | `test_没有证据时不进入生成` |
| `test_verify_returns_true()` | `test_相邻功能码的误挂必须被拦住` |

### 6.3 断言必须能红

写断言时先写出反例。写不出反例的断言不要写——C# 版留下过教训：`assert gap < 0.20` 在覆盖率退化成永远返回 0 时照样绿，那是恒真式，不是验证。

### 6.4 测试里不许 sleep

等待用事件、用轮询条件、用 `pytest-timeout` 兜底。`sleep` 会让测试在不同机器上时快时慢，最终被人加 `-x` 跳过。

## 七 豁免流程

工具判不了"这个豁免合不合理"，所以必须有流程。**豁免不是禁止的，无声的豁免才是。**

| 要豁免什么 | 写法 | 记在哪 |
|---|---|---|
| 一行 lint | `# noqa: E501` | 行内，必须带码 |
| 一行类型 | `# type: ignore[arg-type]` | 行内，必须带码 |
| 一个文件的某类规则 | `[tool.ruff.lint.per-file-ignores]` | `pyproject.toml`，必须写理由注释 |
| 一类规则的全局豁免 | `[tool.ruff.lint] ignore = [...]` | 同上，且要在 `test_gates.py` 登记 |

**裸豁免一律禁止**（`# noqa` 不带码、`# type: ignore` 不带码），`ruff` 的 `PGH` 规则集和 `test_gates.py` 会同时拦。

### 铁律：改 `test_gates.py` 的基线 = 改标准

`tests/test_gates.py` 顶部的常量（`REQUIRED_RULE_SETS`、`ALLOWED_GLOBAL_IGNORES`、`ALLOWED_PER_FILE_IGNORES`、`MIN_LAYERS`）是**标准的快照**。

改它们不是改测试，是**下调标准**。因此：

- 必须在同一次提交里说明理由
- 理由写"这条规则误报了 X"，不写"暂时先这样"
- 放宽之后如果不打算改回来，在本文对应位置补一行记录

这条是整套机制里最容易被绕过的一环：`test_gates.py` 全绿不代表标准没变，只代表标准和快照一致。

## 九 本文怎么改

本文允许**删条目**，而且鼓励删：一条规范一旦被工具接管，就应该从这里消失。

改之前问：这条能不能写成 `pyproject.toml` 里的一行？能 → 删掉本文这条，去改配置。

不能 → 留下，并写清"为什么工具判不了"。写不出这句，这条就不该存在。
