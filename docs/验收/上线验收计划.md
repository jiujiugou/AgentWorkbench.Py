## 1. 方法论：不读代码，如何判断质量

### 1.1 角色转变

AI 工程里，人的职责从「写代码 / 审代码」变成：

> **定义可证伪的验收条件，抽查证据，做发布决定。**

读代码只在「某条证据对不上」时用来定位，不是验收手段。

### 1.2 四层证据

| 层 | 回答的问题 | 当前状态 |
|---|---|---|
| 1. 机器闸门 | 类型、格式、依赖、导入边界是否守住 | **已有**：`scripts/ci.py check` |
| 2. 测试的牙齿 | 实现被改坏时，测试会不会红 | **已有**（D4）：`scripts/mutation.py` 20 个注入点全被抓 |
| 3. 黑盒验收 | 真实部署后，产品行为是否符合需求 | **半有**：`scripts/smoke.py` + 端到端测试 |
| 4. 对抗验收 | 越权、删除残留、审计绕过、密钥泄露能否被挡住 | **半有**：D2 已补 P0-1/2 对抗用例，D4 补了删除残留的变异证明；审计绕过、密钥泄露的对抗验收待 D6 |

**为什么第 2、4 层必须单独做**：AI 会同时写实现和测试。测试全绿可能只是「测试和实现一起错了」。只有变异测试能检验测试本身，只有对抗验收能检验系统边界。

### 1.3 三条原则

1. **不把「测试全绿」当达标**——要证明测试能红。
2. **不把「文档状态列」当事实**——文档可能停留在 C# 结论。
3. **不接受 AI 自报结论**——每条结论必须带可执行 repro，由人亲手跑一遍。

### 1.4 你该看什么 / 不该看什么

| 该看 | 不该看 |
|---|---|
| 需求 → 验收条件 → 测试名 → 失败信息 | 逐行读实现 |
| 覆盖率地图、变异报告、黑盒执行记录 | 文档里的进度表 / 状态列 |
| 线上 trace、日志、指标 | AI 的「已完成」总结 |
| 截图、响应体、退出码 | 没有证据的架构说明 |

### 3.2 P1 · 允许带风险上线

| # | 判定项 | 通过线 |
|---|---|---|
| 1 | 检索质量不退化 | HitRate ≥ 0.906，MRR ≥ 0.733 |
| 2 | 拒答能力可测 | 库外题扩到 15 条，拒答率达标（先定标） |
| 3 | 引用可信 | 抽样 0 条编造引用，覆盖率 ≥ 0.8 |
| 4 | 切块接缝 | ≤ 7.52% 不退化；已知限制记录在案 |

### 3.3 判定规则

- **P0 全绿 + P1 全绿**：可上线。
- **P0 全绿 + P1 有红**：有条件上线，必须写明风险、监控项、回滚方案。
- **P0 任一红**：不上线。修完重跑，不做「口头豁免」。
- **P0 无法执行**（缺环境/凭据）：记为「无法判定」，不得记为通过。

### 3.4 修复与标定的顺序

先分清两类问题，不要混在一起：

| 类型 | 例子 | 顺序 |
|---|---|---|
| 确定性缺陷（P0） | 越权、审计后门、历史丢失、部署失败 | **先修复**，没有标定空间 |
| 质量阈值（P1） | 接缝率 5%、拒答率、引用覆盖率 | **先标定**，再决定修不修 |
| 缺失证据（manual） | I-H5、S-H1、C-H2 | **先测量**，红了再修 |

**接缝率 V-11 / G2 的判定顺序：**

1. 从 40 处接缝抽样 10–15 条，确认是否产生用户可见的「半句引用 / 断头引用」。
2. 有可见后果 → 修解析层（表格 / 代码行），按 P0-adjacent 处理。
3. 无可见后果 → 把目标标定为「不退化于 7.52%」，记录为已知限制，P1 通过。

**不要为了一个继承来的 5% 数字重写解析器，除非用户能感知。**

四项都不是"扫描器报的"，是**按攻击者/事故视角走一遍时撞出来的**：

1. **（高）Windows + WAL 并发开连接会退化成只读连接**。并发激活供应商的用例 5 次红 3 次，报 `attempt to write a readonly database`。四组对照（8 线程 × 10 轮）：冷启动 **59/80** 失败、热库 **5/80**、热库+常驻连接 **0/80**、修复后 **0/80**。修法是 `engine.connect` 开完先 `begin immediate` 验可写、退化就重开（探测 10ms busy_timeout，拿到 `BUSY` 视为可写），代价 1.17ms/连接。这条的重要性在于：它只在并发时出现，单线程跑一万次也复现不了——此前 700+ 测试全绿也照样漏。
2. **（中）校验失败回显提交的 apiKey**。FastAPI 默认 422 的每条错误都带 `input`，`apiKey` 写成对象时哨兵被原样回进响应；且默认体没有 `message`，前端只能把这段 JSON 原文显示给用户。改为五字段信封（400 + `validation_failed`），只报字段与错误类型、不碰 `input`/`ctx`。
3. **（中）换密钥后 500 且标成可重试**。`crypto.decrypt` 的 `ValueError` 冒泡到兜底 handler，「重试一万次也不会好」的错误被提示"稍后重试"。改为 503 `model_not_configured`、不可重试、文案直接说"重新保存一次凭据"。
4. **（中）失败请求在日志里查不到**。503/404 一条日志都不写，客户端贴来 `X-Request-Id` 搜不到任何东西——"响应里带 request_id"这件事此前只在 500 时成立。`on_app_error` 统一记 code/status/path/request_id/reason。

## 6. 台账升级（防止 AI 自报）

现状：`tests/test_gates.py::test_verification_table_matches_tests` 只能保证 `pass` 条目引用的测试文件/函数存在，不能保证测试有牙齿，也不能保证 `manual` 真的验过。

升级建议：

1. 给每条增加字段：
   - `evidence`：证据文件路径或 URL
   - `verified_at`：实际执行日期
   - `verified_by`：人 / 机器
   - `mutation`：该条是否有改坏证明（仅 pass 必填）
2. 闸门扩展：
   - `pass` 要求 `evidence` 文件存在，且对应测试未被 `skip` / `xfail`。
   - `manual` 要求 `verified_at` 与截图路径，否则 CI 红。
   - `fail` 必须写 `reason` 与「是否阻断上线」。
3. 台账状态变更必须出现在 diff 里，提交信息说明理由。

目标：让台账从「AI 自报」变成「发布闸门」。

## 7. 前提与阻塞

### 7.1 文档漂移（内部前提）

| 文档 | 问题 | 处理 |
|---|---|---|
| `README.md` §当前状态 | 仍写「无业务实现」 | 标记为历史，或更新 |
| `docs/需求/阶段1功能需求.md` | 状态列是 C# 结论 | 标记为历史结论 |
| `docs/需求/功能需求.md` | REQ-21/22 自述「尚无 AC」 | 本计划补上可执行判据 |
| 缺失文档 | `验收条件.md`、`非功能需求.md`、`用户与权限.md`、`待确认决策.md`、`接口.md` | 不编造；以本计划与台账替代 |

**事实源约定**：`pyproject.toml` 验证台账 = 当前验收到哪；`docs/验收/` = 本次上线判定的执行记录；需求文档 = 产品定义，不当作进度表。

### 7.2 外部前提

| # | 前提 | 用途 | 缺失后果 |
|---|---|---|---|
| 1 | 干净部署环境（第二台机器 / VM / 容器） | D5、I-H1、NFR-07/08 | 只能模拟，不能给出真实上线结论 |
| 2 | 真实模型凭据（Zhipu 等） | D8、A-H1、G6/G8/G11/G12 | **已具备（2026-11-05）**：从 C# 版库里迁回智谱与硅基流动两把钥匙，chat 用 `glm-4-flash-250414`、embedding 用 `BAAI/bge-m3`；仍缺的是"去供应商后台对账"那一步人工 |
| 3 | 第二个账号 / 团队 | D5、I-H5、I-H3（D2 已用夹具） | 隔离验收降级为仓储层模拟 |
| 4 | 允许新增开发依赖 | D4/D6/D7 | 变异、契约模糊、UI 自动化受限 |

**处理原则**：缺哪项，就把对应 P0 标为「无法判定」，不假装通过。

## 8. 角色分工

| 你（验收负责人） | AI（实现方） |
|---|---|
| 定 P1 阈值（拒答率、引用覆盖率） | 写验收测试与对抗测试 |
| 跑 `scripts/acceptance.py`，看红/绿 | 修 P0 阻断项 |
| 看截图与报告，判断「人看起来一样」 | 提供可执行 repro |
| 要求每条结论带 repro，并亲手跑一遍 | 更新台账与证据 |
| 做最终 Go/No-Go 决定 | 不替你做发布决定 |

**你不读实现代码。** 只在某条证据对不上时，打开对应文件定位。

## 9. 以后每轮 AI 交付契约

每次让 AI 改代码，要求交付以下六项，缺一项不算完成：

1. 对应哪条 REQ / AC
2. 先红的测试（贴出红在哪一行）
3. 实现后全绿
4. 一次改坏证明（改哪处 → 红哪几条）
5. CI 输出
6. 更新验证台账与证据路径

这与 `docs/实现/流程.md` 的四步循环一致：**定契约 → 写断言 → 实现 → 改坏再恢复**。

## 10. 不做什么

- 不逐行读全部代码。
- 不相信文档里的进度表 / 状态列。
- 不用「测试全绿」当达标。
- 不让 AI 自己给自己打分。
- 不把 `manual` 当成「以后再说」。
- 不为通过验收而降低判据。
- 不在 P0 未过时用「演示效果不错」替代结论。
